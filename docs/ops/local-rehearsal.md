# Локальная репетиция пилота

Runbook репетиции выката на машине разработчика. Выкат пилота описан в `docs/ops/deploy.md` (раздел «Пилот»), чек-лист основателя — `docs/founder/pilot-checklist.md`. Код репетиции — `tools/deploy/local.mjs`, слой Helm и образ узла — `infra/local/*`, приёмка — `packages/e2e/specs/rehearsal/pilot.spec.ts`.

## Зачем

Сервера для пилота пока нет, а выкат нельзя проверять только на живой ВМ: каждая ошибка стоит 35–50 минут `bootstrap-pilot`. Репетиция выполняет на машине разработчика всё то же, что `bootstrap-pilot`, кроме создания облачных ресурсов:

- тот же чарт `infra/helm/wizard` и те же слои значений (`k3s` → `pilot` → `staging` → `pilot-staging`), плюс один локальный оверлей;
- те же образы из `tools/deploy/images.mjs`, те же аддоны из `infra/helm/addons/addons.json`;
- те же ключи (`tools/deploy/pilot-secrets.mjs`), те же Secrets кластера, тот же релиз (`wizardReleaseArgs`, `releaseWizard`);
- те же проверки после релиза: проба gVisor, проверка архива WAL-G, Job основателя, smoke через ingress.

Вместо ВМ Timeweb работает k3s в контейнере Docker. Заменено только то, чего нет на ноутбуке: GHCR, S3, выпуск сертификатов и почта (таблица «Чем репетиция отличается от боевого сервера»). Ничего из этого не уходит за пределы машины.

## Требования

| Что | Значение |
|---|---|
| Docker Desktop | не меньше 8 ГБ памяти под виртуальную машину (Settings → Resources) |
| Node | 22 и новее |
| Свободные порты | 80 и 443 (ingress), `127.0.0.1:6443` (API k3s), `127.0.0.1:8025` (Mailpit), `127.0.0.1:9101` (консоль MinIO) |
| helm | не нужен: запускается в контейнере `alpine/helm:3.19.0` |
| kubectl | не нужен отдельно: берётся из Docker Desktop или из `PATH` |
| Диск | образы и тома остаются между запусками; `down --purge` очищает их |

Состояние репетиции (ключи, локальный CA, kubeconfig) лежит в `.data/local` и не попадает в git.

## Команды

```sh
node tools/deploy/local.mjs up [--tag <sha>] [--observability]
node tools/deploy/local.mjs smoke
node tools/deploy/local.mjs status
node tools/deploy/local.mjs down [--purge]
node tools/deploy/local.mjs secrets <systemId>
```

| Команда | Что делает |
|---|---|
| `up` | собирает недостающие образы, поднимает стек, выкатывает релиз и выполняет проверки (раздел ниже). Повторный запуск идемпотентен: выкатывает поверх работающего стека. Код выхода 0, только если прошли smoke и проба gVisor |
| `up --tag <sha>` | берёт образы с этим тегом вместо тега рабочего дерева. Недостающие собираются |
| `up --observability` | дополнительно ставит VictoriaMetrics, VictoriaLogs и сборщик логов. По умолчанию наблюдаемость выключена: она занимает память, а проверять выкат не мешает |
| `smoke` | проверяет платформу и домен систем через ingress, как `bootstrap-pilot`. Выполняется в отдельном процессе Node с `NODE_EXTRA_CA_CERTS=.data/local/ca.crt` |
| `status` | узлы и поды всех пространств имён, сертификаты cert-manager |
| `down` | удаляет контейнеры и сеть. Тома `wizard-local-k3s` и `wizard-local-minio` и каталог `.data/local` остаются: следующий `up` продолжит с теми же данными |
| `down --purge` | дополнительно удаляет тома и `.data/local`: ключи, CA, kubeconfig. Следующий `up` начнёт с нуля |
| `secrets <systemId>` | шаг оператора: кладёт тестовые prod-значения (`rehearsal-<имя>`) всех `secret://` черновика системы через `SecretStore` внутри пода platform-api. Нужен перед публикацией системы с интеграциями (G2-SECRET-02): экрана для этого в продукте пока нет — на пилоте то же придётся делать основателю (см. «Что репетиция уже нашла») |

Доступ к кластеру вручную:

```sh
KUBECONFIG=.data/local/kubeconfig kubectl -n wizard-platform get pods
```

## Что делает `up`

1. **Тег образов.** Это коммит (`git rev-parse --short=12 HEAD`, как тегирует `images.yml`). При незакоммиченной работе тег — коммит и `-wip<хэш>`: хэш считается по `git diff HEAD` и содержимому неотслеживаемых файлов (кроме `.omc/`). Образы пересобираются, только если исходники действительно изменились.
2. **Образы.** Недостающие образы `wizard-local/<имя>:<тег>` собирает `tools/deploy/images.mjs build --registry wizard-local` — из LF-снимка рабочего дерева в `.data/local/build-context` (временный индекс git, рабочее дерево и индекс не трогаются). Без снимка чекаут Windows с `core.autocrlf=true` положил бы в образы исходники с CRLF, в отличие от CI, и G1-RENDER-01 на M1+ ломался бы на якорях `packages/sdk`. Образ узла `wizard-local/k3s-node:v1.34.1-k3s1` собирается из `infra/local/k3s-node.Dockerfile` (раздел «Узел k3s»).
3. **Ключи.** `ensureBundle` из `pilot-secrets.mjs` создаёт тот же набор, что и пилот: пароль PostgreSQL, `WIZARD_SECRETS_KEY`, `WIZARD_PREVIEW_SECRET`, `WIZARD_INTERNAL_TOKEN`, `WALG_LIBSODIUM_KEY`, `WIZARD_DATA_BACKUP_KEY`. Плюс учётная запись MinIO. Файл — `.data/local/secrets.json`, права 600; при следующих запусках ключи берутся из него.
4. **Локальный CA и сертификаты.** Один раз, через `openssl` образа `wizard-postgres` (отдельный openssl на хосте не нужен). Создаются CA `Wizard local rehearsal CA` и три сертификата на 825 дней: платформы (`wizard.localhost` и `*.wizard.localhost`), систем (`wsys.localhost` и `*.wsys.localhost`) и SMTP Mailpit. Файлы лежат в `.data/local`.
5. **Сеть и контейнеры.** Сеть Docker `wizard-local` с подсетью `198.18.0.0/24` и три контейнера с фиксированными адресами:

   | Контейнер | Адрес | Роль |
   |---|---|---|
   | `wizard-local-k3s` | `198.18.0.2` | узел k3s; порты `127.0.0.1:80`, `127.0.0.1:443`, `127.0.0.1:6443` — только эта машина, не локальная сеть |
   | `wizard-local-minio` | `198.18.0.3` | MinIO на `:443` по http; бакеты `wizard-files` и `wizard-backups`; консоль `127.0.0.1:9101` |
   | `wizard-local-mail` | `198.18.0.4` | Mailpit: SMTP `:587` со STARTTLS и локальным сертификатом, веб-интерфейс `127.0.0.1:8025` |

   Скрипт ждёт, пока узел станет Ready (до 3 минут), и сохраняет kubeconfig в `.data/local/kubeconfig`.
6. **Импорт образов.** Образы этого тега переносятся в containerd узла (`docker save` → `ctr images import`). На ВМ их тянет GHCR; здесь тянуть неоткуда, поэтому pull-секрета нет, а политика — `IfNotPresent`. Уже импортированные образы пропускаются.
7. **Аддоны.** Пространства имён из `infra/k8s/namespaces.yaml`, затем аддоны профиля `pilot`: cert-manager и Traefik. VictoriaMetrics, VictoriaLogs и `logs-collector` ставятся только с флагом `--observability`.
8. **Secrets кластера.** Тем же кодом, что на ВМ (`clusterSecretFiles`): `wizard-platform-env`, `wizard-postgres`, `wizard-pgbouncer`. Вместо S3 и SMTP Timeweb подставлены адреса MinIO и Mailpit (`WIZARD_SMTP_PORT=587`, `WIZARD_SMTP_TLS=starttls`, отправитель `Wizard <noreply@wizard.localhost>`). Ключи живых моделей — из `inputs.env` (раздел «Живые модели»). Секрет DNS-01-решателя не нужен.
9. **TLS-секреты.** `wizard-platform-tls` и `wizard-systems-tls` из сертификатов локального CA. ресурсы Certificate остаются неготовыми: Let's Encrypt не вызывается, ingress отдаёт готовые Secrets.
10. **Релиз.** `wizardReleaseArgs` и `releaseWizard` из `infra.mjs` с профилем `pilot` и слоем `staging`, затем оверлей `infra/local/values-local.yaml` и `config.llmMode` (`live` или `fixture`). `postgres.firstBoot` ставится, только если архив WAL-G в `wizard-backups/pg/` пуст (то же правило, что у `pg-ops`): потерянный том узла при живом MinIO восстанавливается из архива, а не делает initdb рядом со старым архивом. Контейнеры пересоздаются сами, если изменились их параметры (метка с хэшем аргументов); тома при этом сохраняются.
11. **Доверие подов к локальному CA.** Платформа и runtime ходят на SMTP по STARTTLS с сертификатом локального CA. Перед релизом создаётся ConfigMap `wizard-local-ca` (ключ `ca.crt`); чарт по `extraCa.configMap` из `values-local.yaml` монтирует его только для чтения в platform-api, worker и runtime (`/etc/wizard/extra-ca/ca.crt`) и задаёт `NODE_EXTRA_CA_CERTS`. В настоящих окружениях `extraCa` выключен. CA ограничен по именам (`nameConstraints`: только домены и сеть репетиции), ключи — права 600, Mailpit монтирует только свою пару из `.data/local/mail`. Затем скрипт ждёт готовности всех deployments (до 10 минут).
12. **Проверки после релиза** (те же функции, что у `bootstrap-pilot`):
    - проба gVisor: проверочный под в песочнице под `runtimeClassName: gvisor`;
    - проверка архива WAL-G: `wal-g backup-list` из работающей базы в бакет `wizard-backups`;
    - Job основателя `wizard-founder-staff`: создаёт приглашение для `founder@wizard.localhost` и выдаёт права staff после первого входа;
    - smoke через ingress: HTTPS платформы и домена систем.
13. **Сводка.** Адреса доступа, итог smoke и пробы gVisor, команда kubectl.

### Сеть 198.18.0.0/24

Адреса сети репетиции — из диапазона RFC 2544, а не из RFC 1918 (`10/8`, `172.16/12`, `192.168/16`). Причина в NetworkPolicy чарта: правила выпускают платформу к S3 и SMTP только на **публичные** адреса и только на порты 443 (S3) и 465/587 (SMTP). Частные диапазоны из правил исключены. Поэтому MinIO слушает порт 443 (по http, без TLS), а SMTP Mailpit — порт 587. Так политики репетиции совпадают с боевыми, и ошибка в них проявится так же, как на ВМ. Тот же адрес MinIO передан runtime в `runtime.s3Cidrs` (`198.18.0.3/32`).

Сеть подов k3s — `10.42.0.0/16`, сервисов — `10.43.0.0/16`.

Внутри кластера домены репетиции (`wizard.localhost`, `*.wsys.localhost`) разрешаются в адрес узла `198.18.0.2` — блоки `template` в ConfigMap `kube-system/coredns-custom`. Так же на ВМ имена указывают на её плавающий IP: worker после публикации проверяет систему по её адресу через ingress. Без этого `*.localhost` в поде — это сам под (`ECONNREFUSED 127.0.0.1:443`).

### Узел k3s

Образ узла (`infra/local/k3s-node.Dockerfile`) повторяет сервер из cloud-init пилота (`infra/k3s/server.yaml.tftpl`):

- k3s `v1.34.1+k3s1` — та же версия, что в модуле OpenTofu;
- `runsc` и `containerd-shim-runsc-v1` из того же apt-репозитория gVisor, что и в cloud-init;
- шаблон containerd `infra/local/containerd-config-v3.toml.tmpl` — тот же блок обработчика `runsc`, что на ВМ;
- `infra/local/runsc.toml`: платформа `systrap`. Она не требует KVM, которого нет в виртуальной машине Docker Desktop.

Узел запускается привилегированным контейнером с метками `wizard.ru/pool=free` и `wizard.ru/sandbox-node=true`, Traefik из k3s отключён (его ставит аддон), шифрование секретов включено.

## Живые модели

По умолчанию репетиция идёт на золотых фикстурах (`config.llmMode=fixture`): сеть не нужна, как у staging пилота. Чтобы пройти на живых моделях, как prod пилота, создайте файл `.data/local/inputs.env` с теми же именами, что у секретов GitHub:

```sh
CLOUDRU_API_KEY=...
ZAI_API_KEY=...
```

- Формат — строки `ИМЯ=значение`; кавычки вокруг значения допустимы, пустые значения игнорируются. Передаются имена из `PLATFORM_PASSTHROUGH` в `pilot-secrets.mjs` (например, `WIZARD_TELEGRAM_BOT_TOKEN`).
- Если задан `CLOUDRU_API_KEY` или `ZAI_API_KEY`, выставляется `config.llmMode=live`. Иначе — `fixture`. Выбранный режим печатается при выкате.
- Файл читается при каждом `up`. После правки запустите `up` ещё раз: Secret обновится, релиз выкатится заново.
- Ключ остаётся на вашей машине в `.data/local` (в git не попадает). Не копируйте его в чат и PR.

## Приёмочный сценарий

Проверяет первый день пилота (`docs/founder/pilot-checklist.md`, §9) на развёрнутом стенде, только через публичный ingress. Dev-стенд не запускается, к базе сценарий не обращается. Письма он читает из Mailpit.

```sh
pnpm --filter @wizard/e2e exec playwright test -c playwright.rehearsal.config.ts
```

Сценарий последовательный, 5 шагов:

1. основатель входит по коду из письма, Job выдаёт права staff, подключается MFA в `/admin`;
2. основатель включает готовность беты с заметкой «D25 пилот без юр. обвязки» и приглашает клиента;
3. клиент входит по ссылке из письма, видит онбординг пилота (организация, 150 кредитов);
4. клиент собирает золотой «форум»: гейты G0 и G1 проходят в песочнице кластера (workerd под gVisor), превью открывается;
5. клиент публикует, основатель одобряет в `/admin`, система отвечает на своём домене `<slug>.wsys.localhost`.

Сценарий проверяет текст золотого «форума» («Северный ритейл»), поэтому запускайте его в режиме фикстур, без ключей в `inputs.env`.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `WIZARD_E2E_WEB` | `https://wizard.localhost` | адрес платформы |
| `WIZARD_E2E_MAILPIT` | `http://127.0.0.1:8025` | адрес Mailpit |
| `WIZARD_E2E_FOUNDER` | `founder@wizard.localhost` | почта основателя |
| `WIZARD_E2E_SYSTEMS` | `wsys.localhost` | домен систем |
| `WIZARD_E2E_STATE_DIR` | `.data/local` | где хранятся секрет TOTP (`founder-totp.secret`) и сессия основателя (`founder-session.json`) |

Секрет TOTP и сессия основателя сохраняются между запусками: повторные коды на один адрес упираются в лимит одноразовых кодов (так задумано). Если нужен чистый вход, удалите эти два файла или выполните `down --purge`. Браузер не знает локальный CA, поэтому в конфигурации `playwright.rehearsal.config.ts` включено `ignoreHTTPSErrors`. Отчёт и снимки экранов — `packages/e2e/playwright-report/rehearsal`.

## Чем репетиция отличается от боевого сервера

| Слой | Боевой пилот | Репетиция |
|---|---|---|
| Образы | GHCR, pull-секрет с токеном задания выката | импорт в containerd узла, pull-секрета нет |
| Объектное хранилище | Timeweb S3 | MinIO в контейнере, `198.18.0.3:443` по http |
| Сертификаты | Let's Encrypt, ACME DNS-01 через DNS Timeweb | локальный CA, Secrets создаёт `local.mjs` |
| Почта | Unisender Go, порт 465 | Mailpit, порт 587 со STARTTLS, письма не покидают машину |
| Сервер | ВМ Timeweb, k3s из cloud-init | привилегированный контейнер Docker с k3s, runsc на платформе `systrap` |
| Адреса | публичные домены платформы и систем | `wizard.localhost` и `wsys.localhost` |
| Релиз, Secrets, чарт, NetworkPolicy, gVisor, WAL-G | как есть | как есть |

**Не проверяются:**

- выпуск сертификатов Let's Encrypt и DNS-01-решатель;
- DNS Timeweb: записи платформы и систем, SPF, DKIM, DMARC;
- firewall и SSH-доступ раннера к ВМ;
- реальная почта: доставляемость и вход в SMTP провайдера;
- cloud-init, OpenTofu и поведение настоящей ВМ (диск, сеть, перезагрузка).

Эти места проверяет `bootstrap-pilot` с `action: check` и первый боевой выкат.

| 5 | Публикация любой собранной моделью системы после ввода реквизитов оператора ПДн падает на G1 (G1-AC-COVER) | сценарии QA жили только в памяти сборки, перезапуск G1 при публикации их не видел | таблица `platform.g1_checks` (миграция `0019`): сценарии прошедшего G1 сохраняются и наследуются по AC (id + sha256 текста) |
| 6 | Клиент не может сам опубликовать систему с интеграциями (ЮKassa, Telegram, почта, QR) | в продукте нет экрана и API для prod-значений секретов, G2-SECRET-02 их требует | **не исправлено** — продуктовая задача; на пилоте значения кладёт основатель (здесь — `local.mjs secrets`) |
| 7 | Каждая публикация откатывается с SMOKE_FAILED | проверка после публикации идёт из worker на адрес системы, kube-proxy переводит его на поды Traefik, а egress-политика worker это не разрешала | egress platform-api и worker к Traefik на порт websecure; тест helm |

Плюс инфраструктурные мелочи, которые проявились только на настоящем кластере: свежий `runsc` требует сайдкары `gvisor-bin/` рядом с бинарником (на ВМ apt ставит их сам, в образе узла репетиции — копируются), политики чарта пускают к S3 только порт 443, а к SMTP — 465/587, Job основателя первые ~30 секунд после чистого выката не достукивается до базы (NetworkPolicy ещё не применены) и повторяет попытку.
