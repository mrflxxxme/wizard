# Замер D67 на сервере пилота

Порог выпуска MVP (`specs/product.yaml#decisions.D67_mvp_readiness`): 10 брифов проходят настоящую сборку на сервере пилота. Не меньше 7 из 10 должны дойти до готовности к публикации, расход моделей — не больше 2 000 ₽. Повторяем только провалившиеся брифы, потом сценарии проходит основатель.

## Как запустить

GitHub → Actions → **eval-pilot** → Run workflow (с V3 у замера своя кнопка, окружение всегда `prod`; поля журнала трат — docs/ops/eval-d76.md «Проба и замер»):

| Поле | Что указать |
|---|---|
| briefs | `all` (все 10) или id через запятую, например `mvp-03,mvp-10`. Короткого `mvp-03` достаточно |
| threshold | `d67` |
| wave, purpose, hypothesis, expect_rub, cap_rub, founder_ok | журнал трат v3 (предрегистрация прогона; cap_rub — жёсткая остановка) |
| confirm | `PROD` |

Замер идёт от одного до нескольких часов: брифы стартуют по очереди, одновременно собираются два. Задание ограничено 5,5 часа. Пока оно идёт, выкат пилота ждёт: у них общая очередь `pilot-prod`.

## Что делает действие

1. Открывает SSH только для адреса раннера, как `diagnose`, и через туннель в кластер создаёт в базе платформы служебную учётку `eval+<прогон>@<домен платформы>` (`tools/eval/server/seed.mjs`). У учётки организация «Замер D67 · <прогон>» на тарифе «пилот», кредиты (в полтора раза больше бюджета, но не меньше 15 сборок) и сессия. Ревью основателя перед публикацией включено. Сессию раннер генерирует сам: в базу попадают только sha256 токена и CSRF, сам токен скрыт в логе (`::add-mask::`). После этого SSH закрывается.
2. Прогоняет брифы через публичный адрес платформы так же, как клиент в кабинете (`tools/eval/server/driver.mjs`):
   - **Интервью.** На вопрос с кнопками выбирается рекомендованный вариант, если его нет — первый. На свободный вопрос уходит короткий ответ из поля `free_answer` брифа.
   - **Карточка.** Одобряется.
   - **Сборка.** На вопросы сборки замер отвечает, как клиент, который хочет довести систему до конца: выбирает рекомендованный вариант или «Попробовать ещё раз». Если сборка просит секрет, замер её отменяет: значения секретов он не придумывает.
   - **Исправление.** Если проверки не прошли, замер один раз нажимает «Исправить».
   - **Первая публикация.** Если нужны данные оператора ПДн, замер ставит тестовые («Тестовый оператор замера D67»). Публикация запускает G0–G2 и останавливается на ревью основателя, поэтому в prod ничего не уходит.
3. Закрывает сессию: выходит через API, потом снова открывает доступ и отзывает сессию в базе. Заодно читает точный расход по журналу вызовов моделей (`platform.llm_calls`) и строки «Запросов на развитие», если такая таблица уже есть.
4. Пишет отчёт в итоги запуска (Summary) и в артефакт `d67-eval-prod-<номер запуска>`: файлы `d67-<прогон>.md` и `.json`. Если порог не достигнут, задание завершается с ошибкой «Порог D67 не достигнут».

Системы замера не удаляются. Их первые публикации ждут в /admin → «Ревью»: одобрять их не нужно. Организацию замера видно в /admin → «Пилот». По каждой системе, дошедшей до ревью, основателю приходит алерт «ждёт ревью», как от обычного клиента.

## Как читать отчёт

- **Итог X из 10.** Бриф засчитан, если система готова к публикации: G0, G1 и G2 прошли без блокеров. Бриф сверх возможностей (`mvp-10`, платная подписка) засчитан и в другом случае: если система с заменой не дошла до готовности, но агент честно сказал, чего платформа пока не умеет, и записал запрос в «Запросы на развитие». Пока таблицы «Запросов на развитие» в базе нет, достаточно честного ответа в карточке или чате. Такой бриф отмечен «✅*».
- **Не прошли.** Здесь перечислены проверки с блокерами по уровням G0, G1, G2, а в разделе «По брифам» — причина каждой. Проверка G2-SECRET-02 (секреты интеграций для prod, например токен бота Telegram) — это работа владельца, а не дефект сборки. Она показана строкой «владельцу» и готовность не снимает.
- **Мин.** Время от отправки брифа до конца сборки, включая «Исправить». Вверху отчёта — медиана.
- **₽.** Если база ответила, это точный расход по журналу вызовов моделей. Иначе — оценка по кредитам: 1 кредит ≈ 5 ₽, такие цифры помечены «≈».
- **Пробелы.** Сколько раз агенты сказали «Пока не умеем…» (`payload.gaps` сообщений), и что они предложили взамен.
- **Публикация.** «ждёт ревью основателя» — система прошла G0–G2 и готова. «публикация остановлена проверками» — см. G2. «до публикации не дошла» — не прошли G0 или G1.

Что делать дальше: дефекты из отчёта чинятся в M2-89, затем в поле `briefs` указываются только провалившиеся брифы и замер запускается снова.

## Вручную, без GitHub Actions

Нужны psql к базе платформы и HTTPS до платформы:

```bash
node tools/eval/server/cli.mjs seed --session-file s.json --max-cost-rub 2000 > seed.sql   # s.json — 0600, в нём токен
psql "$PLATFORM_DB" -X -q -A -t -v ON_ERROR_STOP=1 -1 -f seed.sql > seed.out
node tools/eval/server/cli.mjs run --base https://borntobuild.ru --session-file s.json --seed-output seed.out --out results.json
node tools/eval/server/cli.mjs collect --seed-output seed.out > collect.sql && psql "$PLATFORM_DB" … -f collect.sql > collect.out
node tools/eval/server/cli.mjs report --results results.json --collect collect.out --out report.md
node tools/eval/server/cli.mjs cleanup --session-file s.json --base https://borntobuild.ru > revoke.sql && psql … -f revoke.sql
rm s.json
```

## Что ещё не сведено

- Лимит D70 (5 сборок и 20 правок за 30 дней на организацию) пока не реализован. Учётку замера не ограничивают кредиты и тариф «пилот». Когда лимит и кнопка «поднять лимит» в /admin появятся, `seedSql` должен поднимать лимит учётки замера до 15 сборок тем же механизмом.
- Таблица «Запросов на развитие» (M2-59) ищется по именам `platform.development_requests`, `platform.capability_gaps`, `platform.gaps`. Когда её имя станет известно, лишние имена нужно убрать.
