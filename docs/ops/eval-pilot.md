# Замер v3 на сервере пилота: проба маршрутов и чекпоинт 1

Задача V3-18 (`specs/backlog.yaml`), решение D77_v3 (8)–(11), (16), (18б), план `docs/plans/2026-10-08-v3.md` §4–5.
Чекпоинт 1 волны A — 4 брифа классов 1–3 на сервере пилота через настоящий путь v3, как его проходит владелец.
По каждому брифу замеряется сборка, сценарии, техревью, время и ₽, делаются снимки 390 и 1280 px.

Порядок — по лестнице бережливого харнесса (`specs/agents/builder-v3.md` §4). Следующая ступень запускается, только когда предыдущая зелёная:

| Ступень | Что | Цена |
|---|---|---|
| 0 | CI: драйвер v3 сквозной на локальной платформе на записанных ответах, проба на подменённых ответах | 0 ₽ |
| 2 | `v3-probe`: по одному минимальному живому вызову на голову каждого маршрута v3 | ≤ 30 ₽ |
| 4 | `eval-pilot`, порог `v3`: 4 брифа чекпоинта 1 | ≈ 1 100 ₽, потолок 1 300 ₽ |

Каждый платный прогон начинается только с записью в журнале трат (`docs/progress/v3-spend.json`, V3-01): цель, гипотеза, ожидаемые ₽, потолок, волна.
На потолке прогон останавливается. Больше 1 000 ₽ за раз или выход за план волны — только с «да» основателя (`founder_ok=yes`).

## Ступень 0 — бесплатно, в CI

Эти проверки идут в каждом PR (`pnpm test`):

- `tools/eval/test/v3-driver.test.ts` — драйвер проходит бриф `v3-02` на локальной платформе с настройками пилота. Клиенты на modules, организации замеров на v3. Путь: грилл-интервью (вариант по основе из брифа, «Решите за меня», свой текст) → направления и «Решите за меня» → «Собрать» → сборка харнессом v3 по снимкам хода → G0–G2 → первая публикация до ревью основателя → collect с v3-строками → отчёт чекпоинта. Ответы моделей записаны. Сеть и деньги не нужны, нужен psql.
- `tools/eval/test/v3-pieces.test.mjs` — ответы интервью, покрытие ожиданий, ход сборки, готовность и цифры отчёта. Ещё два случая: организация не на v3 (замер останавливается сразу) и отказ ТЗ или направлений (сборка всё равно идёт).
- `tools/eval/test/v3-probe.test.ts` — головы маршрутов и цены совпадают с реестром `@wizard/llm`, проба проходит через настоящий роутер на подменённых ответах, на потолке останавливается. Для пробы формы: промпты и инструменты равны коду `@wizard/agents`, снимки — размерам плана снимков критика, прямой вызов шлёт то же тело, что шлюз. Провайдер, отклоняющий несколько картинок, и модель, отвечающая текстом вместо инструмента, разбираются на подменённых ответах.
- `tools/deploy/test/pilot.test.mjs` (V3-18) — `pilot.mjs eval --threshold v3` и `pilot.mjs v3-probe`. Скрипт пробы запускается так же, как в поде: `node --import tsx --input-type=module -` в папке воркера.
- `apps/platform-api/test/v3-org-pipeline.test.ts` — переключатель v3 по организациям.

Посмотреть отчёт сухого прогона: `WIZARD_V3_DRY_OUT=/tmp/v3dry pnpm exec vitest run tools/eval/test/v3-driver.test.ts`. Отчёт появится в `/tmp/v3dry/v3-a-checkpoint1-<дата>.md`.

## Подготовка сервера: v3 только для организаций замера

Клиенты пилота остаются на `WIZARD_BUILD_PIPELINE` (modules), пока чекпоинт не принят. На v3 начинают новые системы организаций из `WIZARD_BUILD_PIPELINE_ORGS` (`specs/platform/deploy.yaml`).

1. Выкатите релиз: **deploy-pilot** (`sha` — текущий main, `confirm` — PROD), в поле `pipeline_orgs` укажите:
   - `eval` — организации замеров и проб;
   - `eval,staff` — то же плюс организации основателя (для V3-19);
   - вместо вида можно указать uuid конкретной организации.

   Пустое поле берёт переменную репозитория `WIZARD_BUILD_PIPELINE_ORGS` (Settings → Secrets and variables → Actions → Variables). Опечатку выкат отклоняет. Значение действует до следующего выката: выкат без поля и без переменной возвращает всех на `WIZARD_BUILD_PIPELINE`.
2. `eval-pilot` с порогом `v3` проверяет переменную сам, до траты. Если в окружении воркера нет `eval`, замер останавливается с ошибкой «организации замера не на v3» и ничего не тратит.

Система остаётся на конвейере, с которого начала. Если убрать вид из переменной, уже начатые системы не переедут.

Режим показа (B2-02) проигрывает записанные сценарии конвейера модулей. Если основатель им пользуется, вместо вида `staff` укажите uuid его рабочей организации.

## Ступень 2 — проба маршрутов v3 (≤ 30 ₽)

Workflow **v3-probe** (Actions → v3-probe → Run workflow):

| Поле | Значение |
|---|---|
| `sha` | пусто (последний main) |
| `wave` | `A` |
| `purpose` | `Головы маршрутов v3 отвечают на сервере пилота` |
| `hypothesis` | `8 из 8 типов вызовов отвечают головой маршрута или резервом; ≈ 3 ₽` |
| `expect_rub` | `5` |
| `cap_rub` | `30` (больше 30 форма не примет) |
| `confirm` | `PROD` |

Что делает проба (`tools/deploy/pilot.mjs v3-probe`, `tools/eval/server/probe.mjs`):

1. Создаёт служебную организацию «Замер V3 · <runid>» вида eval. Её сессия сразу отзывается.
2. В поде воркера через stdin запускает скрипт `kubectl exec -i deploy/wizard-worker -- node --import tsx --input-type=module -`. Файлы релиза для этого не нужны.
3. Скрипт создаёт роутер `@wizard/llm` с ключами, реестром и политикой сервера. Вызовы идут в режиме live, расход пишется в `platform.llm_calls` этой организации и входит в бюджет v3.
4. На каждый тип вызова уходит по одному вызову: «Ответь одним словом». У `critic_visual` к вызову приложена картинка 8×8. `research` вызывается, только если на сервере `WIZARD_RESEARCH_MODE=live`.
5. Когда расход дошёл до потолка, следующие вызовы не начинаются.

По каждому вызову отчёт показывает:

- статус;
- голову маршрута по реестру и модель, которая на самом деле ответила;
- уровень (T0/T1) и причину маршрута;
- маскирование ПДн (scrub);
- задержку и ₽;
- попытки цепочки.

Точный расход читается из базы.

Ожидаемый расход по ценам голов (300 токенов на вход и 150 на выход; у моделей Z.ai — 1 000 на выход с размышлением):

| Тип вызова | Голова | ≈ ₽ |
|---|---|---|
| interview_v3, art_direction, page_compose, signature_section | glm-5.3 (T1) | 0,56 каждый |
| brief_extract | gigachat-3.5 (T0) | 0,07 |
| critic_visual (с картинкой → T0) | kimi-k2.6 | 0,16 |
| techreview | deepseek-v4-pro (T0) | 0,16 |
| research | gpt-oss-120b (T0) | 0,01 |
| **Всего** | | **≈ 2,6 ₽** (потолок 30) |

Если на сервере `WIZARD_BUILD_DEFAULT_TIER=T0`, вызовы сборки уйдут на головы T0. Отчёт это покажет в разделе «Ответила не голова маршрута».

### Проба формы запросов (≤ 30 ₽)

Проба маршрутов шлёт крошечный вопрос без инструмента. В сборке запросы другие, и в чекпоинте 1 отказали именно они: `critic_visual` — 0 из 2 попыток за секунды, `techreview` — 2 из 7. Проба формы повторяет запросы сборки на синтетике, по каждой модели цепочки отдельно, и показывает, какая часть запроса не проходит.

Тот же workflow **v3-probe**, в поле `probe_shape` — группы:

| Поле | Значение |
|---|---|
| `probe_shape` | `critic,techreview` (или одна группа: `critic` / `techreview`) |
| `wave` | `A` |
| `purpose` | `Формы запросов critic_visual и techreview на сервере` |
| `hypothesis` | `Видно, какая часть запроса отказывает (картинки, инструмент, размер) и какая форма работает` |
| `expect_rub` | `12` |
| `cap_rub` | `30` |
| `confirm` | `PROD` |

Пустое `probe_shape` — прежняя проба маршрутов, без изменений. Задание с пробой формы длится до 90 минут, сама проба останавливается через 70.

Что идёт в запросах (`tools/eval/server/probe-shape.mjs`):

- **Как в сборке.** Настоящий системный промпт и инструмент из `@wizard/agents`, `toolChoice: required`, лимиты и тайм-аут маршрута.
  - `critic_visual`: текст критики синтетической клиники и шесть JPEG плана снимков (390×844, 384×512, 720×450, 360×2400 и два 390×844, качество 0,6). Модели: kimi-k2.6, qwen3.6-35b.
  - `techreview`: сводка синтетической мастерской из фикстур техревью (≈ 5 000 знаков, размер фикстурной сборки v3). Модели: deepseek-v4-pro, gpt-oss-120b, gigachat-3.5, kimi-k2.6.
  - Для deepseek-v4-pro и gpt-oss-120b всегда ещё два варианта: сводка ×2 и второй ход после отказа проверки (повтор callTool с ошибкой INVALID_ARGS).
- **Варианты разбора.** Они идут только для модели, у которой форма «как в сборке» не годится: ошибка, нет вызова инструмента или аргументы не прошли проверку.
  - `critic_visual`: 1 JPEG без инструмента, 6 JPEG без инструмента, `tool_choice auto` + 6 JPEG, ответ JSON-текстом + 6 JPEG, required + 1 JPEG, required без картинок.
  - `techreview`: `tool_choice auto` и ответ JSON-текстом.
  - Ответ JSON-текстом проверяет, поможет ли `textArgs` из callTool.

Каждый вариант идёт через шлюз сервера, как в сборке. Роутер `@wizard/llm` получает реестр, в котором у маршрута одна проверяемая модель, и свой circuit breaker. Расход пишется в `platform.llm_calls` организации пробы. Аргументы ответа проверяются самим инструментом из `@wizard/agents` (normalize, zod, смысловые проверки). Если пакет в поде не загрузился, проверяются обязательные ключи схемы — отчёт пишет, какой способ сработал.

Если вариант не прошёл шлюз, проба один раз отправляет тот же запрос напрямую провайдеру. Это тело запроса AI SDK, `transformBody`, адрес и ключ из реестра — тот же вызов, что делает `diagnose` (`tools/eval/server/provider-call.mjs`). В отчёт попадают HTTP-статус и текст ответа провайдера до 300 знаков, всё похожее на ключ замаскировано. Содержимое синтетическое, поэтому граница данных не нарушается. `packages/llm` не меняется. Прямой вызов пропускается при тайм-ауте и когда не было ни одной попытки. Его расход тоже пишется в журнал.

Особый случай. При `toolChoice: required` AI SDK 7 отвергает ответ без вызова инструмента (`ToolChoiceViolationError`). До исправления 09.10.2026 шлюз видел это как `NETWORK` и повторял вызов трижды: провайдер ответы выставлял, а в журнале у них было 0 ₽. Теперь шлюз возвращает такой ответ текстом — одна оплаченная попытка в журнале. Дальше решает callTool: повтор с подсказкой или аргументы из JSON в тексте (`textArgs`). Проба показывает такой ответ как «⚠️ без вызова инструмента». `NETWORK` и `EMPTY_RESPONSE` проба по-прежнему учитывает в потолке по оценке и пишет отдельно («вне журнала»): ответ мог быть выставлен и при обрыве связи.

Потолок: вызов не начинается, если расход дошёл до потолка или его верхняя граница (оценка входа плюс `max_tokens` маршрута) потолок превысит.

| Группы | Формы как в сборке проходят | Формы отказывают, варианты разбора отвечают |
|---|---|---|
| `critic,techreview` | ≈ 11,7 ₽ | до ≈ 30 ₽ — потолок срезает последние варианты |
| `critic` | ≈ 3,8 ₽ | до ≈ 16 ₽ |
| `techreview` | ≈ 7,8 ₽ | до ≈ 14 ₽ |

Порядок: сначала формы как в сборке у всех моделей, потом сводка ×2 и второй ход. Затем варианты разбора по ступеням: дешёвые (картинки без инструмента), потом возможные исправления (auto, JSON-текстом), потом дорогие (required + 1 JPEG, без картинок).

Как читать результат. Логи задания и артефакт недоступны через API, поэтому итог — в аннотациях задания. На каждую пару «тип вызова · модель» одна строка `V3 форма · critic_visual · kimi-k2.6` (GitHub показывает не больше 10 аннотаций одного вида на шаг). `notice` — форма как в сборке работает, `warning` — нет. В строке все варианты: `✅ время, ₽`, `⚠️ без вызова инструмента / аргументы не прошли проверку`, `❌ код шлюза [попытки] → напрямую HTTP 400 «текст провайдера»`. Повторный текст провайдера в строке заменён на «то же». Итоговая аннотация `V3 форма` — `notice`, если все формы как в сборке прошли, и `error`, если нет. Отчёт `v3-shape-<дата>-<runid>.md` с таблицами по моделям и `spend-entry.json` — в артефакте `v3-probe-eval-prod-<run>`.

Содержимое запросов лежит в репозитории:

- `tools/eval/server/probe-shape-prompts.json` — промпты и инструменты. Их строит код `@wizard/agents` в `tools/eval/test/probe-shape-fixture.ts`. Тест `tools/eval/test/v3-probe.test.ts` держит файл равным коду; после правки промптов файл обновляет `WIZARD_UPDATE_PROBE_SHAPE=1 pnpm exec vitest run tools/eval/test/v3-probe.test.ts`.
- `tools/eval/server/probe-shape-images.json` — снимки выдуманного сайта. Их делает `node tools/eval/server/probe-shape-images.mjs` (Chromium из `packages/e2e`) тем же уменьшением на canvas, что и критик платформы.

## Ступень 4 — чекпоинт 1 (4 брифа)

Workflow **eval-pilot** (Actions → eval-pilot → Run workflow):

| Поле | Значение |
|---|---|
| `sha` | пусто |
| `briefs` | `all` (4 брифа `v3-*`) или id через запятую |
| `threshold` | `v3` |
| `wave` | `checkpoint` |
| `purpose` | `Чекпоинт 1 волны A: 4 брифа классов 1–3 через путь v3 на сервере` |
| `hypothesis` | `Все 4 системы собираются с превью ≤ 5 мин, сборкой ≤ 30 мин и ≤ 500 ₽, обязательные сценарии проходят, техревью без блокеров` |
| `expect_rub` | `1100` |
| `cap_rub` | `1300` |
| `founder_ok` | `yes` (потолок больше 1 000 ₽ за раз) |
| `confirm` | `PROD` |

Откуда цифры. Цель сборки D77 (11) — ≤ 300 ₽, потолок харнесса — 500 ₽ на сборку. К этому добавляются интервью (≈ 10–20 ₽) и направления (≤ 40 ₽). Итого на бриф ≈ 270–360 ₽, на четыре ≈ 1 100–1 400 ₽.

Приёмка V3-18 — расход ≤ 2 000 ₽ вместе с V3-19 (план «Чекпоинты основателя» — 2 000 ₽). Потолок 1 300 ₽ оставляет ≥ 700 ₽ основателю на 2–3 системы.

Есть вариант без «да» основателя: `cap_rub` = `1000`. Тогда при расходе ≈ 300 ₽ на бриф четвёртый бриф остановит потолок. Его можно догнать отдельным прогоном: `briefs` = `v3-04`, волна `checkpoint`.

Что делает замер (`tools/eval/server/v3.mjs`, параллельно 2 брифа):

1. Проверяет, что организации замера на v3 (см. выше), и создаёт учётку «Замер V3 · <runid>» с ревью основателя.
2. По каждому брифу `POST /systems` создаёт систему и проводит грилл-интервью. Ответы берутся из `answers` брифа:
   - `тема: основа варианта` — первый вариант, где есть эта основа;
   - `delegate` — «Решите за меня»;
   - `{text}` — свой ответ;
   - иначе — рекомендованный вариант.
   После `rest_after` ответов отправляется «Дальше решай сам». Если у брифа есть `tz`, после первого хода прикладывается файл ТЗ.
3. Направления: три первых экрана, выбор `direction` брифа (1–3 или `delegate`). Если направления не получились, сборка всё равно идёт.
4. «Собрать» по последней версии брифа. Сборка отслеживается по снимкам `progress` событий `build_stage`/`step_*`:
   - этапы и их время;
   - живое превью;
   - сценарии;
   - ₽ из потолка.
   Ход по брифам выводится в issue «Замер D67: ход на сервере».
5. G0–G2, затем первая публикация. Она останавливается на ревью основателя, в prod ничего не уходит.
6. Снимки превью на 390 и 1280 px.
7. Из базы читаются:
   - точный ₽ по системам;
   - вызовы моделей по типам и моделям;
   - чекпоинты критика, гейта шаблонности и техревью;
   - сходство с сайтами ниши;
   - события этапов;
   - «Запросы на развитие»;
   - вызовы T1 с запрещёнными для ПДн типами.

Бриф «готов», если сборка завершилась, G0–G2 без блокеров, техревью без блокеров и прошли все обязательные сценарии брифа. Цели D77 (10)–(11) отчёт сверяет отдельно:

- превью ≤ 5 мин;
- медиана ≤ 20 мин, максимум ≤ 30 мин;
- средний расход ≤ 300 ₽, максимум ≤ 500 ₽.

Время замера — около 40–70 минут.

## Отчёт и журнал трат

Артефакт задания `v3-eval-prod-<run>` (у пробы — `v3-probe-eval-prod-<run>`) содержит:

- `v3-a-checkpoint1-<дата>.md` и `.json` — отчёт чекпоинта на русском и данные по брифам. Скопируйте оба в `docs/progress/` (дата — по Москве);
- `shots/*.png` — снимки остаются только в артефакте, в git не попадают;
- `spend-entry.json` — запись для журнала: `node tools/deploy/spend.mjs register --entry spend-entry.json`.

Строка «потрачено X ₽ из плана Y ₽ волны …» есть в отчёте, в сводке задания и в аннотации.

Повтор — только упавших брифов: тот же workflow, `briefs` через запятую (например `v3-03`), волна `retry`. Системы замера не удаляются, первая публикация ждёт ревью основателя в /admin.

## Финальный замер v3 (V3-40, 12 брифов)

Критерии — план v3 (`docs/plans/2026-10-08-v3.md`, §6). Бюджет по плану: финальный замер — 3 600 ₽, повтор упавших брифов — до 1 500 ₽, конкуренты — до 1 000 ₽.

Набор `v3-final` — все брифы `v3-*`, по 3 на класс. Чекпоинт `v3` остаётся прежним: брифы `v3-01`…`v3-05`.

| Класс | Брифы |
|---|---|
| сайт бизнеса | `v3-01-interior-studio`, `v3-04-karelia-tours`, `v3-06-frame-houses` |
| услуги и запись | `v3-02-dental-booking`, `v3-07-auto-service`, `v3-08-vet-clinic` |
| CRM и админка | `v3-03-cleaning-crm` (ТЗ в md), `v3-09-hvac-service-crm`, `v3-10-coffee-wholesale` (ТЗ в txt) |
| магазин | `v3-05-ceramics-shop`, `v3-11-altai-tea-shop`, `v3-12-farm-produce` |

**1. Прогон.** Actions → **eval-pilot**: threshold `v3-final`, briefs `all`, wave `final`, cap_rub `3600`, founder_ok `yes` (потолок больше 1 000 ₽). Сервер готовится так же, как для чекпоинта. В артефакте будут:

- `v3-final-run-<дата>.md` и `.json` — отчёт по брифам и данные прогона;
- `v3-final-<дата>.md` — отчёт по критериям §6. Слепое сравнение в нём пока «ожидает оценщиков»;
- `shots/<бриф>-390.png` и `shots/<бриф>-1440.png` — снимки для слепого сравнения;
- `spend-entry.json` — запись для журнала трат.

**2. Повтор только упавших брифов.** Тот же workflow: threshold `v3-final`, briefs — id через запятую (например `v3-03,v3-08`), wave `retry`. Общий итог по обоим прогонам (более поздний результат брифа заменяет ранний, расход считается по всем попыткам):

```bash
node tools/eval/server/cli.mjs final --results v3-final-run-<дата1>.json,v3-final-run-<дата2>.json \
  [--blind blind-summary.json] [--shots-base v3-final-<дата>] --out docs/progress/v3-final-<дата>.md
```

Разнообразие `final` считает сам — метрикой гейта шаблонности (`packages/gates`, через tsx; нужен `pnpm install`) по отпечаткам сайтов из выгрузки замера.

**3. Сайты конкурента (делает человек).** Те же 12 брифов (поле `text` в `tools/eval/briefs/v3-*.json`) отдайте конкуренту: VibeCraft, Tilda AI, Lovable — кто доступен, сначала на бесплатных квотах. Траты — волна `competitors` журнала трат. По каждому брифу положите в папку `competitor/<бриф>/` (можно короткий id, например `competitor/v3-02/`):

- `390.png` — первый экран на телефоне, окно 390×844;
- `1440.png` — первый экран на компьютере, окно 1440×900;
- `meta.json` — `{"service": "Tilda AI", "url": "https://…"}`.

Снимки сохраняйте в PNG, как у Wizard: по формату файла оценщик может угадать источник.

Снимки может сделать раннер: Actions → **blind-shots**, service — сервис конкурента, urls — публичные адреса сайтов по брифам (`v3-01=https://…;v3-02=https://…`). Артефакт `competitor` уже разложен по папкам `competitor/<бриф>/` с `390.png`, `1440.png` и `meta.json` (`tools/eval/blind/shoot.mjs`). Принимаются только публичные https-адреса; сайт, который не открылся, остаётся без пары и попадает в предупреждения.

**4. Страница для оценщиков.**

```bash
node tools/eval/blind/cli.mjs build --shots <артефакт>/shots --competitor competitor --out blind [--seed v3-40]
```

Оценщикам отправляется папка `blind/` целиком (`index.html` и `img/`). Файл `blind-key.json` рядом с ней — ключ, его не отправлять. На странице 36 пар:

- 12 пар «Wizard — конкурент»;
- 12 пар «Wizard — Wizard» внутри класса;
- 12 пар «конкурент — конкурент» внутри класса.

Порядок пар и стороны A/B задаёт seed. Чей сайт, страница не показывает. Оценщик выбирает лучший сайт в паре или «Одинаково», отмечает «как один шаблон» и скачивает ответы JSON-файлом.

**5. Итог слепого сравнения.** Основатель и 3–5 независимых оценщиков присылают файлы, их кладут в одну папку:

```bash
node tools/eval/blind/cli.mjs aggregate --key blind-key.json --votes votes/ --out blind-summary.json
```

Wizard выигрывает пару, если за его сайт больше голосов, чем за сайт конкурента. Цель — не меньше 70 % пар, оценщиков не меньше четырёх. Жалоб «один шаблон» на два сайта Wizard быть не должно. Затем `final` (шаг 2) с `--blind blind-summary.json`. Отчёт и снимки (`docs/progress/v3-final-<дата>/`) — в `docs/progress/`.

## Паспорта API на тестовых контурах (V3-22)

Проверка бесплатная: модели не вызываются, серверы пилота не участвуют. Запуск: Actions → **integrations-sandbox** → Run workflow.

| Поле | Значение |
|---|---|
| `passports` | `all` — СДЭК и ЮKassa; можно выбрать `cdek` или `yookassa` |
| `cdek_order` | галочка: создать тестовый заказ в учебном контуре СДЭК, прочитать, найти по номеру и удалить. Заказы там не исполняются |

Путь тот же, что у проверки ключа на платформе: контракт из паспорта, ключ в памяти как `secret://…`, egress-клиент рантайма. Токен СДЭК рантайм получает сам. Потом идут безопасные операции, и каждый ответ сверяется со схемой паспорта.

- **СДЭК** (`api.edu.cdek.ru`): токен OAuth, `listCities` (проверка ключа), `calculateTariff`, `calculateTariffList`, `listDeliveryPoints`, `listWebhooks`. С `cdek_order` — ещё `createOrder` → `getOrder` → `findOrder` → `deleteOrder`.
- **ЮKassa** (тестовый магазин, тот же `api.yookassa.ru`): `getShop` — проверка ключа; дальше только если магазин тестовый. Затем платёж на 1 ₽ без списания (`capture: false`) с `Idempotence-Key` и его повтор, `getPayment`, `listPayments`. Отмена — только если платёж ждёт подтверждения.

Результат — одна строка-аннотация на операцию и таблица в сводке шага:

- `notice` — ответ совпал с паспортом;
- `warning` — шаг пропущен или сеть сбоила;
- `error` — расхождение или сбой.

Расхождение называет операцию, указатель JSON, что ждёт паспорт и что пришло. Ключи, токены и заголовки `Authorization` в вывод не попадают.

Сбой соединения повторяется до 4 раз. Если хост недоступен, строка называет этап: DNS, TCP или TLS. Тогда проверку запускают с сервера пилота в РФ.

Секреты репозитория (Settings → Secrets and variables → Actions), все необязательные:

| Секрет | Что это |
|---|---|
| `YOOKASSA_TEST_SHOP_ID` | shopId тестового магазина ЮKassa: личный кабинет → тестовый магазин → Интеграция → Ключи API |
| `YOOKASSA_TEST_SECRET_KEY` | секретный ключ того же магазина, начинается с `test_`; боевой ключ проверка не принимает |
| `CDEK_TEST_ACCOUNT`, `CDEK_TEST_SECURE` | свои тестовые Account и Secure password СДЭК; без них — общая тестовая учётная запись из документации СДЭК |

Без ключей ЮKassa шаг выдаёт предупреждение и ничего не отправляет.

Запуск без GitHub — из сети, где хосты доступны. Если задан `HTTPS_PROXY`, запросы идут через него; `--direct` отключает прокси:

```bash
node tools/integrations/sandbox-check.mjs --passports=all [--cdek-order] [--direct]
```
