# Замер беты v2 (порог D76) на сервере пилота

Порог готовности беты v2 (`specs/product.yaml#decisions.D76_beta_v2`, `specs/quality/eval.yaml#thresholds.by_milestone.B2`) строгий. Каждый бриф, который покрыт модулями, должен дойти до готовой системы. Бриф вне модулей должен дойти до рабочей системы, а всё, что в неё не вошло, должно попасть в «Запросы на развитие». Сначала идёт проба на 2–3 брифах, потом полный замер на 10 брифах `mvp-01…10`. Всё это укладывается в бюджет разработки беты v2: не больше 1 000 ₽ (`WIZARD_B2_BUDGET_RUB`).

## Перед замером: выкат с конвейером модулей

GitHub → Actions → **deploy-pilot** → Run workflow:

| Поле | Что указать |
|---|---|
| Окружение | `prod` |
| sha | полный SHA коммита main |
| confirm | `PROD` |
| llm_daily_cap_rub | пусто: с V3 лимит по умолчанию 3 000 ₽ в день (D77 (18б)) |
| build_pipeline | `modules`: новые системы собираются по плану из модулей. Старые системы остаются на своём конвейере |
| stock_mode | `library`: фото из библиотеки платформы, её пополняет раннер выката (B2-43, стоки с сервера в РФ закрыты). `live`: стоки Pexels и Pixabay с сервера (ключи в секретах GitHub). `off`: графика темы вместо фото |

Выкат также задаёт:

- `WIZARD_G1_BROWSER=chromium`. Сценарии целей в G1 проверяются в Chromium воркера. Образ `wizard-worker` собирается с `CHROMIUM=1` (`infra/docker/images.json`), лимит памяти воркера на пилоте — 2Gi (`infra/helm/profiles/pilot.yaml`).
- `WIZARD_MAIL_DOMAIN`. Это почтовый домен пилота, то есть домен из `WIZARD_SMTP_FROM`: он уже подтверждён у Unisender, у домена систем SPF `-all`. Другой домен можно задать переменной репозитория `WIZARD_MAIL_DOMAIN`.

Вернуть прежний конвейер можно выкатом с `build_pipeline=legacy`, менять код не нужно. Те же значения можно задать переменными репозитория `WIZARD_BUILD_PIPELINE`, `WIZARD_G1_BROWSER`, `WIZARD_G1_BROWSER_SLOTS`, `WIZARD_STOCK_MODE`. Поле формы важнее переменной.

### Фото со стоков (B2-38)

Ключи лежат в секретах репозитория `PEXELS_API_KEY` и `PIXABAY_API_KEY`. Значения ключей нигде не печатаются: выкат регистрирует их в маске GitHub до любого вывода, в итогах только вердикт и код HTTP.

1. **Проверка без выката.** Actions → **bootstrap-pilot**, action `check`. В сводке две необязательные строки «Фото: ключ Pexels» и «Фото: ключ Pixabay»: «действителен», «недействителен», «нет ключа» или «не проверен» и код HTTP. Проверка делает один поисковый запрос к каждому стоку (Pexels — `GET /v1/search?query=coffee&per_page=1` с ключом в заголовке `Authorization`, Pixabay — `GET /api/?q=coffee&per_page=3` с ключом в параметре; адрес с ключом не печатается). Недействительный ключ — ошибка с пометкой «необязательно», `check` из-за неё не падает.
2. **Выкат с фото.** deploy-pilot с `stock_mode=live`. Перед записью секретов кластера выкат так же проверяет оба ключа, итог — в разделе «Пилот prod: фото со стоков» сводки задания:
   - действителен (или 429 — лимит запросов, ключ узнан) — ключ уходит в Secret `wizard-platform-env` как `WIZARD_STOCK_PEXELS_KEY` / `WIZARD_STOCK_PIXABAY_KEY`;
   - недействителен (Pexels 401/403, Pixabay 400/401/403) или нет ключа — этот сток выключен в данном выкате, в журнале предупреждение, выкат продолжается. Если не работает ни один ключ — сайты систем показывают графику темы;
   - не проверен (нет ответа, 5xx) — ключ передаётся без проверки, в журнале предупреждение.
3. С `stock_mode=off` ключи в платформу не передаются и не проверяются при выкате, фото не подбираются.
4. **Библиотека фото (B2-43), `stock_mode=library`.** С сервера пилота стоки недоступны (Pexels отвечает 404, Pixabay обрывает соединение), с раннеров GitHub работают. Платформа получает `WIZARD_STOCK_MODE=library` и ни одного ключа: сборка берёт фото из индекса библиотеки в бакете files (`wz_photos/`), сначала по точному запросу этапа фото, затем по нише, затем общие. Пополняет библиотеку задание `stock-library` того же выката (после успешного выката, на раннере): `node tools/deploy/stock-library.mjs seed` подбирает фото по запросам ниш каталога и брифов mvp, Pexels, затем Pixabay, копирует их в бакет (WebP, без EXIF) и дописывает индекс с автором и лицензией. За запуск — не больше 400 запросов и 20 минут, полные запросы пропускаются, поэтому каждый следующий выкат продолжает с того места, где остановился предыдущий. Нужен ключ S3-аккаунта (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`) — тот же, что получают поды. Сбой задания — предупреждение, выкат не падает. В журнале только числа.

platform-api и воркер берут ключ сначала из этих переменных, затем из хранилища секретов платформы (`secret://platform/stock/pexels|pixabay`, для ключа, добавленного вручную). В хранилище выкат ничего не пишет: новый ключ в GitHub приходит со следующим выкатом, удалённый — исчезает. Запросы к стокам платформа делает только в режиме `live` (и `record`) и только к хостам `api.pexels.com`, `images.pexels.com`, `pixabay.com`, `cdn.pixabay.com` (`STOCK_EGRESS_HOSTS` в `tools/deploy/pilot-secrets.mjs`, проверка в `apps/platform-api/src/agents/stock.ts`). Сетевые правила кластера не меняются: platform-api и воркер выходят в интернет по 443 так же, как к провайдерам моделей.

### Стоки из CI

Ключи стоков можно проверить и опробовать без сервера пилота: GitHub → Actions → **stock** → Run workflow (через API — `POST /repos/{owner}/{repo}/actions/workflows/stock.yml/dispatches` с `{"ref":"main","inputs":{"action":"probe"}}`). Сервер не затрагивается, поэтому подтверждение `PROD` не нужно. Запуски идут по одному (`concurrency: stock`). Код — `tools/deploy/stock-ci.mjs`.

| action | Что делает | Где итог | Права задания |
|---|---|---|---|
| `check` (по умолчанию) | По одному бесплатному поиску к каждому стоку, та же проверка, что в `bootstrap-pilot check` (`stockKeyVerdict`) | Аннотация «Фото со стоков»: «Pexels — действителен (HTTP 200); Pixabay — …». Задание красное, если ключа нет или он недействителен | `contents: read` |
| `probe` | Этап фото сборщика v2 (`runPhotosStage`) с настоящими ключами на 3–5 брифах mvp. Планы и ответы дизайна записаны в B2-37 (`packages/agents/test/design-mvp-scenarios.ts`), модели не вызываются, файлы не сохраняются (копии в памяти). Лимит на всю пробу: не больше 20 поисков и 10 скачиваний, они делятся между брифами. Порядок стоков чередуется по брифам, чтобы скачать с обоих | Аннотация «Стоки: проба этапа фото» и тот же текст комментарием в issue «Стоки: проверка из CI» (issue создаётся один раз, дальше комментарии) | `contents: read`, `issues: write` |
| `record` | Записывает ответы поиска Pexels для словаря запросов фикстур (`QUERIES` в `tools/fixtures/stock/gen.mjs`, не больше 20 поисков по 15 фото) в `tools/fixtures/stock/pexels.recorded.json`, гоняет тесты фикстур и открывает PR из ветки `stock-record/<номер запуска>` в main | Аннотация «Стоки: запись фикстур»: сколько записано, затем «PR #N из stock-record/… в main» или «без изменений» | `contents: write`, `pull-requests: write` |

Поле `briefs` нужно только для `probe`: 3–5 брифов mvp через запятую. Пусто — `mvp-01`, `02`, `03`, `04`, `10`, это брифы, в планах которых есть места для фото (всего 16 мест).

Итог пробы — только числа. Ключей, адресов, авторов и ссылок на фото в нём нет. Пример:

```
Проба этапа фото: стоки работают
Ключи: Pexels — есть, Pixabay — есть
Pexels: поисков 6, найдено 144, скачано 5 (0.5 МБ) — работает
Pixabay: поисков 4, найдено 96, скачано 5 (0.6 МБ) — работает
mvp-02-renovation · ремонт квартир под ключ: мест 7, выбрано 4 (pixabay 4), без фото 3 — лимит пробы; поисков 3, найдено 72; 0.6 с
…
Итого: выбрано 10 из 16 мест; поисков 10 из 20, скачиваний 10 из 10; 1.3 с
```

Уровень аннотации: `notice` — оба стока искали и скачивали без ошибок; `warning` — фото есть, но у одного стока ошибки (например «не работает: HTTP 401 ×4») или нет его ключа; `error` — ни одного фото или ключей нет (тогда запросов к стокам нет вовсе, задание красное). «Без фото N — лимит пробы» — это не сбой: в пробе не больше 10 скачиваний на все брифы.

Ключи передаются только в `env` шага, который их использует. Первой строкой этот шаг регистрирует их в маске GitHub (`::add-mask::`). Установка зависимостей ключей не видит. Шаг `record` получает только ключ Pexels.

**Почему записывается только Pexels.** Правила API Pixabay требуют кешировать ответы 24 часа и запрещают постоянный хотлинк. Хранить их ответы в репозитории бессрочно значит выйти за эти условия. Поэтому ответы Pixabay в фикстурах остаются синтетическими (`pixabay.json` от `gen.mjs`), а `record` и режим платформы `WIZARD_STOCK_MODE=record` пишут только Pexels (`RECORDED_PROVIDERS` в `packages/agents/src/stock/fixtures.ts`). Для Pexels сохраняются только метаданные, которые читает клиент: id, размеры, автор и ссылка на него, страница фото, адреса файлов. Картинок, следующих страниц, цветов и alt-текстов там нет, ключи вычищены (`sanitizeStockAnswer`). В адрес файла добавлен параметр `wz=<ш>x<в>` в пропорциях фото: по нему режим фикстур рисует картинку, а не скачивает её. Записанные ответы лежат отдельным файлом и перекрывают синтетические ответы на тот же запрос. `gen.mjs` этот файл не трогает.

**PR от record.** PR открывается токеном задания, поэтому `ci` на нём сам не запускается (ограничение GitHub для `GITHUB_TOKEN`). Чтобы прошёл `ci`, закройте и снова откройте PR или добавьте в него коммит. Если в настройках репозитория Actions не разрешено создавать pull request (Settings → Actions → General → «Allow GitHub Actions to create and approve pull requests»), ветка всё равно отправляется, а аннотация-ошибка называет её. PR из неё можно открыть вручную или через API. `record` запускается только из main.

## Проба и замер

GitHub → Actions → **bootstrap-pilot** → Run workflow, action `eval`:

| Поле | Проба | Замер |
|---|---|---|
| Окружение | `prod` | `prod` |
| action | `eval` | `eval` |
| briefs | 2–3 брифа, например `mvp-01,mvp-04,mvp-07` | `all` |
| cap_rub (с V3, вместо max_cost_rub) | `50` | `300` |
| threshold | `d76` | `d76` |
| confirm | `PROD` | `PROD` |

Отличие пробы: проба проходит все свои брифы, чтобы показать, что с каждым. Полный замер (10 брифов) останавливается на первом незасчитанном брифе: дальше порог уже не взять, и деньги не тратятся.

## Что делает действие

Порядок тот же, что у D67 (`docs/ops/eval-d67.md`):

1. Создаёт в базе служебную учётку `eval+<прогон>@<домен>` с организацией «Замер D76 · <прогон>» (`orgs.kind = eval`). Её расход идёт в бюджет разработки беты v2, а не в клиентский.
2. Проводит каждый бриф как клиент: интервью по целям, затем **план утверждается как есть** (`POST /systems/:id/plan/approve`), затем сборка v2. Если ход интервью или плана упал со сбоем, который можно повторить, драйвер один раз повторяет этот ход, как кнопка «Повторить» у клиента: заново отвечает на открытые вопросы или отправляет последний текст. Если проверки не прошли, один раз нажимается «Исправить». Затем первая публикация с G0–G2 до ревью основателя.
3. Снимает каждую систему через ссылку превью на 390 и 1280 px (папка `shots/` рядом с отчётом).
4. Читает точный расход по журналу вызовов моделей, «Запросы на развитие», расход бюджета разработки беты v2 с `WIZARD_B2_BUDGET_SINCE` и ответы моделей интервью и плана, которые не прошли проверку (события `orch_invalid`: ход, чем заменили, путь и код ошибки, без персональных данных). Закрывает сессию.

Бриф засчитан, когда выполнены все условия:

- G0–G2 без блокеров;
- в G1 сборки прошли все `G1-GOAL-*` и `G1-MOBILE-01`;
- план покрыт модулями, либо всё из «не входит» записано в «Запросы на развитие». При утверждении плана платформа сама пишет туда пункты «не входит».

## Где смотреть

- **Ход замера.** Issue «Замер D67: ход на сервере», по комментарию на запуск, обновляется раз в минуту.
- **Отчёт.** Итоги запуска (Summary) и артефакт `d76-eval-prod-<номер запуска>`. В артефакте `d76-<прогон>.md`, `d76-<прогон>.json` и `shots/*.png`. В отчёте есть вердикт, строки по брифам, экономика (средняя сборка ≤ 15 ₽ и ≤ 5 мин, дописывание ≤ +20 ₽), расход бюджета разработки беты v2 и сетка скриншотов.
- **Расход по дням.** /admin → «Пилот» (расход по назначениям и бюджет B2) и страница «Бета v2».
- **Итог на странице «Бета v2».** Координатор кладёт `d76-<прогон>.json` в `docs/progress/b2-final.json`, а снимки — в `docs/progress/b2-final/shots/`. После этого `node tools/progress/b2.mjs --html …` показывает блок «Финальный замер»: вердикт, по каждому брифу «готова / нет», ₽, минуты и снимок 390 px.

## Как остановить

- **Отменить задание.** Actions → запуск → Cancel. Идущие прогоны отменяются, отчёт пишется по тому, что есть.
- **Бюджет замера.** С V3 — `cap_rub` с обязательной предрегистрацией (`purpose`, `hypothesis`, `expect_rub`, `wave`; выше 1 000 ₽ — `founder_ok=yes`; журнал `docs/progress/v3-spend.json`, `tools/deploy/spend.mjs`). `cap_rub` — жёсткая остановка: когда оценка расхода по кредитам его превысит, идущий бриф отменяется, остальные не стартуют.
- **Защиты платформы.** Дневной лимит для служебных организаций `WIZARD_LLM_EVAL_DAILY_CAP_RUB` (300 ₽) и бюджет беты v2 `WIZARD_B2_BUDGET_RUB`. При 70 % основателю уходит алерт, при 100 % новые пробы и замеры отклоняются (`LLM_BUDGET_EXHAUSTED`), и замер останавливается.

## Сухой прогон (без сети и денег)

```bash
pnpm db:up
pnpm --filter @wizard/e2e exec tsx stand/d76-dry.ts [--scenarios barber,dental,dental_custom,repair] [--out .data/d76-dry]
```

Поднимает локальный стенд с настройками пилота: `modules`, G1 в Chromium, правила M2, ревью основателя. Учётку создаёт тем же `seedSql` через psql. Дальше идёт тот же драйвер с `threshold d76`, скриншоты, `collectSql` и отчёт. Модели отвечают по записям `tools/fixtures/demo/b2/*.jsonl`. У брифов mvp полных записей нет (есть только этап дизайна), поэтому сухой прогон идёт на четырёх записанных сценариях. Код выхода 0 означает, что порог пройден.
