### Как передавать секреты (для всех пунктов)

- **Никогда** не присылайте ключи, токены и пароли в чат с агентом, в почту, в issue или PR. Не коммитьте их и не кладите в `.env.example`.
- Ключи для CI вводите сами: GitHub → Settings → Secrets and variables → Actions. Значение там только для записи: ни агенты, ни вы его потом не прочитаете.
- Ключи для серверов staging и prod по `deploy.yaml#cloud.secrets` живут в OpenBao в кластере Cloud.ru (staging и prod раздельно). Пока OpenBao не развёрнут (M2-06), их держат в `.env` на сервере (права 600) или вводят прямо в OpenBao после развёртывания. Передавать их можно через менеджер паролей с общим хранилищем (например, Passwork — российский) или файл KeePassXC, но не открытым текстом.
- У каждого ключа задайте срок жизни (Cloud.ru: рекомендовано 90 дней) и запишите, где он используется. При утечке — отзыв и перевыпуск.
- Логины от личных кабинетов (Cloud.ru, регистратор, ЮKassa, Z.ai, GitHub) оставьте у себя, включите 2FA. Команде нужны **сервисные** ключи, не ваш пароль.

## 2. Домены и TLS

**Что это.**
- **Домен систем** — нейтральный, регистрируемый отдельно, не поддомен платформы и не связан с будущим брендом (F8, D9). На нём живут `<slug>.<домен>` и `<slug>--draft.<домен>`. Покупка — **сейчас** (неделя 0).
- **Домен платформы** — `<имя>.ru`, вместе с финальным именем к неделе 12 (E-NAME).
- В `deploy.yaml` есть отдельный `<systems-domain-staging>` для системы на staging.

**Зачем.** M2-06: wildcard TLS, HSTS preload, заявка в Public Suffix List. Почта (SPF, DKIM, DMARC). Магазин ЮKassa: в заявке указывается сайт с HTTPS (раздел 4).

### Как получить

1. **Выберите имя** домена систем: короткое, нейтральное, не похожее на бренды и на название платформы (`docs/week0/naming-check.md` — для платформы; для домена систем подойдёт любое нейтральное).
2. **Регистратор в РФ.** Подойдут [REG.RU](https://www.reg.ru), [RU-CENTER](https://www.nic.ru/catalog/domains/ru/), Beget и другие аккредитованные. Зона — **.ru**: у .рф punycode и проблемы с некоторыми почтовыми клиентами.
   - Администратор домена — **ваше юрлицо**, не физлицо. Регистратор попросит подтвердить данные.
   - **Оплатите сразу на 3+ года.** Правила PSL требуют, чтобы на момент заявки до окончания регистрации оставалось больше 2 лет, и регистрацию нужно продлевать заранее ([PSL Guidelines](https://github.com/publicsuffix/list/wiki/Guidelines)).
   - Включите 2FA и автопродление.
3. **Делегирование в Cloud.ru DNS**, если DNS держим в облаке:
   - Консоль → «Сеть» → «DNS» → «Прямые зоны» → создать **публичную** зону.
   - В свойствах зоны «сгенерировать и скопировать код подтверждения» и добавить его TXT-записью у регистратора.
   - Дождаться статуса «Подтверждена» (до 48 ч), затем прописать у регистратора NS-серверы из карточки зоны ([инструкция](https://cloud.ru/docs/evolution-dns/ug/topics/guides__confirm-zone)).
4. **Домен платформы.** Купите кандидатов заранее, они недорогие. Платёжная форма ЮKassa должна жить на сайте платформы, а заявка подаётся к неделе 8, раньше выбора имени (раздел 4).

### TLS (wildcard)

Wildcard-сертификат Let's Encrypt выдаётся только через DNS-01. Сам сертификат бесплатный. Варианты для `cert-manager`:

| Вариант | Плюсы | Минусы |
|---|---|---|
| a) DNS в Cloud.ru, свой webhook cert-manager к API Evolution DNS | всё в одном облаке и в IaC | готового webhook для Cloud.ru не нашёл: ≈ 1 день работы команды [оценка] |
| b) DNS в Cloud.ru, делегировать `_acme-challenge` через CNAME на self-hosted acme-dns (MIT) | не зависит от API DNS | ещё один сервис в кластере |
| c) DNS у REG.RU, готовый [cert-manager-webhook-regru](https://github.com/daloman/cert-manager-webhook-regru) (Apache-2.0) | работает «из коробки» | API REG.RU пускает только с разрешённых IP; логин и пароль API хранятся в кластере |
| d) [Certificate Manager Cloud.ru](https://cloud.ru/docs/certificate-manager/ug/topics/quickstart) (Let's Encrypt, домен в Evolution DNS) | управляемый сервис | поддержка wildcard и выдача сертификата в ingress K8s — [не проверено] |

Рекомендация: **a или b** — DNS в Cloud.ru, ключи остаются в контуре (`deploy.yaml#tls`: «ключи не покидают кластер»).

### Сколько стоит

## 5. Telegram-бот уведомлений платформы

**Что это.** Общий бот, который шлёт уведомления систем пользователям: «<Система>: Заявка №123» + ссылка, без ПДн (`connectors/telegram.yaml#bots.platform`). Им же идут алерты модерации основателю (F7).

Нужны **два бота**: боевой (prod) и тестовый (staging и e2e).

**Важно про вход.**
- По спекам **общий бот не используется для входа**: у него нет client_id системы. Вход на платформу — по почте.
- Вход через Telegram в системах делает **свой бот клиента** через OIDC. Его настраивает клиент: в мини-приложении BotFather → Bot Settings → Web Login → OpenID Connect Login → Redirect URL, затем Client ID и Client Secret.
- Поэтому `/setdomain` и виджет входа для бота платформы **не нужны**. Если хотите вход через Telegram на саму платформу — это новое решение (E-DECISION) и новая задача.

**Зачем.** M1-06 в live (уведомления по умолчанию), алерты модерации (D21, M2-08, M2-09).

### Как получить (бесплатно)

1. В Telegram откройте **@BotFather**: проверьте синюю галочку.
2. `/newbot` → отображаемое имя (временное до E-NAME, например «Уведомления систем») → username из 5–32 символов на `bot`, нейтральный. Его можно сменить позже, но старые ссылки `t.me/...` перестанут работать [не проверено].
3. Скопируйте **токен** вида `123456:ABC...`.
4. Настройте бота:
   - `/setjoingroups` → Disable;
   - `/setprivacy` → Enable;
   - `/setdescription` и `/setabouttext` — «Этот бот присылает уведомления систем, которые вы подключили»;
   - `/setuserpic` — по желанию.
5. Повторите для тестового бота (например, `…_staging_bot`).
6. Для алертов F7 откройте боевого бота со своего аккаунта и нажмите «Старт».
7. Если токен утёк: BotFather → `/revoke` → новый токен ([документация](https://core.telegram.org/bots/features#botfather)).

### Как передать

| Имя | Кто задаёт | Куда |
|---|---|---|
| `WIZARD_TELEGRAM_BOT_TOKEN` | вы (BotFather) | OpenBao prod (боевой) и staging (тестовый); локально — `.env` |
| `WIZARD_TELEGRAM_BOT_USERNAME` | вы (без @) | конфиг, не секрет |
| `WIZARD_TELEGRAM_WEBHOOK_SECRET` | **команда** генерирует сама: случайная строка, символы `A–Z a–z 0–9 _ -` | OpenBao |

Вебхук `/_wizard/hooks/telegram/_platform/<hookToken>` настраивает команда при деплое.

**⚑ Решения:** username ботов. Финальное имя — вместе с E-NAME.

## 6. SMTP для почты платформы (OTP, приглашения, уведомления систем)

**Что это.** Почтовый аккаунт для транзакционных писем. Провайдер должен быть в РФ: он субобработчик с ПДн (`compliance.yaml#subprocessors`).

По `escalation.yaml#calendar` SPF, DKIM и DMARC настраиваются на **домене систем**: домен платформы появится только к неделе 12.

**Зачем.** M1-06 в live, вход по почте в live (сейчас письма пишутся в `.data/outbox`).

### Варианты

| Провайдер | Подходит? | Цена (01.10.2026) |
|---|---|---|
| **[Unisender Go](https://go.unisender.ru/)** — рекомендую | да: транзакционный, SMTP и API, серверы в РФ, 152-ФЗ, оплата по счёту | по карте от **800 ₽/мес за 6 000 писем** (сверх — 150 ₽ за 1 000); по счёту — от 6 000 ₽/мес за 100 000 писем; скидки до 20 % за предоплату на год |
| [Notisend](https://notisend.ru/transactional-emails/) | да: SMTP и API | тариф «за письма» — от ≈ 130 ₽ [не проверено, вторичный источник] |
| [Yandex Cloud Postbox](https://yandex.cloud/ru/services/postbox) | да: SMTP или API, Яндекс уже наш субобработчик | 2 000 писем в месяц бесплатно, дальше — [не проверено] |
| Яндекс 360, VK WorkSpace (почта для бизнеса) | **нет** для транзакционных: это почтовые ящики, у них лимиты (например, 300 получателей на письмо по SMTP) и риск блокировки ([лимиты Яндекс 360](https://yandex.ru/support/yandex-360/business/send/ru/limits)) | от 319–485 ₽ за сотрудника в месяц |
| Cloud.ru | своего почтового сервиса не нашёл | — |

Объём беты — меньше 6 000 писем в месяц → **≈ 800 ₽/мес** [оценка].

### Как получить (на примере Unisender Go)

1. Зарегистрируйтесь на go.unisender.ru и подтвердите почту. Тариф — по карте или по счёту юрлица.
2. Добавьте **домен отправки**. ⚑ Решите: корень домена систем (`noreply@<домен систем>`) или поддомен, например `mail.<домен систем>`. Поддомен изолирует репутацию, но этот слаг нужно зарезервировать, чтобы его не заняла система пользователя (скажите команде).
3. Добавьте в DNS-зону (Cloud.ru DNS или регистратор) записи, которые выдаст провайдер:
   - **SPF:** `TXT @ "v=spf1 include:<значение из ЛК провайдера> ~all"`. SPF-запись на имени должна быть **одна**.
   - **DKIM:** `TXT <selector>._domainkey "v=DKIM1; k=rsa; p=…"` — значение из ЛК.
   - **DMARC:** `TXT _dmarc "v=DMARC1; p=none; rua=mailto:dmarc@<домен>; adkim=s; aspf=s"`. Через 2–4 недели без ошибок переведите на `p=quarantine`.
4. Дождитесь проверки домена у провайдера.
5. Получите SMTP-доступ: хост, порт 465 (SSL) или 587, логин, пароль или API-ключ.
6. Подпишите с провайдером поручение на обработку ПДн — через юриста (раздел 7).

### Как передать

| Имя | Значение | Куда |
|---|---|---|
| `WIZARD_SMTP_HOST` | хост SMTP из ЛК | конфиг |
| `WIZARD_SMTP_PORT` | `465` (по умолчанию) | конфиг |
| `WIZARD_SMTP_USER` | логин | OpenBao |
| `WIZARD_SMTP_PASSWORD` | пароль или API-ключ | OpenBao (staging и prod раздельно; лучше два ключа) |
| `WIZARD_MAIL_DOMAIN` | домен отправки | конфиг |
| `WIZARD_CONNECTORS` | `live` на staging и prod | конфиг (команда) |

Письма реальным людям — это E-EXTERNAL: на staging только синтетика.

**⚑ Решения:** провайдер; домен или поддомен отправки.

## 7. Юридическое (M2-13): юрист, тексты, уведомление РКН

**Что это.** `compliance.yaml#beta_readiness` — гейт до **первого реального пользователя беты**:
1. уведомление РКН по ст. 22 152-ФЗ;
2. позиция юриста по 149-ФЗ (ОРИ, провайдер хостинга) исполнена;
3. ДПО с Cloud.ru и Yandex, копия аттестата Cloud.ru;
4. письмо Z.ai (zero retention, no training, РФ допустима) — иначе T1 выключен;
5. ОРД в `docs/security`: модель угроз, акт УЗ, перечень лиц, приказы. Черновики готовит агент;
6. тексты от юриста: оферта, ДПО, политика ПДн платформы, согласие на ПДн, уведомление по 243-ФЗ, шаблоны согласия и политики для систем.

**Зачем.** **M2-13** (owner: founder) → **M2-09**: приглашение партнёров технически невозможно, пока флаг `beta_readiness` не выставлен. И выход M2.

### Как сделать

1. **Нанять юриста.** Готовый бриф — `docs/week0/lawyer-brief.md`, открытые вопросы — `escalation.yaml#E-LEGAL.open_items`:
   - Z.ai в Сингапуре и ст. 12, ст. 18 ч. 5 (265-ФЗ) — нужно **до первого live-вызова T1 с данными не-основателя**;
   - ОРИ и статус провайдера хостинга;
   - привязка карты как идентификация по ПП 2011;
   - срок хранения по умолчанию: 30 или 90 дней;
   - НДС и реестр ПО.

   Возьмите 2–3 кандидата со специализацией IT и ПДн, сравните цену и сроки.
2. **Тексты** — к неделе 14. Агент вставит их в `docs/legal/*.md` и в шаблоны runtime. Публиковать их от имени компании без юриста нельзя.
3. **Уведомление РКН об обработке ПДн (ст. 22):**
   - [pd.rkn.gov.ru](https://pd.rkn.gov.ru/) → «Реестр операторов» → «Электронные формы заявлений» → уведомление об обработке.
   - Что в нём: оператор, адрес, цели, категории ПДн и субъектов, правовые основания, меры по ст. 18.1 и 19, ответственный за обработку, дата начала, **трансграничная передача** (Z.ai, Сингапур), место нахождения БД (ЦОД Cloud.ru в РФ).
   - Подписать УКЭП руководителя или отправить на бумаге.
   - Срок внесения в реестр — до 30 дней. Подать **до** начала обработки реальных пользователей ([разбор Т-Банка](https://secrets.tbank.ru/buhgalteriya/uvedomlenie-v-roskomnadzor-opd/)).
   - Изменения в сведениях — до 15-го числа следующего месяца.
4. **Уведомление о трансграничной передаче (ст. 12)** — отдельное, тоже до передачи. Спека требует подать его «как страховку», даже если Z.ai получает только обезличенный контекст. Срок рассмотрения в РКН — уточнить у юриста [не проверено].
5. **Приказ** о назначении ответственного за обработку ПДн. Перечень допущенных лиц — в черновиках агента.

### Сколько стоит

- Уведомления РКН — **0 ₽**, госпошлины нет.
- Юрист — **50–150 тыс. ₽** за бриф целиком (`docs/week0/README.md`) [оценка].
- Рынок для ориентира [вторичные источники, [пример](https://abp.legal/personal_data_protection_lawyers)]:
  - пакет «политика + согласие для сайта» — 20–50 тыс. ₽;
  - подготовка уведомления РКН — до 50 тыс. ₽;
  - полный комплект SaaS-документов (оферта, пользовательское соглашение, согласия, cookie) — от 300 тыс. ₽ у крупных фирм.

### Как передать

Секретов нет. Тексты юриста передайте файлами: агент положит их в `docs/legal/`. Ответы Cloud.ru, Yandex и Z.ai перешлите в чат сессии — это не секреты, но **без ПДн третьих лиц**. Отметка «уведомление подано» с номером в реестре нужна команде для флага `beta_readiness`.

**⚑ Решения:** юрист и бюджет; позиция по T1; срок хранения по умолчанию; модель НДС.

## 8. GitHub: тариф, защита `main`, метки, секреты

**Что это.** Настройки репозитория `mrflxxxme/wizard`, без которых не работают auto-merge (F1), обязательные проверки, ночной eval и деплой.

**Зачем.** `escalation.yaml#merge_policy` (запрет прямого push и force-push в main), M1-10, M2-06 (окружения staging и prod).

### Как сделать

1. **Тариф.** Репозиторий приватный, на личном аккаунте. По [документации GitHub](https://docs.github.com/en/get-started/learning-about-github/githubs-plans) защита веток и обязательные ревьюеры в приватных репозиториях есть только с **GitHub Pro**. Environment-секреты в приватном репозитории тоже требуют Pro или Team ([документация](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)).
   - Pro — **$4/мес ≈ 335 ₽** ([pricing](https://github.com/pricing)), Actions — 3 000 мин/мес против 2 000 на Free.
   - Оплатить с российской карты, скорее всего, не выйдет [не проверено].
   - Альтернатива — организация на GitHub Team, $4 за пользователя.
2. **Ветка по умолчанию:** Settings → General → Default branch → `main`.
3. **Auto-merge:** Settings → General → Pull Requests → включить «Allow auto-merge» и «Automatically delete head branches».
4. **Защита `main`:** Settings → Rules → Rulesets → New branch ruleset (или Settings → Branches → Add rule), цель — `main`:
   - Require a pull request before merging. Approvals — 0, иначе auto-merge агентов встанет.
   - Require status checks to pass: **`build`** (workflow ci), **`validate`** (specs), **`fixture`** (eval).
   - Block force pushes, Restrict deletions.
   - «Require branches to be up to date» — на ваше усмотрение: включённое замедляет поток PR агентов.
   - Bypass — никому, или только вам на аварийный случай.
5. **Метки:** Issues → Labels → New label:
   - `founder-review` — PR, требующие вас (`merge_policy`);
   - `eval:full` — полный live-eval;
   - `eval` — по желанию.
6. **Окружения:** Settings → Environments → `eval-live`, `staging`, `prod`.
   - ⚠ **Required reviewers в приватном репозитории на Pro и Team недоступны** (по той же документации). ⚑ Варианты для «prod только с ручным одобрением»:
     - а) деплой prod только через `workflow_dispatch`, запускать его можете только вы. Правила на ветки и теги — по возможностям плана;
     - б) ручная пауза-подтверждение на self-hosted раннере в Cloud.ru;
     - в) GitHub Enterprise, от $21 за пользователя в месяц.
   - Рекомендую **а**. Скажите команде (M2-06).
7. **Секреты и переменные** — Settings → Secrets and variables → Actions, лучше в environment `eval-live`:

| Имя | Тип | Обязательно | Для чего |
|---|---|---|---|
| `CLOUDRU_API_KEY` | secret | да | live-eval, T0 |
| `ZAI_API_KEY` | secret | да, пока сборка по умолчанию на T1 | live-eval, T1 |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | secret | нет | резерв T0 |
| `EVAL_S3_ACCESS_KEY_ID` | secret | нет | Cloud.ru: `<tenant_id>:<key_id>` ([AWS CLI для Cloud.ru S3](https://cloud.ru/docs/s3e/ug/topics/tools__aws-cli)) |
| `EVAL_S3_SECRET_ACCESS_KEY` | secret | нет | Key Secret |
| `EVAL_S3_BUCKET` | variable | нет | имя бакета eval |
| `EVAL_S3_ENDPOINT` | variable | нет | `https://s3.cloud.ru` |
| `EVAL_S3_REGION` | variable | нет | `ru-central-1` — **задать обязательно**: по умолчанию в workflow стоит `ru-central1` |
| `ZAI_BASE_URL` | variable | да для Z.ai | `https://api.z.ai/api/paas/v4/` |
| `WIZARD_BUILD_DEFAULT_TIER`, `EVAL_FULL_MODELS` | variable | нет | см. раздел 3 |
| `CLOUDRU_PROJECT_ID`, `CLOUDRU_IAC_KEY_ID`, `CLOUDRU_IAC_KEY_SECRET` | variable / secret в `staging` и `prod` | к M2-06 | **предлагаемые имена**, временно до OIDC и OpenBao (раздел 1) |

Секреты платформы для работающих серверов (`WIZARD_TELEGRAM_*`, `WIZARD_SMTP_*`, `WIZARD_PLATFORM_YOOKASSA_*`, `WIZARD_SECRETS_KEY` и т. п.) в GitHub **не кладутся** — они живут в OpenBao (`deploy.yaml#cloud.secrets`).

**⚑ Решения:** оплатить Pro или перейти в организацию; способ ручного одобрения prod.
