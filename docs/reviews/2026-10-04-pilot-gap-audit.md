# Аудит готовности к живому пилоту (04.10.2026)

Срез кода и спецификаций на коммите `bce8f1a` (ветка `local/pilot-rehearsal`) перед [грилл-4](grill-4.md). Три независимых прохода: живые модели, универсальность сборки, позиционирование и путь клиента. Ссылки — на файлы репозитория; значения секретов не приводятся.

## 1. Живые модели

**Провайдеры.** Все вызовы идут через OpenAI-совместимый адаптер (`@ai-sdk/openai-compatible`, `packages/llm/src/providers.ts:145-195`). Зарегистрированы (`packages/llm/src/registry.ts:51-98`): `cloudru` (T0, `CLOUDRU_API_KEY`), `yandex` (T0, `YANDEX_API_KEY` + `YANDEX_FOLDER_ID`), `zai` (T1, `ZAI_API_KEY`); `moonshot` выключен, `deepseek` только для eval. Anthropic, OpenAI и OpenRouter запрещены спецификацией (`specs/agents/models.yaml:66`). Маршруты по типам вызовов — `ROUTES` в `registry.ts:191-240`: основная модель сборки glm-5.3 (Z.ai), цепочки T0 — kimi-k2.6, deepseek-v4-pro, glm-5.1, qwen3-coder-next.

**Режимы.** `WIZARD_LLM_MODE` = `fixture` | `live` | `record`, по умолчанию fixture (`packages/llm/src/router.ts:106-108`); для fixture нужен `WIZARD_FIXTURE`. Демо-набор фикстур отвечает по порядку вызовов, а не по содержанию (`packages/llm/src/fixtures.ts:181-188`): **в режиме фикстур любой бриф собирает форум**. Helm: staging — fixture, prod — live. `tools/deploy/local.mjs` включает live, если в `.data/local/inputs.env` есть `CLOUDRU_API_KEY` или `ZAI_API_KEY` (`llmModeOf`).

**Где ключи.** Локально ключей нет: нет `.data/local/inputs.env`, нет `.env` (только `.env.example` с пустыми именами), переменные окружения не заданы. В GitHub есть секреты `CLOUDRU_API_KEY` и `ZAI_API_KEY` (заведены 02.10.2026), их используют `pilot-reusable.yml` и `eval-live.yml`. Значения секретов GitHub наружу не отдаёт.

**Пробелы.**
- Неизвестный регион организации считается ограничением: `orgPolicyOf` (`apps/platform-api/src/runs/queue.ts:249-251`), а новые личные организации создаются с `region_code: null` (`apps/platform-api/src/auth/accounts.ts:90`). На практике клиенты пилота получали бы только T0, и без `CLOUDRU_API_KEY` сборка падала бы с `LLM_UNAVAILABLE`.
- `tools/deploy/pilot-secrets.mjs` (`PLATFORM_PASSTHROUGH`, :196-209) передаёт в поды только `CLOUDRU_API_KEY` и `ZAI_API_KEY`: `YANDEX_*`, все `*_BASE_URL` и `WIZARD_BUILD_DEFAULT_TIER` до подов не доходят.
- Неверный ключ клиенту не виден: 401/403 переводит маршрутизатор на следующую модель, отсутствующий ключ пропускается молча (`router.ts:399`), при отказе всей цепочки — «Модели сейчас недоступны» (`router.ts:438`). Причина остаётся только в `errorCode` таблицы `llm_calls`.
- Живой режим ни разу не запускался: `tools/eval/results/` пуст, M1-10 в статусе `todo`, критерий живой приёмки отложен (`specs/CHANGELOG.md:106`), идентификаторы части моделей помечены `[?]` (`specs/agents/models.yaml`). Зонд ключей есть в `tools/deploy/preflight.mjs:193-224`, но вызывается только из `pilot.mjs check`.
- Сетевой доступ: platform-api и worker могут ходить на `0.0.0.0/0:443` кроме внутренних диапазонов (`infra/helm/wizard/templates/networkpolicies.yaml`); прокси для моделей не нужен, доступность Z.ai из России не проверена (`docs/founder/models-research.md:85`).
- Защиты от перерасхода есть: лимиты на прогон (интервью 2 кредита, импорт 15, сборка — потолок карточки), месячный лимит платформы `WIZARD_LLM_MONTHLY_CAP_RUB` (6 000 ₽), ретраи с backoff, circuit breaker. Ограничителя частоты запросов к провайдеру нет, параллельность — `WIZARD_RUN_CONCURRENCY` = 2.
- Приёмочный e2e стенда (`packages/e2e/specs/rehearsal/pilot.spec.ts`) вводит бриф «форума» и кликает кнопки вопросов по порядку фикстуры — с живыми моделями сломается.

## 2. Универсальность сборки

**Конвейер.** Оркестратор (DLP брифа → анализ → до 7 вопросов → карточка системы, `specs/agents/orchestrator.yaml`) → строитель (план → операции над AppSpec → код только в `ui/**.tsx` и `functions/**.ts` → проверки G0, QA, G1 → цикл исправлений, `specs/agents/builder.yaml`) → QA (сценарии из критериев приёмки) → ворота G0/G1/G2 (`specs/quality/gates.yaml`).

**Промежуточное представление — AppSpec плюс свободный код** (`specs/appspec/appspec.schema.json`): до 60 сущностей, 16 типов полей (включая `file`, `qr_token`), роли и вход (`phone_otp`, `email_otp`, `telegram`), матрица прав с `rowFilter`, воркфлоу (триггеры `on_create`/`on_update`/`on_status`/`schedule`/`webhook`/`manual`, шаги `notify`/`connector`/`function`/`ai_*`/`wait`), функции со списком `egress`, страницы, критерии приёмки, 152-ФЗ, токены темы. **Доменных веток в коде сборки нет** — архитектура общая.

**Что ограничивает на деле:**
- Интеграций четыре: `yookassa` (только разовые платежи, рекуррентные исключены — `specs/connectors/yookassa.yaml:7-8`), `telegram`, `email`, `qr`.
- `ctx.http.fetch` всегда возвращает `EGRESS_DISABLED` (`apps/runtime/src/sandbox/guest.mjs:175`); входящие вебхуки — только через коннекторы.
- Уведомление уходит только пользователю, на которого ссылается запись (`packages/connectors/src/notify.ts:79-83`), письмо — только на `users.email`: владелец не узнает о заявке анонимного посетителя, клиент без аккаунта не получит напоминание.
- У пользователя ровно одна роль, воркфлоу не меняет роль, `rowFilter` видит только встроенные поля `users` — доступ «оплатил → видишь» не выражается.
- Файлы отдаются только на скачивание (`specs/runtime/runtime.yaml:179-182`), CSP не пускает сторонние источники — нет картинок на странице, видео, счётчиков аналитики. Своих доменов нет (non-goal в `specs/product.yaml`).
- Строитель не пишет CSS, ui-kit заточен под полигоны обкатки (Catalog, ItemCard, QrTicket, QrScanner, StatusBoard — `specs/ui/ui-kit.yaml`): нет блоков лендинга, календаря, тарифов, галереи, графиков.
- SMS только для кодов входа, маркетинговые письма запрещены (`specs/connectors/email.yaml:4`).

**Перекос в сторону золотых сценариев:**
- QA: оба few-shot примера — сценарии тикетов форума (`packages/agents/scripts/gen-qa-assets.mjs:55-66`).
- Оркестратор: пример — бриф торта на заказ (`packages/agents/src/orchestrator/prompt.ts:48-53`), текст платформы закрепляет скелет Каталог→Заявка→Процесс→Оплата→Выдача (`prompt.ts:11`).
- Таксономия развилок: кроме 14 общих есть группы только для мероприятий и товаров на заказ (`packages/agents/src/orchestrator/taxonomy.ts:218-280`), сегменты — `events` | `made_to_order` | `horizontal` (`orchestrator/schemas.ts:8`).
- Документация строителя обрезана на M0, описание `FileField` из M2 в промпт не попадает (`packages/agents/scripts/gen-builder-assets.mjs:13`).
- Шаблоны на стартовом экране — только пресеты промпта: `templateId` сохраняется, но агенты его не читают.

**Оценка четырёх типовых брифов:**

| Бриф | Что уже ложится | Чего не хватает |
|---|---|---|
| Лендинг с заявками (стоматология) | Публичная роль, сущность заявки с ПДн, форма с согласием, сроки хранения | Письмо клиники о новой заявке, картинки на странице, блоки лендинга, SEO, свой домен, Метрика |
| Запись в салон с напоминаниями | Услуги, мастера, расписание, записи; мастер видит только свои; проверка пересечений в SERIALIZABLE-мутации; напоминание «за 24 часа»; отчёты | SMS, напоминания клиентам без аккаунта, календарь со слотами |
| Подписка фитнес-тренера | Разовая оплата ЮKassa, личный кабинет | Рекуррентные платежи, доступ по оплате, видео, чат тренера и клиента (non-goal) |
| CRM агентства с Telegram | Стадии сделок и канбан, «менеджер видит свои», напоминания, Telegram ответственному, вложения | Имя клиента в Telegram запрещено G2-TG-01, нет входящих заявок извне и исходящих запросов |

## 3. Позиционирование и путь клиента

- **Позиционирование в спецификации:** «Российская альтернатива Яндекс VibeCraft для нетехнических пользователей» (`specs/product.yaml:8-11`); мероприятия и товары на заказ — полигоны обкатки, не позиционирование. Главное сообщение концепции — «система за ~20 кредитов, цена известна заранее» (`docs/concept.md`).
- **Лендинга нет:** все маршруты, кроме входа, приглашения, юридических страниц и abuse, ведут на вход (`apps/platform-web/src/app/router.ts:23`); лендинг запланирован на M4 (M4-01).
- **Путь клиента:** приглашение → вход по коду → бриф или шаблон → интервью кнопками → карточка системы с оценкой и потолком в кредитах (единственная точка согласия) → сборка с лентой шагов G0/G1/G2 и живым превью → отчёт проверок и публикация с ревью модератора → правки чатом, панель «Стиль», «укажи и измени».
- **Цены:** тарифы Free (100 кредитов на 30 дней, потом 25 в месяц), «Старт» 1 990 ₽ / 50, «Бизнес» 6 990 ₽ / 230, пополнение 990 ₽ / 60; 1 кредит ≈ 5 ₽ себестоимости моделей, сборка около 20 кредитов (`specs/platform/billing.yaml`). На пилоте оплата выключена (`WIZARD_PAYMENTS=off`). При нехватке — ошибка 402 «Не хватает кредитов… Докупите кредиты» с кнопкой «Пополнить» (`apps/platform-api/src/billing/ledger.ts:89`): на пилоте купить нельзя, текст вводит в заблуждение.
- **Связи с людьми почти нет:** нет чата поддержки и контактов, в приветствии «напишите нам» без адреса (`apps/platform-web/src/i18n/ru.ts:88`).
- **Технический жаргон в интерфейсе клиента:** G0/G1/G2, `file:line` в строках проверок, «prod», «DRAFT · РЕВИЗИЯ N · копия prod», «Спека · гарантии / Код · гибкость», «Миграция … аддитивная», «PITR», «агенты видят только ссылку на секрет», «spec.json», «Адрес: slug.<домен систем>» (`ru.ts`, `BuildLog.tsx`, `GateReport.tsx`, `runs/queue.ts`, `publish/workflows.ts`). Правило «без жаргона» есть только для реплик агентов (`specs/agents/orchestrator.yaml`).
- **Сигналы доверия, которые уже есть:** проверка модератором перед первой публикацией, данные систем только в России, 152-ФЗ из коробки, бэкапы с восстановлением на момент времени за 14 дней и откат к любой ревизии, потолок цены и возврат кредитов при сбое платформы. **Чего нет:** SLA, чата поддержки, примеров и отзывов; юридические тексты — черновики для закрытого тестирования.
- **Бренд:** «Wizard» — кодовое имя (`specs/product.yaml:4`), шорт-лист русских имён в `docs/week0/naming-check.md`; в переменных выката GitHub уже стоят домены borntobuild.ru (платформа) и sandpile.ru (системы).

## Итог

Архитектура сборки общая, а «заскриптованность» стенда — следствие режима фикстур. Чтобы пилот стал настоящим, нужны: живые ключи и снятие ограничения неизвестного региона; очистка промптов от золотых примеров; расширение возможностей (платежи с подписками, уведомления посетителям, внешние запросы по списку, картинки и видео, свои домены, компоненты и темы); человеческий слой и рублёвые цены вместо кредитов в интерфейсе; живой замер на брифах всех типов. Решения по каждому пункту — в [грилл-4](grill-4.md).
