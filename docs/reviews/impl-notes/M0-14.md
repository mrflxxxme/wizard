# M0-14 — QA-агент (packages/agents/src/qa): решения

- 2026-09-30 · M0-14 · Экспорт `@wizard/agents/qa`: `createQaAgent({route, orgPolicy?, ctx?, cache?, milestone?, runStep?, onEvent?, signal?})` → `{generate, explain, lastChecks}`. Интерфейс совместим с `BuilderQa` (builder/types.ts). `route` — это `RouteInput → RouteOutput` (Router или обёртка хоста). Адаптер к `host.route` с бюджетом сборки делается в M0-26. До этого кредиты QA в бюджет строителя не входят.
- 2026-09-30 · M0-14 · generate отдаёт полную PC-матрицу (generatePermissionChecks + generateConsentChecks из @wizard/gates). Проверки из выборки qa.yaml#permission_auto.selection (selectG1 по AC карточки) получают level=G1, остальные level=G2: g1Checks берёт только G1, а G2 получит готовую матрицу. AC type=permission → SC-<AC> 1:1 без LLM. AC более поздней вехи (ctx.milestone, по умолчанию WIZARD_MILESTONE или M0) не генерируются.
- 2026-09-30 · M0-14 · Источник AC — карточка (card.acceptance, при пустой — spec.acceptance). Если у AC в спеке уже есть check.steps, QA не вызывает LLM: G1 сам строит SC-<AC> из спеки. Все AC scenario/constraint без сценария уходят в один вызов qa_generate (как в golden: «Критерии для сценариев: AC1, …»).
- 2026-09-30 · M0-14 · Валидация сценария: zod-форма DSL + validateScenario из gates + правила QA: acId/id соответствуют AC, есть ≥1 expect, у constraint есть негативная ветка (error или status ∈ denied/not_found/invalid/conflict/limit/≥400), create/callFn от роли без isAdmin с полями pii≠none несут consent: true. Для callFn запись ПДн определяется эвристически: имя аргумента совпадает с именем поля pii≠none без учёта регистра и «_» (holderEmail ~ holder_email).
- 2026-09-30 · M0-14 · Повтор делается по каждому AC отдельно: если у AC есть невалидный сценарий, модели возвращается tool-result INVALID_ARGS с ошибками и просьба прислать заново сценарии только этих AC. После повтора берутся валидные сценарии, а AC без валидных становится check_invalid. Такой AC отдаётся в G1 как SC-<AC> с пустыми steps: G1 ставит status=error с evidence check_invalid, а explain показывает настоящие ошибки валидации (owner=qa).
- 2026-09-30 · M0-14 · Кеш (qa.yaml#determinism) — ключ `specVersion:acId:sha256(text)`, дословно по спеке. Поэтому новая ревизия вызывает LLM заново. Внутри одного прогона строителя это не важно: он вызывает generate один раз. Кеш подключаемый (`QaCache {get,set}`), по умолчанию в памяти. Невалидный результат тоже кешируется, чтобы повтор G1 был детерминирован.
- 2026-09-30 · M0-14 · В QaGenerateInput добавлено необязательное поле `files`: строитель передаёт исходники functions/**, а дайджест QA показывает имена аргументов функций по валидаторам v.* (regex, best effort). В memory-host добавлены `runtime`/`runtimeRole` для G1 на настоящем runtime.
- 2026-09-30 · M0-14 · explain: код классифицирует по фактам отчёта и по проверке, восстановленной через g1Checks(spec, lastChecks). Правила: PC/SC-permission deny→2xx = permission_too_broad, allow→401/403 = permission_too_narrow, row/hidden/ro = permission_too_broad. В сценарии шаг действия ищется по номеру из evidence: denied/not_found→2xx = too_broad, 401/403 без ожидания отказа = too_narrow (для callFn target=/functions/<i>), UNKNOWN_FIELD/ENTITY = missing_entity_or_field, callFn с 5xx или 400 вместо ok/другой ошибки = function_error (target = файл функции), invalid/conflict→2xx = validation_mismatch. G1-FN-01 = function_error, G1-AC-COVER и check_invalid = check_invalid (owner=qa), SEED_PII = seed_problem, прочие сбои среды (нет runtime, таймаут) = check_invalid (owner=qa, строителю чинить нечего).
- 2026-09-30 · M0-14 · Неоднозначные случаи (fields/count/outbox и т. п.) уходят в один вызов qa_explain (submit_explanations). Ответ проходит zod и guardrails. fix с target /acceptance или текстом «удалить/ослабить/изменить критерий» превращается в owner=qa, fix.kind=none («конфликт критерия и прав: решает QA через оркестратор»). Длины обрезаются, текст проходит scrubJson (ПДн). ask_orchestrator для конфликта AC и прав в M0 не вызывается: хватает owner=qa, мост — в M0-26. Если LLM недоступен или ответа нет, даётся общее объяснение wrong_status_flow без исключения. BUDGET_EXCEEDED и abort пробрасываются.
- 2026-09-30 · M0-14 · Промпт собирается из assets/qa.json. Файл генерирует scripts/gen-qa-assets.mjs из gates.yaml#scenario_dsl, qa.yaml (правила, категории, deterministic_rules, guardrails) и двух эталонов: пример gates.yaml и AC3 из forum.json. Свежесть проверяет тест.
- 2026-09-30 · M0-14 · Приёмка на golden (M0-21) с настоящим G1: спека — `buildSpec`, то есть с полями compliance, которые задают владелец и платформа. Сборка строителя (expectedSpec) не содержит consentText (OWNER_ONLY, из шаблона его подставляет платформа, author=system), поэтому runtime отдаёт consentTextHash="" и любой сценарий с ПДн получает 422 CONSENT_REQUIRED. В e2e-тесте строителя (builder.forum.test.ts) гейт G1 обёрнут и накладывает owner-поля из buildSpec перед runGates. Для M0-26: platform-api должен подставить consentText из consentTemplateId до G1, иначе G1 на черновике упадёт на всех системах с ПДн.
- 2026-09-30 · M0-14 · Новые devDependencies @wizard/agents: `@wizard/runtime` и `@wizard/connectors` (workspace, для G1 в тестах, как у packages/gates).
