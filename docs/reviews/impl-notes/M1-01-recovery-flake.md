# M1-01 — «флейк» восстановления import_table после kill -9: причина и исправление

## Симптом
`apps/worker/test/import-kill.test.ts` › «killed while waiting for confirm…» примерно в каждом третьем запуске (на загруженной машине) падал по таймауту `waitRun` (60 с): после kill -9 воркера 1, правки маппинга и `POST /runs/:id/input` (confirm) при остановленном воркере воркер 2 восстанавливал прогон, но тот так и не завершался.

## Что проверено и отброшено
- executor id и версия приложения: оба воркера `executor_id = local`, `application_version = wizard-worker-1`; `reenqueueWorkflowsForRecovery` переводит PENDING-воркфлоу в ENQUEUED, очередь `runs` его забирает (в диагностике `recovery_attempts` растёт, воркфлоу исполняется).
- Доставка сообщения: `DBOSClient.send` с ключом `<runId>:<inputId>` пишет строку в `dbos.notifications`, восстановленный `DBOS.recv` (topic `input`) её читает — в диагностике `consumed = true`.
- Таймаут и опрос recv (500 мс), конкуренция очереди, дедупликация, гонка со строкой статуса прогона — не влияют: сообщение было получено.

## Причина
Окно «транзакция шага закоммичена, чекпоинт DBOS ещё не записан». `DBOS.runStep` записывает результат шага в `dbos.operation_outputs` отдельным запросом после возврата функции шага. Шаг `needs_input` (RunEngine.#needsInput) внутри своей транзакции ставил `runs.status = needs_input`, `pending_input` с **случайным** `inputId` (`randomUUID`) и событие `needs_input`. Тест видит `inputId` сразу после коммита и убивает воркер; если kill попадает в окно до записи чекпоинта (обычно 2–5 мс, под нагрузкой из-за пауз event loop и очереди к пулу DBOS — десятки мс):
1. confirm уходит с `inputId` A, `provideInput` переводит прогон в `running`;
2. воркер 2 переисполняет шаг `needs_input` (чекпоинта нет) — новый случайный `inputId` B, прогон снова `needs_input`, второе событие `needs_input`;
3. `recv` получает сообщение с A, цикл `if (msg.inputId !== pending.inputId) continue` его отбрасывает, и прогон ждёт ответа на B 24 часа.

Воспроизведено детерминированно (задержка между функцией шага и записью чекпоинта): в `dbos.notifications` сообщение A `consumed`, в `platform.runs.pending_input` — B, воркфлоу PENDING в `DBOS.recv`/`DBOS.sleep`. Естественное воспроизведение на этой машине без нагрузки — 0 из 42 (ширина окна по замеру — 3 мс при опросе теста раз в 20 мс); запуск параллельной нагрузки в этой сессии был запрещён.

## Исправление
- `RunEngine.#needsInput`: `inputId` = `<decisionId|secret>-<sha256(runId:input:<порядковый номер вызова needs_input в исполнении>)[0..8]>`. Код воркфлоу между чекпоинтами детерминирован (то же требование, что и у нумерации шагов DBOS), поэтому повтор доходит до того же вызова с тем же номером. Транзакция шага идемпотентна по этому id: если событие `needs_input` с таким `inputId` уже есть, ничего не пишется (прогон мог уже уйти в `running` от ответа), срок `expiresAt` берётся из события. Порядок шагов не меняется — `WORKER_VERSION` поднимать не нужно; уже записанные чекпоинты со случайными id воспроизводятся как есть.
- Тот же класс ошибки в соседних шагах:
  - `start` (`RunEngine.#start`): переисполнение после закоммиченного старта видело `running` и возвращало null — воркфлоу завершался без finalize, sweep через ≥ 10 с ставил `failed WORKER_RESTARTED`. Теперь в durable-режиме `running` = «наш старт уже закоммичен» (запускает прогон только его воркфлоу), шаг возвращает base/cap из строки без второго `run_started`.
  - `mapping_saved` (imports/workflow.ts): переисполнение затирало правку маппинга, сделанную пользователем, пока воркер лежал. Запись теперь только из статуса `mapping`.
- Остальные шаги с тем же окном уже идемпотентны (acquire_lock, finalize под FOR UPDATE, raise_cap по ключу hold, apply_ops, load_rows) или допускают at-least-once по M1-01.md (события emit, commit_files, LLM-шаг в полёте).
