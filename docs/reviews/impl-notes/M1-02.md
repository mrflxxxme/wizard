# M1-02 — аккаунты, организации, роли, приглашения, блокировка сборки, регион: решения

- 2026-09-30 · M1-02 · Режим по умолчанию — `WIZARD_AUTH_MODE=session` (email OTP): api.yaml#info.x-auth разрешает dev только при явном `WIZARD_AUTH_MODE=dev`. Локальный стенд сохраняет прежнее поведение: scripts/dev.mjs ставит `WIZARD_AUTH_MODE ??= dev` (экраны входа S-auth/S-invite — задача M1-11), playwright.config и .env.example уже задают dev. Неизвестное значение режима — ошибка старта.
- 2026-09-30 · M1-02 · Cookie сессии работает в любом режиме и имеет приоритет. Без cookie в dev-режиме действует M0-пользователь (X-Wizard-Dev-User / dev@wizard.local), в session — 401 UNAUTHORIZED. Неизвестная или дублированная cookie → 401 и очистка cookie.
- 2026-09-30 · M1-02 · Dev-login: `POST /auth/dev-login {email}` (нет в api.yaml) выдаёт настоящую сессию без OTP. Доступен только при `WIZARD_AUTH_MODE=dev` или `WIZARD_DEV_LOGIN=1`, иначе 404. Старт процесса с dev-режимом, `WIZARD_DEV_LOGIN=1` или `WIZARD_UNSAFE_LOCAL_EXEC=1` запрещён при NODE_ENV=production, внутри Kubernetes и на не-loopback адресе (`assertStartupAllowed`, как у runtime). При WIZARD_DEV_LOGIN=1 включается и host guard.
- 2026-09-30 · M1-02 · Cookie: локально по http — `wizard_session`/`wizard_csrf` без Secure, по https — `__Host-wizard_session`/`__Host-wizard_csrf` с Secure. Схему задаёт WIZARD_PUBLIC_SCHEME, при NODE_ENV=production по умолчанию https — как cookie runtime. Остальные атрибуты: Path=/, без Domain, SameSite=Lax, Max-Age 30 дней. Сессия — HttpOnly, CSRF — читаемая (double submit). Срок скользящий, но UPDATE не чаще раза в сутки на сессию.
- 2026-09-30 · M1-02 · CSRF: мутирующий запрос с cookie требует Origin, строго равный WIZARD_PLATFORM_ORIGIN, и X-Wizard-CSRF, равный cookie; sha256 значения должен совпасть с sessions.csrf_hash (защита от подброса cookie). В session-режиме Origin обязателен для всех не-GET, включая /auth/otp/* (login CSRF). platform-web (`client.ts`) шлёт X-Wizard-CSRF из cookie.
- 2026-09-30 · M1-02 · OTP: code_hash = HMAC-SHA256(HKDF(WIZARD_SECRETS_KEY, «otp-pepper»), email ␀ code) — код привязан к адресу. ip_hash — HMAC с отдельным подключом. Без WIZARD_SECRETS_KEY ключ случайный на процесс (после перезапуска коды недействительны). При NODE_ENV=production ключ короче 32 символов → отказ старта.
- 2026-09-30 · M1-02 · Лимиты 5/ч на email и 20/ч на IP считаются по строкам auth_otps за час под `pg_advisory_xact_lock` на email. Добавлен индекс (ip_hash, created_at), в db.yaml его нет, тест колонок это не затрагивает. IP берётся из адреса сокета node-server; за прокси — с M2 (WIZARD_TRUSTED_PROXIES). Во внутрипроцессных тестах IP = «unknown».
- 2026-09-30 · M1-02 · verifyOtp: после 5 неверных попыток код мёртв (attempts = 5). Нет согласия → 422 CONSENT_REQUIRED с details.missing ⊂ [acceptOffer, pdConsent]; код при этом не гасится, чтобы пользователь отметил чекбоксы и отправил тот же код. Согласия нужны новому пользователю, а оферта — ещё и при offer_version ≠ `OFFER_VERSION` («draft-2026-09», до текстов юриста).
- 2026-09-30 · M1-02 · При первом входе пользователь без членств получает личную организацию «Моя организация» (owner, free, region_code NULL → T0 до определения региона). Так работает переход «вход → S1». Стартовый грант Free — задача M1-03.
- 2026-09-30 · M1-02 · Почта: провайдер не выбран (E-ACCESS). `OutboxMailer` пишет письма (OTP, приглашения) в .data/outbox/platform/*.json. WIZARD_DEV_SMTP=1 (dev-smtp :1025) не реализован. При NODE_ENV=production без переданного `mailer` platform-api не стартует.
- 2026-09-30 · M1-02 · Регион: createOrg и PATCH /orgs/:orgId принимают необязательные `regionCode` (2 цифры, «регион при регистрации») и `inn`. В api.yaml этих полей нет, но схемы не запрещают дополнительные свойства. ИНН проверяется по контрольной сумме (иначе 422 INN_INVALID) и не хранится: колонки нет до реквизитов M2. t1_restricted только ставится (90–95 по региону, префиксу ИНН или GeoIP входа), снимает его staff.
- 2026-09-30 · M1-02 · GeoIP — хук `PlatformApiOptions.geoRegion(ip)`: вход из региона с ограничением ставит t1_restricted всем org пользователя. Офлайн-базу GeoIP ещё не выбрали (лицензия данных, THIRD_PARTY_NOTICES), поэтому по умолчанию хука нет. Правило «вход за 90 дней» проверяется в момент входа.
- 2026-09-30 · M1-02 · OrgSettings.t1Restricted отдаёт фактическое значение (t1_restricted || region_code IS NULL), как у роутера и buildModelLabel. PATCH /orgs/:orgId/settings {ruOnly} (owner) реализован: движок читает политику на каждом вызове. Сброс кэша и отмена T1-вызовов в полёте — задача M1-07.
- 2026-09-30 · M1-02 · Приглашения: токен — 32 байта base64url, в БД sha256. Повторное приглашение на тот же адрес отзывает прежнее. Приглашение текущего участника → 400 VALIDATION_FAILED. Неизвестный токен → 404, принятое/отозванное/истёкшее → 410 INVITE_EXPIRED, чужой email сессии → 403 FORBIDDEN. Место в лимите тарифа (members) занимают участники и активные приглашения (402 PLAN_LIMIT {limit, current, plan}); при принятии лимит проверяется снова. Принятие не понижает роль. Лимит приглашений в сутки (L3-29) — задача M1-06.
- 2026-09-30 · M1-02 · Лимит draft_systems в createSystem (billing.yaml#enforcement) не введён: локальная org M0 и тесты создают больше 3 систем. Переносится в M1-03 вместе с тарифами. createSystem без orgId у участника нескольких org в session-режиме → 400; dev-режим по-прежнему берёт локальную org.
- 2026-09-30 · M1-02 · Блокировка: GET /systems/:id/lock — очередь состоит из прогонов waiting_lock по created_at, holder.name = name ?? email. DELETE (owner) отменяет держащий прогон через RunEngine.cancel. Устаревшая строка locks завершённого прогона удаляется. Очередь и lock_waiting — прежние, из движка M0.
- 2026-09-30 · M1-02 · Роли: `checkOrgAccess(..., code)` умеет 403 NOT_OWNER. test/roles-idor.test.ts перебирает все операции api.yaml с {id}/{orgId}, которые есть в app.routes. Чужая org → 404, роль ниже x-roles → 403 FORBIDDEN|NOT_OWNER. Поэтому publish/rollback M1-04 попадут в проверку автоматически. Для M1-04: publish — `checkOrgAccess(user, org, "owner", "Система", "NOT_OWNER")`, в publishBlockers — NOT_OWNER для не-owner.
- 2026-09-30 · M1-02 · Тест миграций проверяет колонки таблиц M0 и M1-02 (auth_otps, sessions, invites) и требует, чтобы каждая таблица схемы platform была в db.yaml. Таблицы M1-04 его не сломают. Миграция — отдельный файл 0002_m1_accounts.
- 2026-09-30 · M1-02 · Проверки Playwright «M1-02» из ui/platform-screens.yaml (S10: viewer видит settings-invite/revision-rollback disabled; S-invite: принятие приглашения) требуют экранов M1-11. Бэкенд для них готов и покрыт API-тестами (orgs.test.ts).
