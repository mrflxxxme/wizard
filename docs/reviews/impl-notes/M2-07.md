- 2026-10-01 · M2-07 · Анти-кардинг (L3-28). Попытка = строка payments kind=card_binding. Лимиты: ≤ 3 на org и ≤ 10 на IP (по meta.ipHash = HMAC(IP), IPv6 по /64) за 24 ч, считаются под advisory xact locks, превышение → 429 RATE_LIMITED. Неудачные и брошенные попытки тоже считаются. payments.created_at пишется часами ledger, так тесты двигают время. IP клиента = `clientIp(c, WIZARD_TRUSTED_PROXIES)` через effectiveClientIp: правый недоверенный хоп XFF и только от доверенного пира. Это действует и на лимиты OTP M1-02.
- 2026-10-01 · M2-07 · Привязку проверяет вебхук waiting_for_capture после GET. Порядок проверок: payment_method.saved = true, затем issuer_country = RU (иначе CARD_NOT_RU), затем three_d_secure.applied = true. Затем отпечаток не встречается в ≥ 3 других org; считаются все строки, включая отозванные. Отказ без 3-DS и по лимиту карт → CARD_BINDING_REJECTED с текстом без причины. Успех: payment_methods (last4, card_type, issuer_country), прежние карты org отзываются, подписка переходит на новую карту. В любом случае затем POST /payments/{id}/cancel с ключом cancel:<paymentId> и статус canceled. Результат в meta.result; GET billing отдаёт его как `cardBinding {status: pending|bound|rejected|cancelled, code, message_ru}` (расширение схемы Billing), его опрашивает страница возврата. first6, срок и PAN в БД не попадают (тест).
- 2026-10-01 · M2-07 · Вебхук POST /api/v1/webhooks/yookassa смонтирован до Origin-guard и аутентификации. Проверки по порядку: IP вне allowlist или неизвестен → 401 без обращения к API; тело > 256 КиБ → 413; затем GET /payments/{id}. Строку ищем по provider_payment_id, иначе по metadata.paymentId, если ответ на создание был неизвестен и id не сохранён. Затем сверяются metadata.paymentId, сумма и RUB; несовпадение → 200 и игнор. Неизвестный платёж → 200. Сбой API → 500, чтобы ЮKassa повторила доставку. Платёж выходит из pending/waiting_for_capture один раз под FOR UPDATE, поэтому двойная доставка succeeded даёт один грант (тест). Тело уведомления статусом не считается (тест на поддельный succeeded).
- 2026-10-01 · M2-07 · Поле subscriptions.plan означает тариф СЛЕДУЮЩЕГО периода, текущий — orgs.plan. PUT с тем же тарифом возобновляет автоплатёж. Более дешёвый тариф применяется с продления; Billing.nextPlan — расширение схемы. Более дорогой тариф: платёж сразу по привязанной карте за полную цену, новый период с текущего момента; кредиты старого периода живут до своего срока. Без активной подписки (none/cancelled/past_due) — первый платёж: по привязанной карте (payment_method_id) или страница ЮKassa с save_payment_method. Сохранённая этим платежом карта становится привязкой, если проходит те же проверки L3-28. 409 не используется. DELETE ставит cancel_at_period_end и next_charge_at = null. past_due при DELETE заканчивается сразу и переводит org на free.
- 2026-10-01 · M2-07 · Период подписки — календарный месяц (addMonth с усечением дня), а не 30 дней, как в CLI M1-03. Грант тарифа — ledger.grant plan_monthly с ключом grant:plan_monthly:<org>:<начало периода ISO>, сроком до конца периода и payment_id. Докупка — grantTopup с ключом topup:<paymentId>, payment_id = payments.id.
- 2026-10-01 · M2-07 · Продление: Idempotence-Key renew:<org>:<начало нового периода ISO>; вторая и третья попытки — renew:<org>:<period>:2 и :3. Каждая попытка — новый платёж: ЮKassa вернула бы отменённый платёж по старому ключу. Попытки идут в current_period_end + 0, +1 и +3 дня; на время повторов тариф сохраняется, новых кредитов нет. После третьей неудачи — past_due без автоплатежей, а через 7 дней (end + 10 дней) — cancelled и orgs.plan = free. Отказ API 4xx (метод не сохранён) или отсутствие карты считается неудачной попыткой. Неизвестный результат оставляет платёж pending и повторяется с тем же ключом.
- 2026-10-01 · M2-07 · Письмо за 24 ч до автоплатежа (MailMessage.kind = billing) отправляет ежечасный проход, если конец периода попадает в (now+23 ч, now+24 ч]. Отметки об отправке в схеме нет: в окно попадает ровно один ежечасный проход, а при повторе шага DBOS письмо может уйти дважды.
