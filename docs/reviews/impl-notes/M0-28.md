# M0-28 — решения реализации

- 2026-09-30 · M0-28 · `validateSpec(config, spec, at)` получает третий аргумент `{integration, base}`: без него нельзя проверить объявленные secretRefs (telegram при bot=own, email при smtp) и шаги notify по имени интеграции; пути ошибок — абсолютные JSON Pointer в спеке.
- 2026-09-30 · M0-28 · `SpecIssue {code: SCHEMA_INVALID|CONFIG_INVALID, path, message_ru, rule, allowed?}`: ошибки configSchema → SCHEMA_INVALID (правило `<connector>.config_schema`), ссылки/секреты → CONFIG_INVALID; поле `rule` — стабильный id правила для гейтов и фикстур. Точка входа G0 — `validateIntegrations(spec)`.
- 2026-09-30 · M0-28 · В `ConnectorCtx` добавлены `store` (KV с TTL: `_w_connector_calls`, метаданные платежей, отозванные QR), `outbox` и `now()`; `SystemDb` — минимальный нетипизированный интерфейс (get/getBy/list/insert/patch), `insert` бросает `UniqueViolation`. Runtime (M0-09/M0-23) адаптирует DataAccess к нему.
- 2026-09-30 · M0-28 · yookassa: журнал платежей проверяется на статусы pending/succeeded/canceled; `needs_review` не требуется, потому что его нет в эталонных forum.json и bakery.json (иначе они не проходят G0), хотя обработчик payment.succeeded пишет `needs_review` по yookassa.yaml. Нужна правка эталонов (добавить needs_review в payment.status) — до M2-02.
- 2026-09-30 · M0-28 · yookassa: G0-правило «amountField ∈ readonlyFields или роль без update» реализовано так: у каждой permission с update на сущность привязки amountField обязан быть в readonlyFields. `refundWindowDays` и `receipt` обязательны.
- 2026-09-30 · M0-28 · Привязка платежа к binding хранится в `ctx.store` (`pay:<provider_payment_id>`), так как сущность журнала общая для нескольких привязок (bakery prepay/final) и поля binding в ней нет.
- 2026-09-30 · M0-28 · `/api/pay` и `/_wizard/pay-mock` — функции `startPayment`/`confirmMockPayment`, а не `routes` коннектора: чтение записи с правами вызывающего делает runtime. Mock-подтверждение вызывает тот же `applyPaymentSucceeded`, что и вебхук после GET-сверки (L1-23).
- 2026-09-30 · M0-28 · telegram: bot=own требует botUsername (нужен для deep link) и secret://telegram_bot_token; telegram_webhook_secret не обязателен (генерирует платформа). bot=platform + botUsername → SCHEMA_INVALID.
- 2026-09-30 · M0-28 · telegram.sendToUser в test-режиме возвращает `{delivered: true, reason: 'test_mode'}` (сообщение ушло в outbox); без привязанного чата — `not_linked`, как в live.
- 2026-09-30 · M0-28 · email: provider по умолчанию `platform`; при platform поля host/port/secure/user запрещены; при smtp secure обязан совпадать с портом (465 ↔ true, 587 ↔ false). Проверка резолва host в приватные адреса — при подключении (M1-06), в G0 только запрет IP-литералов через EGRESS_HOST_RE из appspec.
- 2026-09-30 · M0-28 · email outbox в M0 пишется в `<connector>.jsonl`, как у telegram, а не в `*.eml`; PNG QR-вложения нет (нужна библиотека QR — M1-06), в outbox пишется только `attachQrOf`.
- 2026-09-30 · M0-28 · QR: rand — base32 RFC 4648 в верхнем регистре; секрет qr_signing_key — либо один base64url-ключ (kid 1), либо JSON-связка `{activeKid, keys[]}` для ротации. Неразбираемый payload, неизвестный/истёкший/отозванный kid → `bad_signature`. Отозванные токены хранятся хешем `qrTokenHash(rand)` в `ctx.store`.
- 2026-09-30 · M0-28 · QR G0: checkin-сущность обязана иметь поле `scanned_at` (datetime); device_id/gate/offline пишутся, если поля есть. Проверка `displayFields` на pii=none оставлена G2.
- 2026-09-30 · M0-28 · M1/M2-коннекторы в mode=live в M0 бросают `EGRESS_DISABLED`; ретраи и живые вызовы провайдеров — M1-06/M2-02.
