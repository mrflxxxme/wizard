# M2-14 — файлы в системах: решения реализации

- 2026-10-01 · M2-14 · Хранилище (apps/runtime/src/files/storage.ts): интерфейс `FileStorage {put, head, get, delete, list}` и три бэкенда — `S3FileStorage` (S3-совместимое, Cloud.ru Object Storage, path-style `<endpoint>/<bucket>/<key>`, SSE-KMS заголовками `x-amz-server-side-encryption: aws:kms` + key id, если задан `WIZARD_S3_KMS_KEY_ID`), `FsFileStorage` (папка, dev и e2e) и `MemoryFileStorage` (тесты, G1). Ключ — `<schema app_<key>_<env>>/<fileId uuid>`; бэкенды принимают только такую форму ключа (без обхода путей и чужих префиксов). Метаданные `{name, mime, size, entity, field, uploadedBy, uploadedAt}` едут с объектом (S3 — `x-amz-meta-wizard` base64url JSON, папка — `<id>.meta.json`): отдельной системной таблицы нет, appspec SYSTEM_TABLES и DDL старых схем не меняются.

- 2026-10-01 · M2-14 · `POST /api/files` (multipart: `file`, `field`, `entity?`): тело читается с потолком 10 МБ + 256 КБ (без Content-Length тоже), файл > 10 МБ → 413 «Файл больше 10 МБ», пустой → 422. Тип — только по сигнатуре (jpeg FF D8 FF, PNG, RIFF…WEBP, %PDF-), имя и Content-Type игнорируются; остальное (SVG, HTML, XML, JS, zip, gif) → 415 UNSUPPORTED_MEDIA_TYPE «Такой тип файла загрузить нельзя». Право: у роли create или update на сущность, поле не hidden и не readonly; `entity` необязателен — если поле с таким именем пишет ровно одна сущность роли (FileField по спеке ui-kit не получает entity). Имя файла очищается (без пути, управляющих и bidi-символов, ≤ 120). Ответ 201 `{fileId, name, size, mime}`. Лимит 60 загрузок в час на пользователя (у public-роли — на HMAC сети клиента) на систему → 429 + Retry-After (в процессе, как остальные M1-лимиты).
- 2026-10-01 · M2-14 · Значение поля file — fileId загрузки. Проверка в DataAccess (data/pg.ts, `FileFieldGuard`) для data API и ctx.db: uuid, объект этой системы для той же entity.field, загружен тем же пользователем (системный контекст — любой загрузкой поля) и не занят другой строкой; иначе 422 VALIDATION_FAILED с полем `{code: FILE_NOT_FOUND, message: «Файл не найден — загрузите его снова»}`. Неизменённое значение не перепроверяется. Без этой проверки знание чужого fileId давало бы чтение файла через свою строку.
- 2026-10-01 · M2-14 · Раздача: `GET /api/files/:fileId` → проверка права read строки, которая держит файл (getBy от имени субъекта: rowFilter, hiddenFields, нет права, неизвестный id → 404) → 302 на `/api/files/:fileId/content?t=…`. Ссылка — AES-GCM-конверт ключей runtime (`WIZARD_SECRETS_KEY`, AuthKeys.seal) `{fileId, userId, exp}`, привязан к схеме, TTL 5 мин (≤ 15), принимается только той же сессией (у public-роли — любой). Ответ: `Content-Disposition: attachment` (ASCII-замена + `filename*=UTF-8''…`), `Content-Security-Policy: sandbox` (+ frame-ancestors от общих заголовков), `X-Content-Type-Options: nosniff`, Content-Type из allowlist, `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`. `GET /api/files/:fileId/info` → `{fileId, name, size, mime}` с той же проверкой (FileField в форме редактирования).
- 2026-10-01 · M2-14 · РАСХОЖДЕНИЕ runtime.yaml#files.serve: «302 на подписанную ссылку» реализован как 302 на ссылку, подписанную runtime (байты отдаёт runtime из хранилища), а не presigned URL S3: S3 не умеет отдавать `Content-Security-Policy: sandbox` и nosniff по объекту, а заголовки — критерий приёмки. `presignUrl` есть и проверен, если позже понадобится отдача напрямую из бакета (тогда CSP — на стороне CDN/прокси). В спеке стоит уточнить формулировку.
