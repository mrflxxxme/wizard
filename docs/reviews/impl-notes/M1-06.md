# M1-06 — решения реализации

- 2026-09-30 · M1-06 · G2-TG-01 в M1 — правило validateSpec telegram (G0): плейсхолдеры `{{field}}`/`{{ref.field}}` текста шага notify разрешаются по сущности триггера воркфлоу; pii≠none, любая ссылка на users (`{{holder_user.x}}`) и ПДн в самом тексте (packages/pii detect) → CONFIG_INVALID с rule `G2-TG-01`; неизвестное поле → `telegram.template_field`; `to` не `$record.<ref на users>` → `<connector>.notify_recipient`.
- 2026-09-30 · M1-06 · email G0: тема с pii-плейсхолдером → `email.subject_pii` (для шаблона без шагов — по имени поля в любой сущности, консервативно); тело с pii допустимо только когда `to` шага = `$record.<ownerField>` сущности триггера, иначе `email.body_pii_recipient`.
- 2026-09-30 · M1-06 · Токен ссылки общего бота — `<systemId 12><d|p><19 случайных base64url>` (32 символа, ~114 бит): вебхук платформы находит систему по префиксу; хранится только sha256 в `_w_telegram_links`, одноразовый (delete … returning), TTL 24 ч. Свой бот — 32 случайных символа. Для поиска по systemId в SystemRegistry добавлен необязательный `resolveById`, в SystemCache — `byId`.
- 2026-09-30 · M1-06 · Вебхук общего бота обслуживается на голом домене систем (`<systemsDomain>/_wizard/hooks/telegram/_platform/<hookToken>`); hookToken = HMAC(WIZARD_TELEGRAM_WEBHOOK_SECRET, "hook:_platform")[:32], у своего бота — HMAC(telegram_webhook_secret, "hook:<integration>"); без секрета telegram_webhook_secret он выводится из токена бота (HMAC). Хранить hookToken не нужно. Неверный hookToken → 404, неверный заголовок секрета → 401.
- 2026-09-30 · M1-06 · Ответы бота («Готово, уведомления подключены», автоответ) отдаются методом в теле ответа вебхука (sendMessage в JSON), без исходящего запроса; идемпотентность по update_id: свой бот — ctx.store (24 ч), общий бот — множество последних 10 000 update_id в процессе runtime.
- 2026-09-30 · M1-06 · kicked у общего бота обнуляет telegram_chat_id во всех схемах `app_*`, где у роли runtime есть UPDATE на users (транзакция на схему, `wizard.role='__system'`).
- 2026-09-30 · M1-06 · Лимиты — счётчики фиксированного окна в ctx.store (`consumeQuota`): email 300/ч (Free 100), общий бот 60/мин на систему (≈1/с) и Free 500/сут, приглашения 20/сут (Free 5). Счётчик не атомарен и в runtime хранится на интеграцию (для писем и Telegram), приглашения — на систему (`_platform`). Общая очередь 25/с с честным разделением и событие владельцу о превышении — вместе с поллером _w_jobs (M1-01/воркфлоу).
- 2026-09-30 · M1-06 · Тариф в ctx.system.plan: реестр в M1 несёт только features.phoneOtp (Старт/Бизнес по F4), поэтому phoneOtp=true → paid, иначе free. Нужен явный plan в platform.deployments.
- 2026-09-30 · M1-06 · Повторы в invokeAction: `retry.attempts` — общее число попыток; задержка baseMs·4^n ±20% или retry_after/Retry-After провайдера; не дольше дедлайна (30 с по умолчанию, у функций 25 с). В логе — status `retry` и providerStatus.
- 2026-09-30 · M1-06 · SMTP — свой минимальный клиент (node:net/tls), без nodemailer: полный контроль заголовков (CR/LF/NUL, RFC 2047 B-кодирование по кодовым точкам ≤ 75 символов), неявный TLS 465 или обязательный STARTTLS 587 (нет STARTTLS → CONFIG_INVALID), буфер до STARTTLS сбрасывается. Хост provider=smtp резолвится, при любом адресе RFC1918/loopback/link-local/CGNAT/ULA/NAT64/multicast → CONFIG_INVALID до соединения; соединение идёт на проверенный IP с SNI и проверкой сертификата по имени хоста (защита от DNS rebinding). «Адрес кластера» отдельно не задан — закрывает egress-proxy M2.
- 2026-09-30 · M1-06 · Письма: text + HTML (простой шаблон без внешних картинок), multipart/related с inline PNG QR (cid), если attachQrOf; QR берётся из поля tokenField qr-интеграции этой сущности (библиотека qrcode-generator, MIT — уже в THIRD_PARTY_NOTICES, PNG собирается через node:zlib). Message-ID — на домене адреса отправителя. Test-режим пишет в outbox и `.eml`; при WIZARD_DEV_SMTP=1 (локально) — в dev-приёмник 127.0.0.1:1025.
- 2026-09-30 · M1-06 · Отказы почты (bounces, users.email_bounced_at) не реализованы: провайдер не выбран (E-ACCESS), в users нет колонки email_bounced_at (appspec SYSTEM_TABLES) — нужна миграция в packages/appspec.
- 2026-09-30 · M1-06 · Переменные окружения сверх deploy.yaml#local.env_vars.M1: WIZARD_TELEGRAM_BOT_USERNAME (имя общего бота — E-NAME; без него /api/telegram/:i/link → 503 SECRET_MISSING), WIZARD_TELEGRAM_API_BASE (заглушки), WIZARD_SMTP_HOST/PORT/USER/PASSWORD (почтовый аккаунт платформы, E-ACCESS), WIZARD_MAIL_DOMAIN (по умолчанию WIZARD_SYSTEMS_DOMAIN), WIZARD_DEV_SMTP_PORT, WIZARD_CONNECTORS=live (main.ts: функции идут через @wizard/connectors). Нужно дописать их в deploy.yaml и .env.example.
- 2026-09-30 · M1-06 · POST /api/admin/invite реализован минимально в runtime (routes/invite.ts): только isAdmin, роль с access=login, email или телефон +79…, квота до вставки, users(role, email|phone, invited_by), конфликт → 409; письмо-приглашение — с почтового аккаунта платформы (sendPlatformEmail), SMS не отправляется (провайдер — E-ACCESS/M1-05). Ошибка почты не откатывает пользователя: ответ `emailSent: false`.
- 2026-09-30 · M1-06 · Зарезервированные slug (L3-29) — `RESERVED_SYSTEM_SLUGS` в @wizard/connectors; runtime отбрасывает такие записи реестра и не пиннит их. В apps/platform-api/src/services/slug.ts есть свой такой же список — стоит перейти на общий экспорт.
- 2026-09-30 · M1-06 · В ConnectorCtx добавлены `platform` (секреты и настройки платформы, DNS/TCP для SMTP), `telegramLinks`, `users.setTelegramChat/clearTelegramChat`, `system.plan`; ctx.fetch в runtime — guardedFetch (только https и публичные адреса после резолва; хост Bot API из настроек платформы доверенный). - 2026-09-30 · M1-06 · Шаг notify (`runNotifyStep`) готов для поллера _w_jobs: ключ `<jobId>:<stepIndex>:<action>:0`, `{{link}}` — абсолютная ссылка из params.link (путь с `$record.<поле>`) или корень системы. Вызов из поллера — задача воркфлоу M1.
