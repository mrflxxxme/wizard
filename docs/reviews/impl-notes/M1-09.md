# M1-09 — G1 полный: воркфлоу и время в сценариях, объяснения — решения

- 2026-09-30 · M1-09 · Минимальный исполнитель заданий — apps/runtime/src/jobs/runner.ts (+ cron.ts), `RuntimeApp.runJobs({slug, env, now?, since?, maxRounds?})` → `RunJobsReport {now, ran, failed[], retention[], pending}`. Это один проход при заданном `now`: триггеры → выполнение → повтор, пока есть работа (≤ 20 раундов), затем retention. Фоновый поллер (runtime.yaml#workflows.execution, M1) в процессе runtime не запускается. Его цикл — вызов runJobs по таймеру, это отдельный шаг.
- 2026-09-30 · M1-09 · Триггеры on_create/on_update/on_status читаются из _w_audit, а не из пути записи: каждая запись data API и ctx.db/ctx.systemDb уже пишет туда entity/record_id/op/fields. Курсор (последний id аудита и время прошлого прохода) хранится в строке _w_jobs с idempotency_key `__wizard_cursor` (run_at = locked_until = infinity). Триггер ставится в _w_jobs в одной транзакции со сдвигом курсора. Поэтому pg.ts (зона M0-09/M0-23) не менялся. Расхождение со спекой: задание появляется не в транзакции изменения, а при следующем проходе. Семантика at-least-once сохраняется.
- 2026-09-30 · M1-09 · on_status срабатывает на последнюю запись поля в пачке аудита (create считается всегда), если текущее значение равно equals. Ключ идемпотентности — `wf:<name>:a<auditId>`. Повторная запись того же значения (paid → paid через update со status) запускает воркфлоу снова. schedule relative: запись с `field + offset ≤ now` и `≥ created_at` («прошедшее время → не запускать»), ключ `wf:<name>:<id>:<due>`: при смене поля due меняется, и задание ставится заново. cron — только последнее вхождение в окне (курсор.at или since, now], 5 полей, app.timezone (по умолчанию Europe/Moscow), не дальше года назад.
- 2026-09-30 · M1-09 · Выполненные задания не удаляются, а помечаются payload.state=done и locked_until=infinity. Иначе relative-триггер поставил бы их снова (дедупликация по ключу). Упавшее задание: attempts+1, run_at = now + 1 с·4^(n−1) (≤ 16 мин), после 5-й попытки state=dead. Шаг воркфлоу возобновляется с упавшего шага (payload.step). wait ставит продолжение с ключом `<jobId>:<stepIndex>`. Очистка завершённых строк _w_jobs не сделана (задача поллера/M2).
- 2026-09-30 · M1-09 · Шаги: function — FunctionHost.call(via internal, SYSTEM_USER), при выключенном WIZARD_UNSAFE_LOCAL_EXEC → FUNCTIONS_DISABLED. notify — telegram.sendToUser {userId, text} / email.sendTemplate {userId, template, attachQr, entity, recordId}, в outbox значения полей не идут (текст — из шаблона {{field}}/{{ref.field}}). connector — действие outboxConnectors. update/create — ctx.systemDb. wait — продолжение. ai_* — пропуск до M3. В отчёт идёт только код ошибки, без сообщения: в нём могут быть значения. Коннекторы в режиме live пока тоже пишут в outbox (живые email/telegram — M1-06). ctx.now функций — часы runtime, а не «замороженное» время прохода.
- 2026-09-30 · M1-09 · Retention (runtime.yaml#workflows.retention) выполняется на каждом проходе runJobs, а не «ежесуточно в 03:00»: для G1 время сдвигает сценарий, а операция идемпотентна. anonymize → поля pii≠none (и file) = NULL, только у строк, где что-то не NULL. delete → DELETE. Если строк > 0, пишется счётчик в _w_audit (op='retention', fields = имена). Режим по умолчанию — delete. users (3 года без входа) — M2.
- 2026-09-30 · M1-09 · DSL: advanceTime сдвигает $now сценария и сразу делает проход runJobs (как runWorkflows). Время прохода = max(ctx.now, реальные часы в начале сценария) + сдвиг: строки получают created_at от часов БД, и исполнитель не должен отставать от них. since окна cron = начало сценария. Упавшее задание даёт шагу результат HTTP 500 <code>, evidence «(воркфлоу <name>, шаг <k> <type>)» или «(функция <name>)». FUNCTIONS_DISABLED и runtime без runJobs дают status=error. validateScenario: advanceTime.minutes — целое 1…5 760 000 (4000 дней), runWorkflows — только {}. RuntimeHandle.runJobs необязателен. platform-api (trackingHandle) его пробрасывает.
- 2026-09-30 · M1-09 · Форум AC6 зависит от даты: registerTicket (specs/runtime/examples) фиксирует начало 2026-11-14, а сценарий сдвигает время на 63 дня. Порог (+30 дней) пройден, только если часы сценария позже 2026-10-12. Тест G1 на M1 передаёт ctx.now = max(сейчас, 2026-10-20). Спеку не меняли.
- 2026-09-30 · M1-09 · QA: constraint со сдвигом времени валиден без expect-ошибки, если после advanceTime есть expect: негативная ветка — это состояние после срока (retention, дедлайны). Дайджест qa_generate показывает сроки хранения («ticket: 30 дн. от event_starts_at, anonymize») и триггеры/шаги воркфлоу (on_status ticket.status="paid", schedule ticket.event_starts_at-1440м, notify(email → $record.holder_user), if).

- 2026-10-01 · M1-09 · G1-RENDER-01 подключена (с M1): packages/gates/src/g1/render/. Для каждой страницы и каждой её роли выполняется react-dom/server renderToString (как в gates.yaml). - 2026-10-01 · M1-09 · Данные при SSR: эффекты на сервере не выполняются, поэтому при сборке бандла рендера useRemote в @wizard/sdk получает в начале перехват (globalThis.__wzSsrRemote, правка исходника только в бандле рендера; сам пакет sdk не меняли). Проход рендера записывает недостающие ключи, они загружаются, следующий проход рендерит с данными (≤ 4 проходов). Поэтому ловятся и падения «до данных» (data === undefined), и падения на данных seed. Если якорь useRemote в sdk изменится, сборка рендера упадёт с понятной ошибкой (тест g1-render).
- 2026-10-01 · M1-09 · Изоляция рендера: код страниц — это сгенерированный код. Поэтому он выполняется в отдельном процессе по механизму isolation.yaml#M0_M1, как исполнитель функций runtime: node --permission --allow-fs-read=<папка бандла>, env {}, node:vm без кодогенерации из строк, только JSON по IPC. Из рендера выходят только чтения: GET /api/* и /_wizard/*, POST /api/fn/<query>. Остальное получает 403, абсолютные URL отклоняются. Без WIZARD_UNSAFE_LOCAL_EXEC=1 (runtime.env.unsafeLocalExec) проверка даёт error, код страниц не запускается. Лимит — 10 с на пару «страница × роль» (G1Options.renderTimeoutMs). Зависший процесс получает SIGKILL, следующий рендер стартует в новом процессе. Общий бюджет G1 120 с соблюдается: при его исчерпании проверка даёт error.

- 2026-10-01 · M1-09 · Подсказки seed от QA (qa.yaml#seed.rules MAY): Scenario.seedHints?: [{entity, field, values}] — values[i] попадает в строку i сущности, не больше 10 значений и 20 подсказок на сценарий. Подсказки живут в сценарии, а не в отдельном поле GateContext: QaCheck и так проходит через builder и platform-api без изменений, а кеш QA хранит их вместе со сценарием. Допустимы только поля pii=none типов string/text/enum/int/decimal/money/bool, не unique. Значения проверяются по maxLength, enum, min/max, для money — кратность 100. DLP (nonSyntheticPii) отклоняет значения, похожие на ПДн. validateScenario возвращает ошибки подсказок, и QA повторяет запрос с ними. G1 сливает подсказки всех исполняемых сценариев (для каждой строки побеждает первая) и передаёт их в generateSeed(spec, key, {now, hints}). Невалидные подсказки генератор игнорирует, rowFilter-владельцы строк не перезаписываются. seedDlp выполняется как раньше.
