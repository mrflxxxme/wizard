# M2-04 (продолжение) — G2 в публикации: решения реализации

- 2026-10-01 · M2-04 · Переключатель — `config.prodG2Required`: веха ≥ M2 (`WIZARD_MILESTONE`) или `NODE_ENV=production`. Устроен так же, как `cardBindingRequired` из M2-07 (общая функция `m2OrProd`). При выключенном флаге публикация идёт как в M1: только G0 для prod. Поэтому тесты M1, e2e и dev-стенд (`WIZARD_MILESTONE=M0`) не меняются.
- 2026-10-01 · M2-04 · apps/platform-api/src/agents/executors.ts: в обход runtime идёт только G0. G1 и G2 получают один и тот же in-process runtime (trackingHandle, выгрузка в finally), runtimeRole и `withConsentText(spec)`. Тест golden (forum) прогоняет настоящий G2 через исполнителей платформы. G2-PERM-01…04 дают pass, а не error, схема `app_<key>_g2_%` удалена.
- 2026-10-01 · M2-04 · Шаги publish (src/publish/workflows.ts, `prodG2`): после `gate_G0_prod` и до `telegram_webhook`, как в workflows.yaml. (1) Предусловие G2 «G1 passed на этой ревизии» (gates.yaml#G2.precondition): если в gate_reports нет пройденного G1 для публикуемой ревизии, запускается шаг `gate_G1_prod`. Типичный случай — ревизия из setCompliance без сборки. Если G1 не пройден, публикация падает с GATES_FAILED. (2) Шаг `gate_G2` получает `env=prod`, `slug`, `secretExists` и `abuse`. Каждый гейт пишет gate_started, gate_reports и gate_result, как гейты черновика, поэтому отчёт виден в `/gates/latest` и в ленте прогона.
- 2026-10-01 · M2-04 · Блокер G2 → run_failed GATES_FAILED, publication=failed, prod не тронут. При провале G2-AF-* пользователь видит `message_ru` первой упавшей AF-проверки, то есть нейтральный текст abuse.yaml#messages_ru без раскрытия правил. При прочих блокерах — «Ревизия не прошла проверку безопасности для prod — подробности в отчёте G2».
- 2026-10-01 · M2-04 · Событие `abuse_flag` (gates.yaml#G2.antifraud_rules): если в G2 упала любая G2-AF-* (status=fail), в журнал модерации пишется {runId, orgId, systemId, revision, checks}. Тексты и evidence туда не попадают. В db.yaml нет таблицы журнала модерации, а тест миграций запрещает таблицы вне db.yaml. Поэтому журнал по умолчанию — структурная строка лога платформы `msg=abuse_flag, kind=abuse_flag, code=<id через запятую>`, она идёт в Loki и алерты. В тестах журнал подменяется через `PublishOptions.moderationLog`. Полный отчёт G2 при этом лежит в platform.gate_reports.
- 2026-10-01 · M2-04 · Ревью основателя (abuse.yaml#scoring.effect, #patterns.ori_signal). Если G2 пройден, но есть warn по G2-AF-08 или G2-AF-09, создаётся строка founder_reviews (system_id, revision, pending) с ON CONFLICT DO NOTHING. Публикация падает с GATES_FAILED и текстом abuse.yaml#messages_ru.review. FOUNDER_REVIEW_PENDING не входит в run_lifecycle.failure_codes, поэтому код прогона — GATES_FAILED. Пока ревью pending или rejected, GET /systems/:id отдаёт `publishBlockers` с FOUNDER_REVIEW_PENDING, а POST /publish этой ревизии — 403 FOUNDER_REVIEW_PENDING. Для rejected текст свой («Модератор не одобрил публикацию этой версии…»), отдельного кода в api.yaml нет. После approve повторная публикация снова прогоняет G0 и G2 (G1 уже пройден на ревизии), и warn больше не блокирует. Новая ревизия с тем же warn снова требует ревью: ревью привязано к ревизии.
- 2026-10-01 · M2-04 · Хранилище — миграция 0010_m2_moderation: platform.founder_reviews и platform.brand_allowlist, колонки строго по db.yaml плюс стандартный created_at. FK founder_reviews.system_id без cascade, как в db.yaml: строки систем не удаляются, а очистка удалённых систем их не трогает.
- 2026-10-01 · M2-04 · Решение staff (api.yaml#adminFounderReview): операция реализована в `decideFounderReview(db, {systemId, revision, decision, reviewer?, note?})` (false — ревизия не на ревью) и `pendingFounderReviews`. Маршрут POST /admin/systems/{id}/founder-review не смонтирован. api.yaml#info.x-auth.M2 требует staff с MFA (TOTP за 12 ч) и запись в staff_audit_log, а ни MFA, ни staff_audit_log пока нет (M2-08/M2-09). Открытый маршрут без MFA нарушил бы спеку. До тех пор действует CLI с прямым доступом к БД, по образцу `credits` (M1-03): `pnpm --filter @wizard/platform-api moderation reviews | approve <systemId> <revision> [note] | reject <systemId> <revision> <note>`. reviewer CLI не заполняет.
- 2026-10-01 · M2-04 · `secretExists(name)` (G2-SECRET-02 для prod) — значение секрета не читается. Секрет считается заданным, если есть строка platform.secrets_refs системы с этим именем для env=prod или env=draft либо задана переменная runtime `WIZARD_SECRET_<SYSTEMID>_<NAME>` (envSecretReader коннекторов, systemId = schema_key). Учитывается и draft, потому что ввода prod-секретов в платформе пока нет: needs_input kind=secret пишет только env=draft, а значение из чата — секрет системы. Когда появится отдельный ввод prod (OpenBao, M2-06), draft нужно убрать из проверки.
- 2026-10-01 · M2-04 · `abuse` из БД (`abuseContext`): orgAgeDays — целые сутки от orgs.created_at, plan — orgs.plan, brandAllowlist — brand_id из platform.brand_allowlist организации. abuseReportsPrev считается, только если уже есть platform.abuse_reports (`to_regclass`; таблицу создаёт M2-08): это жалобы на системы org со status ≠ dismissed. До M2-08 поле не передаётся, и сигнал не учитывается, как и задумано в G2.
- 2026-10-01 · M2-04 · Тесты: apps/platform-api/test/publish-g2.test.ts — 7 тестов на скриптованных гейтах: чистый G2, блок AF-01, блок PERM без abuse_flag, AF-08 → pending → 403 → approve → публикация, AF-09 → reject → 403, abuse context с abuse_reports, переключатель вехи. В golden.test.ts добавлен настоящий G2 через исполнителей. В migrations.test.ts добавлены founder_reviews и brand_allowlist.

## Остаётся (вне этой задачи)

- M2-09: `orgs.require_founder_review` (по умолчанию true): первая публикация каждой системы и публикации с новыми формами ПДн тоже должны идти через founder_reviews (abuse.yaml#identification.founder_review). Здесь ревью создают только warn G2-AF-08/09. Если включить это правило сейчас, при дефолте true блокировалась бы каждая публикация M2.
- M2-08/M2-09: маршрут `/admin/systems/{id}/founder-review` с staff+MFA и записью в staff_audit_log; уведомление владельцу о решении. Запись в brand_allowlist (staff) — тоже через админку.
- Спека: в db.yaml нет таблицы «журнала модерации» для abuse_flag. Предлагается либо `moderation_events {id, kind, org_id, system_id, revision, run_id, checks text[], created_at}`, либо явно записать в gates.yaml, что журнал — это лог платформы (Loki) плюс gate_reports. В run_lifecycle.failure_codes стоит добавить FOUNDER_REVIEW_PENDING, чтобы run_failed отличал ожидание модерации от провала проверок.
