# Пилот: проверка настроек перед выкатом (pilot-preflight)

Задача: основатель ввёл секреты и переменные GitHub, а прочитать их обратно нельзя. Нужен дешёвый прогон только на чтение, который до 40-минутного `apply` скажет, чего не хватает и что неверно.

Runbook — `docs/ops/deploy.md`, раздел «Проверка настроек (`check`)». Шаг основателя — `docs/founder/pilot-checklist.md`, шаг 8.

## Что сделано

- `tools/deploy/preflight.mjs` содержит пробы. `fetch` и SMTP-коннектор (`connect({host, port})` → TCP-сокет, плюс `ca`) внедряются, зависимостей нет — только `node:net` и `node:tls`, как у остального `pilot.mjs`. В workflow нет `pnpm install`.
- `tools/deploy/pilot.mjs check --env prod|staging`. Команда стоит первой в `COMMANDS`, `--tag` ей не нужен. Сначала `::add-mask::` для всех секретов-входов, затем `runPreflight`: `checkInputs("bootstrap")`, правила `envVars` для staging, живые пробы. Пробы бакета и пароля — `checkState`: `ensureStateBucket(create: false, attempts: 0)`, `getObjectOrNull`, `decryptBundle`. Модуль preflight не импортирует `pilot.mjs`, чтобы не было цикла.
- Workflow `bootstrap-pilot.yml`: у `action` варианты `[check, apply, destroy]`, по умолчанию `check`. Команда — `inputs.action == 'apply' && 'bootstrap' || inputs.action`.
- Workflow `pilot-reusable.yml`:
  - `authorize` принимает `check` и не требует `PROD`. Проверки владельца, `triggering_actor`, main, env и SHA остались.
  - `images` пропускается для `check` и `destroy`.
  - У задачи `pilot` `timeout-minutes` равен 5 для check и 90 для остального.
  - OpenTofu, оба шага кэша провайдеров, helm и `Tools` пропускаются через `if: inputs.command != 'check'`.
  - `Close SSH access` — `always() && inputs.command != 'check'`: check ничего не открывает и может идти с отклонённым `TWC_TOKEN`, а `close-access` с таким токеном упал бы. `Clean up the runner` остаётся `always()`, а `rm -rf` упасть не может.
- Вывод — таблица на русском в `GITHUB_STEP_SUMMARY`, те же строки в лог, `::error` для обязательных ошибок, `::warning` для предупреждений и необязательных ошибок. Код выхода 1, если не прошла обязательная проверка.

## Решения

- **Не печатать значения.** Сообщения называют только имена переменных. Хост SMTP тоже не печатается: основатель вводит его секретом. Дополнительно каждая строка лога и сводка проходят через `scrubber`: любое значение секрета длиной ≥ 6 символов заменяется на `***`. Ошибки `fetch` сводятся к коду (`ENOTFOUND`, «таймаут»), без URL: у Telegram токен стоит в пути.
- **Timeweb.**
  - Токен и баланс проверяются через `GET /api/v1/account/finances` (`balance`, `currency`, `hours_left`) и `/account/status` (`is_blocked`).
  - Домен ищется через `GET /api/v1/domains/{fqdn}` — это поиск домена по имени в OpenAPI Timeweb (`timeweb.cloud/api-docs-data/bundle.json`), туда же пишутся записи DNS (`/domains/{fqdn}/dns-records`). Исходник `twc_dns_zone` провайдера недоступен, так что «тот же запрос» — вывод, а не сверка с кодом.
  - Поддомен считается найденным, если его перечисляет родительская зона (`subdomains`). Это staging на поддоменах, как разрешает deploy.md.
  - Статус домена expired / no_paid / free и баланс ≤ 0 дают предупреждение, а не ошибку.
- **Cloud.ru.**
  - Запрос — `GET {base}/models`. Значение по умолчанию продублировано в `DEFAULT_BASE`, а тест сверяет его с `PROVIDERS` из `@wizard/llm`: импортировать TS в `.mjs` раннера без install нельзя.
  - `CLOUDRU_BASE_URL` учитывается, но в env задачи workflow не добавлен: платформа его не получает (`PLATFORM_PASSTHROUGH`), значит в CI проверяется тот адрес, которым пойдёт платформа.
- **Z.ai.**
  - По `docs.z.ai/llms.txt` у API нет списка моделей, баланса или иного бесплатного метода. Tokenizer — POST без сведений о тарификации, поэтому он не используется.
  - Вместо него проба запрашивает результат несуществующей задачи: `GET /async-result/wizard-preflight-0`. Это аутентифицированный GET без генерации.
  - 401 означает, что ключ отклонён (коды 1000–1005). 429 с кодами 1113/1309/1314/1316/1317 — нет баланса. JSON-ответ 200/400/404 — ключ прошёл аутентификацию. Всё прочее даёт «не проверено».
  - Как Z.ai отвечает на несуществующий id с верным ключом, вживую не проверено. Отсюда условие «JSON, а не страница прокси».
  - Z.ai необязателен (без ключа сборка идёт на Cloud.ru), поэтому его ошибка — только `::warning` и не влияет на код выхода.
- **Telegram.** Если токен задан, проверка обязательна: битый токен уронил бы `alertSettings` в bootstrap, а алерты — канал основателя. Если токена нет, строка «пропущено». `WIZARD_OPS_ALERT_URL` не вызывается: неизвестно, что за ним.
- **SMTP.**
  - Режим TLS выбирается как в `apps/platform-api/src/config.ts`: `WIZARD_SMTP_TLS`, иначе 465 — неявный TLS, остальные порты — STARTTLS. Разговор построен по `packages/connectors/src/smtp.ts`, но только до AUTH: `MAIL FROM` не отправляется никогда.
  - `WIZARD_SMTP_TLS=none` вместе с логином даёт ошибку: пароль без TLS не отправляется.
  - Без `WIZARD_SMTP_USER` проба только проверяет соединение и выдаёт предупреждение.
- **Пароль состояния.** Расшифровка существующих ключей окружения — проверка «пароль верный» без записи. Бакет не создаётся и не ожидается. Если бакета или ключей ещё нет, это «пропущено» или ok с пояснением.
- **SPF.** Значение — только механизмы `include: | a | mx | ip4: | ip6: | exists:` с необязательным квалификатором, без `v=spf1` и `all`.
- **Минуты Actions.** check — это две задачи, `authorize` и `pilot`. Без образов и OpenTofu. Каждая задача округляется до минуты, поэтому выходит ≈ 2 оплачиваемые минуты при реальном времени меньше минуты. Ниже двух не опуститься, не убрав отдельную `authorize`, а она должна идти до чтения секретов.
- Группа concurrency общая с apply (`pilot-<env>`): check, запущенный во время apply, ждёт его окончания. Это проще и не мешает.

## Тесты

- `tools/deploy/test/preflight.test.mjs`, 21 тест.
  - Каждая проба на фейковом `fetch`.
  - SMTP проверяется против локального приёмника на `node:net`/`node:tls` с самоподписанным сертификатом: он генерируется `openssl` в каждом прогоне, без openssl тесты пропускаются. Случаи: неявный TLS, STARTTLS, AUTH PLAIN и LOGIN, 535, нет STARTTLS, недоверенный сертификат, без логина. Проверено, что `MAIL` не отправляется.
  - Вся команда `main(["check", …])`: только GET, кроме одного `sendMessage`; маски до вывода; ни одного значения секрета (включая ключи S3 бакета состояния и сгенерированные ключи окружения) ни в одной строке лога, кроме `::add-mask::`, и ни в сводке. Ещё проверены неверный пароль состояния, отклонённый токен Timeweb (пробы доменов и бакета пропускаются), staging, экранирование таблицы и `scrubber`.
- `workflows.test.mjs`: новый `action` и его значение по умолчанию; shell-скрипт `authorize` исполняется в bash с разными контекстами (check без PROD, не владелец, не main, destroy prod, неизвестная команда); условия шагов и задачи `images`.
- `pilot.test.mjs`: `parseArgs` для `check`.

## Не сделано / на потом

- Живой прогон против реальных Timeweb, Cloud.ru, Z.ai, SMTP и Telegram не выполнялся: ключей в сессии нет. Первый `check` основателя и есть проверка проб. Особенно это касается ответа Z.ai на несуществующий id и формы `subdomains` у Timeweb.
- Спеку менять не нужно: `specs/platform/deploy.yaml#pilot` не перечисляет действия `bootstrap-pilot`, кроме `apply` / `destroy` для staging, и они остались.
