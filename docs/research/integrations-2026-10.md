# Интеграции: платежи, SMS, фото, коннекторы, Метрика, видео, домены, vision-LLM (04.10.2026)

> Справочник для агентов-исполнителей. Собран по официальной документации поставщиков на 04.10.2026. Всё, что не удалось подтвердить официальным источником, помечено **[не подтверждено]**. Выводы «рекомендуем» — инженерные решения автора, а не слова документации; они помечены словом «рекомендация».
>
> **Метод.** Часть сайтов (yookassa.ru, developer.tbank.ru, docs.robokassa.ru, amocrm.ru, help.prodamus.ru, docs.pexels.com, api-docs.cdek.ru) не открывалась напрямую из среды исследования. Их страницы читались через reader-прокси `r.jina.ai`, который отдаёт текст официальной страницы без правок. Документация Яндекс Cloud/AI Studio закрыта SmartCaptcha. Капчу мы не обходили, поэтому данные по Yandex взяты из выдачи поиска **[не подтверждено]**. Полный список ссылок — в конце.
>
> **Термины.** «Egress-хост» — хост, который нужно внести в allowlist egress-прокси (исходящие вызовы server-функций). «Клиентский хост» — хост, который нужен только браузеру посетителя сайта (CSP), в egress он не нужен.

## Кратко

1. **Входящие вебхуки почти нигде не подписаны.** Криптографическая подпись есть у CloudPayments (HMAC-SHA256), Prodamus (HMAC-SHA256, заголовок `Sign`), Т-Банка (SHA-256 «токен» с паролем терминала), Robokassa (хеш с Password #2). У ЮKassa, amoCRM, Tilda, МойСклад, СДЭК, SMS Aero подписи нет. Защита — секретный путь в URL, проверка IP там, где поставщик их публикует, и перезапрос объекта по API (ЮKassa, amoCRM, Bitrix24).
2. **Автоплатежи включаются людьми, а не API.** ЮKassa и Т-Банк включают сохранение способа оплаты только по заявке менеджеру. В Robokassa рекуррент «по предварительному согласованию» (ошибка 34, если не включён). У клиента-новичка это главный блокер подписок. Без подписки остаются разовые платежи и ручные ссылки.
3. **Секреты и ID для каждого поставщика свои, клиент получает их сам в личном кабинете.** Список полей — в таблице ниже и в п. 1.7.
4. **Статический исходящий IP нужен.** Тестовая среда Т-Банка работает только с IP из белого списка. Часть поставщиков публикует свои IP для входящих вебхуков (ЮKassa, CloudPayments, Robokassa), а для исходящих вызовов whitelist нужен Т-Банку. Если egress-прокси не имеет постоянного IP, Т-Банк в тесте не заработает.
5. **Prodamus, amoCRM, Bitrix24 живут на хосте клиента.** Egress-allowlist для них должен быть per-tenant (`<имя>.payform.ru`, `<sub>.amocrm.ru`, `<portal>.bitrix24.ru`) или с маской. Для Prodamus, Robokassa и Т-Банка ссылку на оплату можно собрать без исходящего вызова: подписанный URL открывает браузер клиента.
6. **Подводные камни по документации:** `crm.lead.add` в Bitrix24 объявлен устаревшим (нужен `crm.item.add`); в МойСклад вес запроса по логину и токену пользователя растёт до 4 единиц с 01.12.2026 (11 запросов за 3 секунды); у приватной интеграции amoCRM на нетехническом аккаунте клиент подписывает бессрочный отказ от техподдержки amoCRM; Unsplash требует hotlink и вызов `download_location`, то есть самохостинг картинок из его API запрещён; Let’s Encrypt выдаёт не больше 50 сертификатов на зарегистрированный домен в неделю, поэтому поддомены нашего же домена нельзя выпускать по одному.
7. **Vision.** Самый удобный вариант — Z.ai `glm-5.3-flash` (нативная мультимодальность, картинка URL или base64, $0.15/$0.50 за 1M токенов). В Cloud.ru из «внутренних» моделей картинки понимают `Qwen/Qwen3.6-35B-A3B`, `Qwen/Qwen3.5-397B-A17B`, `moonshotai/Kimi-K2.6`. Но спецификация Cloud.ru описывает `content` как строку, формат изображения в документации не показан **[не подтверждено]**. Qwen2.5-VL и GLM-4.5V в каталоге Cloud.ru нет.
8. **Метрика:** для счётчика достаточно `mc.yandex.ru` и `yastatic.net`; для Вебвизора добавляются `wss://mc.yandex.ru`, `mc.webvisor.com` и `blob:` в `frame-src` и `child-src`.

## 1. Платежи: подписки, автосписания, чеки 54-ФЗ

### 1.0. Что общего (рекомендации для адаптера)

- **Суммы.** ЮKassa: строка `"100.00"`. Т-Банк: целое число копеек. CloudPayments: число в рублях. Robokassa: строка через точку (в боевом ResultURL приходит с шестью знаками: `100.000000`, для подписи брать строку как пришла). Prodamus: строка/число в рублях.
- **НДС 22% с 01.01.2026.** ЮKassa: `vat_code` 11 (22%) и 12 (22/122). Т-Банк: `vat22`, `vat122`. Prodamus: `tax_type` 14 и 15. CloudPayments: в примерах документации `vat: 20`, значение 22 **[не подтверждено]**. Robokassa: список значений `tax` в выгрузке свёрнут, поддержка 22% **[не подтверждено]**. Для клиентов на УСН подставляем «без НДС».
- **Единый приёмник вебхуков.** Рекомендация: по маршруту на систему и поставщика (`/hooks/<systemId>/<provider>/<секрет>`), с сохранением сырого тела (подписи считаются по телу). Ответы разные, их надо отдавать точно:

| Поставщик | Ответ приёмника | Срок ответа |
|---|---|---|
| ЮKassa | HTTP 200, тело игнорируется | не указан |
| Т-Банк | HTTP 200 и тело `OK` (заглавные, без тегов) | 10 секунд |
| CloudPayments | JSON `{"code":0}` | 30 секунд |
| Robokassa | текст `OK{InvId}` (например `OK5`) | не указан |
| Prodamus | HTTP 200 (в примере тело `success`), иначе не 200 | не указан |
| Tilda | HTTP 200 (в примерах `ok`) | 5 секунд |
| МойСклад | HTTP 200 или 204 | 1500 мс |
| amoCRM | любой 2xx | 2 секунды |
| СДЭК | HTTP 200 | таймаут подключения 15 секунд |

- **Ретраи.** ЮKassa 24 часа; Т-Банк раз в час 24 часа, затем раз в сутки месяц; CloudPayments 100 попыток (интервалы 1, 2, 5, 10, 30 минут); Prodamus 7 попыток по URL (3 мин, 30 мин, 1, 3, 6, 12, 24 часа); amoCRM 5 попыток (5 мин, 15 мин, 15 мин, 1 час); SMS Aero 24 часа. Значит, обработчик обязан быть идемпотентным (ключ — `payment.id`, `PaymentId`, `TransactionId`, `InvId`).
- **Не доверять «success URL».** Редирект покупателя не доказывает оплату (прямо сказано в Robokassa). Заказ закрываем только по серверному уведомлению с проверкой суммы и номера заказа. Т-Банк требует сверять сумму заказа с суммой операции перед отгрузкой.

### 1.1. ЮKassa

**Документация:** https://yookassa.ru/developers/ , справочник https://yookassa.ru/developers/api , основы https://yookassa.ru/developers/using-api/basics , вебхуки https://yookassa.ru/developers/using-api/webhooks , автоплатежи https://yookassa.ru/developers/payment-acceptance/scenario-extensions/recurring-payments/basics , чеки https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/basics , тест https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing .
В английской версии документации сервис называется «YooMoney», хост и API остались `yookassa.ru`.

| Параметр | Значение |
|---|---|
| Base URL | `https://api.yookassa.ru/v3/` |
| Auth | HTTP Basic: `shopId` как логин, секретный ключ как пароль. OAuth 2.0 (Bearer) только для участников партнёрской программы |
| Egress | `api.yookassa.ru` |
| Клиентский хост | виджет `https://yookassa.ru/checkout-widget/v1/checkout-widget.js`; при `confirmation.type=redirect` покупатель уходит на страницу ЮKassa. Список CSP-хостов виджета **[не подтверждено]** |
| Формат | JSON в POST, query в GET и DELETE |
| Лимиты запросов | в документации не указаны **[не подтверждено]** |
| Комиссия | заголовок на главной «от 0,4% + НДС»; фактический тариф индивидуален **[не подтверждено]** |

**Что просить у клиента:** `shopId` (ЛК → Настройки → Магазин) и секретный ключ (ЛК → Интеграция → Ключи API; ключ создаётся и подтверждается SMS-паролем). Клиент делает это сам. Договор: клиент отправляет реквизиты компании, получает договор, подписывает (обычная или электронная подпись). Работа самозанятых: **[не подтверждено]** в официальной документации.

**Ключевые эндпоинты:** `POST /payments` (поля `amount{value,currency}`, `capture`, `confirmation{type: redirect|embedded|qr, return_url}`, `description` до 128 символов, `metadata` до 16 ключей, `receipt`, `save_payment_method`, `payment_method_id`), `GET /payments/{id}`, `POST /payments/{id}/capture`, `POST /payments/{id}/cancel`, `POST /refunds`, `POST /receipts`. Статусы платежа: `pending`, `waiting_for_capture`, `succeeded`, `canceled`.

**Автоплатежи (подписки):**
- По умолчанию доступны только в demo-магазине. Для боевого нужно написать менеджеру ЮKassa и заранее подготовить оферту: условия подключения и отключения автоплатежей, периодичность, суммы.
- Сохранение способа оплаты: `save_payment_method: true` в первом платеже (безусловно или по выбору покупателя на форме) либо привязка на нулевую сумму (событие `payment_method.active`). Из ответа сохраняем `payment_method.id` рядом с ID пользователя.
- Списание: `POST /payments` с `payment_method_id` и без подтверждения покупателя. Расписание и сумму ведём мы, ЮKassa их не хранит.
- Если покупатель отозвал разрешение в банке, платёж получает `canceled` и `cancellation_details.reason = permission_revoked`.
- Отключить сохранённый способ в ЮKassa нельзя, мы просто перестаём его использовать.

**Чеки 54-ФЗ.** Три режима: «Чеки от ЮKassa» (без собственной кассы и ФН, комиссия — процент с каждого успешного платежа, возврат без комиссии; значение процента в документации не указано **[не подтверждено]**), собственная онлайн-касса (только для организаций и ИП) или без чеков. В «Чеках от ЮKassa»:
- чек уходит только на email (SMS нет), поэтому email покупателя нужен всегда;
- данные передаются в `receipt` в запросе платежа или возврата (ФФД 1.2): `customer`, `items[]` (`description`, `quantity`, `amount`, `vat_code`, `payment_mode`, `payment_subject`, `measure`), `tax_system_code`;
- `tax_system_code`: 1 ОСН, 2 УСН доходы, 3 УСН доходы-расходы, 4 ЕНВД, 5 ЕСХН, 6 патент;
- `vat_code`: 1 без НДС, 2 0%, 3 10%, 4 20%, 5 10/110, 6 20/120, 7 5%, 8 7%, 9 5/105, 10 7/107, 11 22%, 12 22/122;
- `payment_mode`: `full_prepayment`, `partial_prepayment`, `advance`, `full_payment`, `partial_payment`, `credit`, `credit_payment`;
- `payment_subject`: `commodity`, `service`, `job`, `payment` и другие;
- чек для автоплатежа передаётся в том же запросе `POST /payments` **[не подтверждено в явном виде]**.
При собственной кассе есть три сценария: чек вместе с платежом, платёж после чека (если чек не пробит за 5 минут, платёж отменяется) и чек после платежа (отдельный запрос, `receipt` в платеже недопустим).

**Вебхуки.** События: `payment.waiting_for_capture`, `payment.succeeded`, `payment.canceled`, `refund.succeeded`, `payment_method.active`, `payout.*`, `deal.closed`. Тело: `{"type":"notification","event":"…","object":{…}}`.
- Настройка при Basic-авторизации — **только в личном кабинете** (клиент вставляет наш URL сам). Через API (`POST /webhooks`) вебхуки создаются только по OAuth. Требования к URL: HTTPS, порт 443 или 8443, TLS 1.2+, подойдёт и самоподписанный сертификат.
- Подписи нет. Проверка: IP из списка `185.71.76.0/27`, `185.71.77.0/27`, `77.75.153.0/25`, `77.75.156.11`, `77.75.156.35`, `77.75.154.128/25`, `2a02:5180::/32` и сверка статуса через `GET /payments/{id}`.

**Идемпотентность:** заголовок `Idempotence-Key` (до 64 символов, лучше UUID v4), обязателен для POST и DELETE, хранится 24 часа.

**Тест:** демо-магазин создаётся в ЛК (до 20 штук), `shopId` и секрет тестового магазина видны в ЛК, базовый хост не меняется. Тестовые карты без 3-D Secure: Visa `4111 1111 1111 1111`, Mastercard `5555 5555 5555 4444`, Мир `2202 4743 0132 2987`; срок любой будущий, CVC любой. Объект платежа несёт `test: true`. Реальные товары по демо-магазину отгружать нельзя. Автоплатежи в demo доступны без заявки.

**Подводные камни:** уведомления настраиваются в ЛК клиента (UX: показать URL и кнопку «проверить»); сохранённый способ работает у конкретного магазина; для самозанятых и «Чеков от ЮKassa» нужен email.

### 1.2. Т-Касса (интернет-эквайринг Т-Банка)

**Документация:** https://developer.tbank.ru/eacq , Init https://developer.tbank.ru/eacq/api/init , Charge https://developer.tbank.ru/eacq/api/charge , токен https://developer.tbank.ru/eacq/intro/developer/token , уведомления https://developer.tbank.ru/eacq/intro/developer/notification , автоплатежи https://developer.tbank.ru/eacq/scenarios/payments/nonPCI/autopay/ , тест https://developer.tbank.ru/eacq/intro/errors/test .

| Параметр | Значение |
|---|---|
| Base URL | боевой `https://securepay.tinkoff.ru/v2/`, тестовый `https://rest-api-test.tinkoff.ru/v2` |
| Auth | подпись `Token` в теле запроса (не заголовок). На странице Init в разделе Security значится «Bearer API Token», но руководство описывает только `Token` **[не подтверждено, как они соотносятся]** |
| Egress | `securepay.tinkoff.ru`, `rest-api-test.tinkoff.ru` (для тестов) |
| Клиентский хост | платёжная форма по `PaymentURL` на домене Т-Банка (хост **[не подтверждено]**) |
| Лимиты | не опубликованы **[не подтверждено]** |
| Комиссия | подключение 0 ₽, без абонплаты; ставка индивидуальная, её называет менеджер. Облачная касса CloudKassir от 1 800 ₽ в месяц для клиентов Т-Банка; «Чеки Т-Бизнеса» без аренды кассы для ИП без маркировки |

**Что просить у клиента:** `TerminalKey` и `Password` терминала из ЛК интернет-эквайринга (`business.tbank.ru/oplata/main`, раздел «Магазины» → «Терминалы»). Клиент должен быть юрлицом или ИП с доступом в Т-Бизнес. Нужен ли расчётный счёт именно в Т-Банке и доступ для самозанятых — **[не подтверждено]** официально. Также клиенту надо в настройках терминала указать `NotificationURL`.

**Подпись `Token` (SHA-256).** Берём все параметры корневого объекта запроса (вложенные `Receipt`, `DATA` не входят), добавляем `Password`, сортируем по имени ключа, конкатенируем только значения, считаем SHA-256 в UTF-8, кладём в `Token`. Пример из документации: `19200` + `Подарочная карта на 1000 рублей` + `00000` + `11111111111111` + `MerchantTerminalKey` → `72dd466f8ace0a37a1f740ce5fb78101712bc0665d91a8108c7c8a0ccd426db2`. В ЛК у операции есть поле `inittokenisvalid`.

**Init** (`POST /v2/Init`): `TerminalKey` (≤64), `Amount` (копейки, равен сумме `Items.Amount`), `OrderId` (≤50, уникален), `Token`, `Description` (≤140), `CustomerKey` (≤255), `Recurrent="Y"`, `PayType` (`O` одностадийная, `T` двухстадийная), `NotificationURL`, `SuccessURL`, `FailURL`, `RedirectDueDate` (от 1 минуты до 90 дней; по умолчанию 1440 минут), `DATA` (до 20 пар), `OperationInitiatorType` (`0`, `1`, `2`, `R`, `I`, `D`, `N`), `Receipt`. Минимальная сумма СБП 10 ₽. Другие методы: Confirm, Cancel, Charge, AddCard, AttachCard, GetCardList.

**Рекуррентные платежи (RebillId, Charge):**
- По умолчанию выключены. На DEMO-терминале включение — письмо на `acq_help@tbank.ru`, на боевом — персональному менеджеру.
- Родительская операция: `Init` с `Recurrent=Y` и `CustomerKey` (CC-покупка) либо `AddCard` (CC-привязка без оплаты). Нужна аутентификация 3DS или ввод CVV. После `AUTHORIZED` в уведомлении приходит `RebillId`.
- Дочерняя операция: `Init` на сумму, затем без редиректа `POST /v2/Charge` с `TerminalKey`, `PaymentId`, `RebillId`, `Token`; `OperationInitiatorType`: `R` рекуррентный (подписка), `I` по графику, `D` отложенный, `N` неявка, `2` покупатель инициирует сам.
- Подходит и для T-Pay, MIR Pay. Автоплатёж через СБП — только по API, привязывается счёт, а не карта.
- Сценарии `D` и `N` требуют родительскую CC-покупку с подтверждением, а не привязку.

**Чеки.** Объект `Receipt` обязателен, если подключена онлайн-касса: `Email` или `Phone`, `Taxation` (`osn`, `usn_income`, `usn_income_outcome`, `esn`, `patent`), `Items[]` до 100 (`Name` ≤128, `Price`, `Quantity`, `Amount` в копейках, `Tax`: `none`, `vat0`, `vat5`, `vat7`, `vat10`, `vat22`, `vat105`, `vat107`, `vat110`, `vat122`; `PaymentMethod` по умолчанию `full_payment`, `PaymentObject` по умолчанию `commodity`), `Payments`.

**Уведомления.** JSON POST на `NotificationURL` (из `Init` или настроек терминала). Если указан порт — только 443. Статусы платежа, привязка карты, фискализация. Для одностадийной оплаты приходят две нотификации: `AUTHORIZED` и `CONFIRMED`. Проверка: собрать все параметры кроме `Token` и вложенных `Data`, `Receipt`; добавить `Password`; отсортировать по ключу; склеить значения (булев `true` пишется как `true`; `null` не участвует); SHA-256; сравнить с `Token`. Для привязки карты набор: `TerminalKey`, `CustomerKey`, `RequestKey`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `CardId`, `Pan`, `ExpDate`, `NotificationType`, `RebillId`. Ответ `OK`; ретраи раз в час сутки, затем раз в день месяц; архив 90 дней. Список IP отправителя в документации не найден **[не подтверждено]**. Параметр `DATA` в уведомлении включается через менеджера.

**Идемпотентность:** отдельного ключа нет; `OrderId` должен быть уникальным, поведение при повторном `Init` с тем же `OrderId` не описано **[не подтверждено]**.

**Тест:** есть DEMO-терминал (без реальных списаний). Для реальных тестовых платежей используется боевой терминал на `rest-api-test.tinkoff.ru`, **IP клиента добавляется в белый список** через чат ЛК (ИНН, название организации, IP или пул, тестовый URL). Запросы на открытие платёжной формы тоже должны идти с whitelisted IP. Карты (срок любой, CVV 123): `2201382000000013` (3DS 2.0 frictionless), `2201382000000047` (challenge, пароль `1qwezxc`), `2201382000000831` (недостаточно средств), `2201382000000021` (ошибка списания), `2200770239097761` (без 3DS).

Серверный API: `/payments/cards/charge|auth` (по криптограмме), `/payments/cards/post3ds`, `/payments/tokens/charge|auth` (по токену), `/payments/confirm`, `/payments/void`, `/payments/refund`, `/payments/get`, `/payments/find`, `/orders/create`.

(1) Расписание ведёт CloudPayments: объект `recurrent` в виджете (`period`, `interval` Day|Week|Month, `amount`, `startDate`, `maxPeriods`, `receipt`) или `POST /subscriptions/create` (`Token`, `AccountId`, `Description`, `Amount`, `Currency`, `RequireConfirmation`, `StartDate` в UTC и в будущем, `Interval`, `Period`, `MaxPeriods`, `CustomerReceipt`); CloudPayments сам отвечает за периодичность и повторные попытки. Также `subscriptions/get|find|update|cancel`. (2) Расписание наше: списываем по токену. Токен действует только на терминале (`publicId`), где получен.

**Чеки.** CloudKassir: объект чека `Items[]` (`label`, `price`, `quantity`, `amount`, `vat`, `method`, `object`), система налогообложения и сумма электронных. Для чека подписки есть поле `CustomerReceipt` / `recurrent.receipt`.

**Уведомления.** Типы: `Check`, `Pay`, `Fail`, `Confirm`, `Refund`, `Recurrent`, `Cancel`. Включение и URL настраиваются в ЛК. Формат по умолчанию form-urlencoded, JSON настраивается. Подпись: заголовки `X-Content-HMAC` (считается по URL-decoded параметрам) и `Content-HMAC` (по URL-encoded телу). Алгоритм HMAC-SHA256, ключ `API Secret`, UTF-8, результат в base64; для POST сообщением является тело запроса. Ответ `{"code":0}`. Источники: `185.98.81.0/28`, `87.251.91.160/27`, `46.46.175.96/27`, `46.46.168.160/27`, `162.55.174.97/32`, `91.216.178.243/32`. SSL3 не поддерживается.

**Тест.** Тестовые карточные данные и реальные карты допускаются без списания, пока терминал в тестовом режиме (в ответах `TestMode: true`). В документации используется публичный `test_api_00000000000000000000002`, карта `4242 4242 4242 4242`.

### 1.4. Robokassa

**Документация:** https://docs.robokassa.ru/ru/pay-interface , уведомления https://docs.robokassa.ru/ru/notifications-and-redirects , рекуррент https://docs.robokassa.ru/ru/recurring-payments , фискализация https://docs.robokassa.ru/ru/fiscalization , тест https://docs.robokassa.ru/ru/testing-mode , XML-интерфейсы https://docs.robokassa.ru/ru/xml-interfaces .

| Параметр | Значение |
|---|---|
| Платёжный URL | `https://auth.robokassa.ru/Merchant/Index.aspx` (GET или POST) |
| Рекуррент | `https://auth.robokassa.ru/Merchant/Recurring` |
| XML-интерфейсы | `https://auth.robokassa.ru/Merchant/WebService/Service.asmx/<Метод>` |
| Egress | `auth.robokassa.ru`. Для платёжной ссылки исходящий вызов не нужен, URL подписывается локально |
| Комиссия | на главной «тариф на приём платежей от 1,8%» (маркетинг) **[не подтверждено]** |

**Что просить:** `MerchantLogin` (идентификатор магазина), `Пароль #1`, `Пароль #2` и выбранный алгоритм хеша (раздел «Мои магазины» → «Технические настройки», `partner.robokassa.ru/Shops`). Магазин должен быть активирован (иначе ошибка 25). Для теста используется отдельная пара тестовых паролей.

**Подпись `SignatureValue`.** Строка через двоеточия без пробелов: `MerchantLogin:OutSum:InvId:[Receipt]:[StepByStep]:[ResultUrl2]:[SuccessUrl2]:[SuccessUrl2Method]:[FailUrl2]:[FailUrl2Method]:[Token]:Пароль#1` и затем `:Shp_key=value` в алфавитном порядке. Хеш по умолчанию MD5; алгоритм должен совпадать с настройкой магазина (перечень допустимых алгоритмов в выгрузке не показан **[не подтверждено]**). Если `InvId` не передаётся, остаётся пустой слот (`OutSum::…`). В подпись `Receipt` входит в том виде, в котором передан (в примере документации — URL-encoded JSON). `IsWithoutFreeSale` и `FiscalParentOpId` в подпись не входят. Параметры `Shp_*` чувствительны к регистру. `InvId` уникален (иначе ошибка 40), в тесте не проверяется.

**ResultURL** (задаётся в ЛК, вызывается при успешной оплате): параметры `OutSum`, `InvId`, `Fee`, `EMail`, `SignatureValue`, `PaymentMethod`, `IncCurrLabel`, `Shp_*`. Проверка: хеш от `OutSum:InvId:Пароль#2[:Shp_…]` (с `OutSum` как пришёл, в бою с шестью знаками). Ответ `OK{InvId}`. IP: `185.59.216.65`, `185.59.217.65`. `ResultUrl2` — дополнительный POST в формате JWS (RS256), сертификат для проверки `https://docs.robokassa.ru/media/files/jwtsign.cer`, обязателен для уведомлений о холде. `SuccessURL` и `FailURL` подписываются Паролем #1, но не доказывают оплату.

**Рекуррент.** Услуга «только по предварительному согласованию» (ошибка 34, если не включена); готовое решение «Подписки» в ЛК (`partner.robokassa.ru/RecurringSubscription`) либо своя интеграция. Материнский платёж: обычная форма с `Recurring=true` (оплата картой). Дочерний: `POST https://auth.robokassa.ru/Merchant/Recurring` с `MerchantLogin`, `InvoiceID` (новый, не 0), `PreviousInvoiceID` (счёт первого платежа, в подпись не входит), `OutSum`, `SignatureValue`; без `IncCurrLabel`, `ExpirationDate`, `Recurring`. Ответ `OK+InvoiceId` не гарантирует списания, итог придёт на `ResultURL`/`ResultUrl2`. Есть также оплата по сохранённой карте (`Token`).

**Чеки.** `Receipt` — JSON в UTF-8, URL-encoded: `{"sno":"osn","items":[{"name","quantity","sum","cost","payment_method","payment_object","tax","nomenclature_code"}]}`. `sno` необязателен (берётся из ЛК): `osn`, `usn_income`, `usn_income_outcome`, `esn`, `patent`. `tax` обязателен. В чеке до 100 позиций, наименование до 128 символов, сумма позиций равна сумме операции; без номенклатуры — нарушение ФЗ-54. Решения: «Робочеки», облачная касса, своя касса. Если `Receipt` не передан, автоматически формируется позиция «Свободная продажа» (отключается `IsWithoutFreeSale`, чек регистрируется потом отдельным запросом).

**Тест:** `IsTest=1` и тестовые Пароль #1/#2 из технических настроек (боевые дадут ошибку 29). Тестовые оплаты не видны в ЛК. Есть демо-магазины (`https://docs.robokassa.ru/ru/demo-shops`).

### 1.5. Prodamus

**Документация:** https://help.prodamus.ru/payform/integracii/rest-api/instrukcii-dlya-samostoyatelnaya-integracii-servisov , секретный ключ и URL https://help.prodamus.ru/payform/integracii/rest-api/url-dlya-uvedomlenii-i-sekretnyi-klyuch , интервалы уведомлений https://help.prodamus.ru/payform/uvedomleniya/intervaly-uvedomlenii .

|---|---|
| Хост | страница клиента `https://<имя>.payform.ru/` (демо: `demo.payform.ru`) |
| Auth | HMAC-SHA256 от запроса, ключ — «секретный ключ» страницы |

Код интеграции `sys` согласуется с поддержкой Prodamus; в примере документации для самописных систем он может быть пустым (противоречие, **[не подтверждено]**).

Обязательные: `do` (`link` вернёт ссылку, `pay` переведёт покупателя на оплату), `products[]` (`name`, `price`, `quantity`; опционально `sku`, `type`: `course|service|goods`, `tax{tax_type,tax_sum}`, `paymentMethod`, `paymentObject`, `discount_value`), `sys`. Для самозанятых: `npd_income_type` (`FROM_INDIVIDUAL`, `FROM_LEGAL_ENTITY`, `FROM_FOREIGN_AGENCY`), `npd_income_inn`, `npd_income_company`.

**Подпись запроса:** привести все значения к строкам, отсортировать ключи по алфавиту рекурсивно, перевести в JSON, экранировать `/`, подписать HMAC-SHA256 секретным ключом, результат — параметр `signature`. Готовые библиотеки `Hmac` (PHP, Python).

**Подписки.** Параметр `subscription` (id подписки; передаётся вместо `products`), `subscription_date_start`, `subscription_demo_period`, `subscription_limit_autopayments`. Списания ведёт Prodamus. Уведомления о платежах по подписке настраиваются отдельно во вкладке «Подписки», иначе автоплатежи молчат.

**Чеки.** Самозанятые и ИП на НПД чеки получают автоматически (касса не нужна). Для ИП на других режимах и ООО нужна облачная касса Prodamus или своя.

**Вебхук.** URL (можно несколько) в настройках страницы. Приходит POST (в примере разбирается как `$_POST`), заголовок `Sign` — подпись (HMAC-SHA256 тела по секретному ключу). Верификация: тот же алгоритм (сортировка, JSON, `/`), сравнить с `Sign`. При несовпадении вернуть не 200. При успехе — 200.

**Тест:** в настройках страницы включается демо-режим (не влияет на подпись). Если боевой режим отключает сама система Prodamus, подпись намеренно меняется (ключ с суффиксом demo), чтобы демо-платёж нельзя было принять за реальный. Тестовая страница `demo.payform.ru` доступна по запросу у менеджеров.

## 2. SMS-агрегаторы (транзакционные SMS, Россия)

**Общие правила.**
- Имя отправителя (альфа-имя): латиница, цифры, знаки, до 11 символов. Оно должно подтверждаться брендом, названием организации, товарным знаком или доменом. Агрегаторы вправе требовать подтверждающие документы. Операторы вправе блокировать сообщения.
- Подключается и согласуется у операторов в личном кабинете агрегатора. Сроки: SMS.ru заявляет 1–2 рабочих дня, иногда до недели; общая справка по рынку (Unisender) — до 30 рабочих дней **[не подтверждено для SMS Aero и SMSC]**.
- Платное имя тарифицируется помесячно по каждому оператору. SMS Aero: МТС 3 000 ₽, МегаФон 2 550 ₽, t2 2 450 ₽, Билайн 2 100 ₽, Мотив 2 250 ₽ в месяц. SMSC: МТС 3 000 ₽, Билайн 3 325 ₽ и т.д. Цена каждой SMS зависит от оператора, типа сообщения (рекламное, сервисное/шаблонное, авторизационное, транзакционное), числа SMS одному абоненту за месяц и суммы пополнения.
- Альфа-имя могут зарегистрировать только юрлица и ИП (прямо сказано в документации Exolve). Самозанятые у остальных **[не подтверждено]**.
- Сервисные и авторизационные SMS по шаблонам дешевле рекламных; шаблоны тоже согласуются с операторами и имеют абонплату.
- Рекомендация: заводить отдельное имя на клиента (бренд клиента), не отправлять от общего имени платформы.

### 2.1. SMS Aero

**Документация:** https://smsaero.ru/integration/documentation/api/ . Base `https://gate.smsaero.ru/v2`. Egress: `gate.smsaero.ru`.
- **Auth:** HTTP Basic: логин — email аккаунта, пароль — API-ключ (`https://smsaero.ru/cabinet/settings/apikey/`). Ответы JSON (или XML по `Accept`).
- **Отправка:** `POST/GET /sms/send`: `number` или `numbers[]`, `sign` (имя; по умолчанию `SMS Aero` только для теста), `text`, `dateSend` (unixtime), `callbackUrl`, `callbackFormat=JSON`, `shortLink=1`. Ответ: `id`, `from`, `number`, `status`, `extendStatus`, `cost`, `dateCreate`, `dateSend`.
- **Статусы:** `0` в очереди (`queue`), `1` доставлено (`delivery`), `2` не доставлено (`undelivered`), `3` передано (`sent`), `4` ожидание (`wait`), `6` отклонено (`reject`), `8` на модерации (`moderation`).
- **Callback:** POST на `callbackUrl` с `id`, `status`, `extendStatus` (form-urlencoded или JSON). Ждёт HTTP 200, иначе повторы 24 часа. Подписи нет; защита — секрет в пути URL.
- **Другое:** `/sms/status?id=`, `/sms/list`, `/balance`, `/tariffs`, `/sign/list` (имена со статусами по операторам), `/sms/testsend`, `/sms/teststatus`, `/hlr/check`, группы и контакты.
- **Тест:** `sms/testsend` (тестовая отправка). Бесплатное имя требует указывать в тексте источник (организация, адрес сайта), иначе блок оператором.
- **Цена:** заявлено от 2,79 до 14,19 ₽ за SMS; без минимальных пакетов; тариф зависит от разового пополнения и действует до исчерпания суммы или 30 дней. Физлица платят картой, юрлица по счёту.
- **Лимиты API:** не найдены **[не подтверждено]**.

### 2.2. SMSC

**Документация:** https://smsc.ru/api/http/ . Egress: `smsc.ru`.

### 4.1. amoCRM

**Документация:** https://www.amocrm.ru/developers/ , OAuth https://www.amocrm.ru/developers/content/oauth/step-by-step , сделки https://www.amocrm.ru/developers/content/crm_platform/leads-api , вебхуки https://www.amocrm.ru/developers/content/crm_platform/webhooks-api , формат вебхука https://www.amocrm.ru/developers/content/crm_platform/webhooks-format , ограничения https://www.amocrm.ru/developers/content/api/recommendations .

- **Хосты.** `https://{subdomain}.amocrm.ru` (аккаунты `amocrm.com`/`kommo.com` на других доменах). В egress нужен хост клиента: `*.amocrm.ru`. Страница выдачи доступа `https://www.amocrm.ru/oauth` нужна только браузеру.
- **Способы авторизации.**
  1. OAuth 2.0 (authorization code): `client_id` = ID интеграции, `client_secret`, `redirect_uri`; обмен кода на токены `POST https://{subdomain}.amocrm.ru/oauth2/access_token`. `access_token` живёт 86 400 секунд, `refresh_token` 3 месяца (если интеграция не используется 3 месяца, токен умирает). Заголовок `Authorization: Bearer <access>`. Код авторизации действует 20 минут. Домен `redirect_uri` не может быть кириллическим и должен быть с SSL.
  2. **Долгоживущий токен** (с февраля 2024, для приватных и внешних интеграций): вкладка «Ключи» → «Сгенерировать токен», срок от 1 дня до 5 лет, виден один раз, `refresh_token` нет, привязан к конкретному аккаунту. Подходит для одного аккаунта.
- Рекомендация для MVP: клиент создаёт приватную интеграцию у себя и вставляет долгоживущий токен и поддомен. Развернутый OAuth даёт нам одна публичная интеграция Wizard.
- **Важное ограничение.** При подключении приватной интеграции на аккаунте, который не является техническим, клиент заполняет заявление об отказе от технической поддержки amoCRM. Оно бессрочно и необратимо (консультации и вопросы по оплате остаются). Создавать интеграцию может только администратор аккаунта.
- **Лимиты.** Не более 7 запросов в секунду на интеграцию и 50 в секунду на аккаунт; сверх лимита HTTP 429, при систематических нарушениях аккаунт блокируется (403). Страница — до 250 сущностей (местами до 500).
- **Создание заявки.** `POST /api/v4/leads/complex` (до 50 сделок за запрос; на сделку не более 1 контакта и 1 компании; до 40 доп. полей на сущность; нет обязательных полей). Тело: массив `{name, price, pipeline_id, status_id, responsible_user_id, custom_fields_values, tags_to_add, _embedded:{contacts:[{first_name, custom_fields_values:[{field_code:"PHONE", values:[{value, enum_code:"WORK"}]}]}], companies, tags, metadata}}`. Если передать `_embedded.metadata` (`category`: `forms` или `sip`), сделка уйдёт в «Неразобранное». Дубли ищутся только если включён «Контроль дублей» для интеграции; сам метод не дедуплицирует.
- **Вебхуки.** Подписка: `POST /api/v4/webhooks` (`destination`, `settings` — список событий) или в интерфейсе. Формат запроса `application/x-www-form-urlencoded` с вложенными массивами `{entity:{action:{0:{…}}}}`; при удалении — `{entity:{action:"id"}}`. Ответ 2xx за 2 секунды; ретраи: 5 мин, 15 мин, 15 мин, 1 час; хук отключается, если за 2 часа пришло более 100 невалидных откликов (администраторы получают уведомление). **Подписи нет в документации [не подтверждено]**; рекомендация: секрет в URL и перезапрос сущности по её `id`.
- **Тест:** песочницы нет; нужен тестовый аккаунт amoCRM (условия пробного периода **[не подтверждено]**).

### 4.2. Bitrix24

**Документация:** https://apidocs.bitrix24.ru/ , вебхуки https://apidocs.bitrix24.ru/local-integrations/local-webhooks.html , OAuth https://apidocs.bitrix24.ru/settings/oauth/index.html , события https://apidocs.bitrix24.ru/api-reference/events/index.html , безопасность обработчиков https://apidocs.bitrix24.ru/api-reference/events/safe-event-handlers.html , лимиты https://apidocs.bitrix24.ru/limits.html .

- **Входящий вебхук:** `https://{portal}.bitrix24.ru/rest/{user_id}/{webhook_code}/{method}.json`. Секрет — сам URL, права определяются создавшим сотрудником и выбранными `scope`. Создать может администратор или сотрудник с разрешением. Подходит для одного портала; часть методов вебхуком недоступна. Рекомендация для MVP: клиент вставляет полный URL вебхука.

- **Лид.** `crm.lead.add` помечен **DEPRECATED («развитие метода остановлено»)**, нужно `crm.item.add` с `entityTypeId` (1 лид, 2 сделка, 3 контакт, 4 компания). Поля старого метода: `TITLE`, `NAME`, `LAST_NAME`, `PHONE: [{VALUE, VALUE_TYPE}]`, `EMAIL`, `SOURCE_ID` (например `WEB`), `STATUS_ID` (`NEW`), `COMMENTS`, `ASSIGNED_BY_ID`, `UTM_*`. Проверка подлинности — сравнение `auth.application_token` с токеном, выданным при создании. В событии лишь ID объекта, поэтому нужен дополнительный вызов метода. Обработчик доступен из внешней сети.
- **Лимиты:** алгоритм leaky bucket; при превышении HTTP 503 с `QUERY_LIMIT_EXCEEDED`; запрос не дольше 60 секунд. Числовые пороги в выгрузке не показаны **[не подтверждено]**.

### 4.3. Tilda (входящий webhook)

### 4.4. МойСклад

**Документация:** https://dev.moysklad.ru/doc/api/remap/1.2/ (SPA; исходники в репозитории GitHub `moysklad/api-remap-1.2-doc`).

- **Base:** `https://api.moysklad.ru/api/remap/1.2`. Egress: `api.moysklad.ru`.
- **Auth:** Basic (логин и пароль пользователя) или `Authorization: Bearer <токен>`. Токен пользователя выдаёт `POST /security/token` с Basic. Бывает токен решения (приложения, через Vendor API). Обязателен заголовок `Accept-Encoding: gzip`: без него и с другой кодировкой ответ 415.

Для логина/пароля и токена пользователя вес растёт: с 12.05.2026 — 2 (22 запроса за 3 с), с 01.09.2026 — 3 (15 за 3 с), **с 01.12.2026 — 4 (11 за 3 с)**. Токен публичного или приватного решения остаётся на 45 за 3 с; решение в статусе «Черновик» или «На модерации» с 13.04.2026 — 11 за 3 с. `GET /report/stock/all` и `/report/stock/bystore` весят 5. Параллельно не более 5 запросов от пользователя или решения и 20 от аккаунта; до 8 КБ в заголовках; до 20 МБ в теле; до 1000 объектов в массиве. Превышение: 429. Пара `entityType` + `action` уникальна. МойСклад шлёт `POST <url>?requestId=<uuid>` с JSON `{events:[{meta, action, accountId, updatedFields}]}`; ждёт 200 или 204 в течение 1500 мс; неудачные попытки идут подряд без пауз, `requestId` при повторе тот же. Заголовок запроса `X-Lognex-WebHook-DisableByPrefix` отключает вебхуки по префиксу URL (против эха от собственных записей). Подписи нет **[не подтверждено]**. Сертификат получателя должен иметь корректную цепочку.
- **Тест:** бесплатный демо-аккаунт **[не подтверждено]**.

## 5. Яндекс Метрика: CSP и SPA

**Документация:** https://yandex.ru/support/metrica/ru/code/install-counter-csp , SPA https://yandex.ru/support/metrica/ru/code/counter-spa-setup , `hit` https://yandex.ru/support/metrica/ru/objects/hit .

**Минимальный CSP (клиентские хосты) по документации:**

```
Content-Security-Policy:
  script-src 'self' 'nonce-<N>' https://mc.yandex.ru https://yastatic.net;
  img-src    'self' data: https://mc.yandex.ru;
  connect-src 'self' https://mc.yandex.ru wss://mc.yandex.ru https://mc.webvisor.com wss://mc.webvisor.com;
  frame-src  blob: https://mc.yandex.ru;
  child-src  blob: https://mc.yandex.ru;
```

- `script-src`: `https://mc.yandex.ru` (тег `https://mc.yandex.ru/metrika/tag.js`) и `https://yastatic.net`. Для inline-кода счётчика нужен `nonce` на элементе `script` (CSP-nonce на каждый ответ) либо вынос кода во внешний файл (`/metrika.js`), тогда `nonce` не нужен.
- `img-src`: `https://mc.yandex.ru` для пикселя в `noscript` (`https://mc.yandex.ru/watch/<id>`). `'self' data:` — наш добавок.
- `connect-src`: `https://mc.yandex.ru`. В «общем списке адресов» документации также `wss://mc.yandex.ru` (Вебвизор), `https://mc.webvisor.com`, `https://mc.webvisor.org` и их `wss://`.
- Вебвизор: `child-src` и `frame-src` с `blob:` и `https://mc.yandex.ru`.
- `frame-ancestors` нужен, только если открываем свой сайт внутри интерфейса Метрики (карты кликов). Список: `metrika.yandex.ru`, `metrica.yandex.com`, `metrika.yandex.by`, `metrika.yandex.kz`, `metr.yandex.ru` и ещё ~20 региональных (в выгрузке документации).
- Региональные зеркала `mc.yandex.az|by|co.il|com|com.am|com.ge|com.tr|ee|fr|kg|kz|lt|lv|md|tj|tm|uz` нужны, если счётчик обращается к ним; для аудитории РФ достаточно `mc.yandex.ru` **[не подтверждено]**. `worker-src` документация не упоминает **[не подтверждено]**.
- Пример в документации содержит опечатку `frame-ancestors:` с двоеточием; в заголовке его быть не должно.

**SPA.** Инициализация с `defer: true`, чтобы отключить автоматический просмотр:

```js
ym(ID, 'init', { defer: true, clickmap: true, trackLinks: true, accurateTrackBounce: true, webvisor: true });
// на каждую смену маршрута:
ym(ID, 'hit', location.pathname + location.search, { title: document.title, referer: prevUrl });
```

`hit(url, options)`: `options.title`, `options.referer`, `options.params`, `callback`, `ctx`. Цели без смены URL — `ym(ID, 'reachGoal', 'GOAL')`. Параметры визита `params`, посетителя `userParams`. Для e-commerce `dataLayer.push({ecommerce:{purchase:{…}}})`, `hit` вызывается один раз при переходе на новую страницу.

## 7. Кастомные домены клиентских сайтов (Traefik + cert-manager на k3s)

### 7.1. Рекомендуемая схема (рекомендация автора)

1. **Целевой хост** `sites.<наш-домен>` — для поддоменов клиента (`www.example.ru`, `shop.example.ru`) CNAME на него. Для корня (apex) CNAME нельзя, поэтому по умолчанию A-запись на статический IP входа (IPv4; AAAA только если у нас есть IPv6 и мы его отдаём). ALIAS/ANAME работает только у некоторых регистраторов и DNS-хостингов, как основной способ не годится.
2. **Проверка владения (TXT)** до привязки: клиент создаёт `_wizard-verify.<домен>` TXT со значением-токеном. Это не требование Let’s Encrypt, а защита от привязки чужого домена и от висящих записей; HTTP-01 всё равно докажет контроль над трафиком домена.
3. **Сертификат на каждый домен:** ресурс `Certificate` на apex + `www` (secret на домен), `ClusterIssuer` типа ACME с solver HTTP-01 и `ingressClassName: traefik` (поле добавлено в cert-manager 1.12; рекомендовано документацией). Можно и аннотацией `cert-manager.io/cluster-issuer` на Ingress (ingress-shim). cert-manager сам создаёт временный `Ingress` и pod `acmesolver`. Для кириллических доменов (.рф) в `dnsNames` ставить punycode (`xn--…`).
4. **Не выпускать по сертификату на каждый поддомен нашего же домена** (`клиент.sites.<наш-домен>`): лимит 50 сертификатов на зарегистрированный домен в неделю. Выход: один wildcard `*.sites.<наш-домен>` через DNS-01 (нужен API нашего DNS-провайдера) либо запись в Public Suffix List. Кастомные домены клиентов лимитом не затрагиваются, у каждого свой зарегистрированный домен.
5. **Сначала staging-issuer**, потом боевой. Сброса лимитов нет, лимиты «восстанавливаются» постепенно.

### 7.2. Факты Let’s Encrypt (https://letsencrypt.org/docs/rate-limits/ , https://letsencrypt.org/docs/challenge-types/)

| Лимит | Значение |
|---|---|
| Новые сертификаты на зарегистрированный домен | 50 за 7 дней (глобальный, общий для всех аккаунтов) |
| Идентичный набор имён | 5 сертификатов за 7 дней |
| Новые заказы на аккаунт | 300 за 3 часа (восстановление 1 заказ в 36 секунд) |
| Ошибки авторизации на имя и аккаунт | 5 в час |
| Аккаунты с одного IP | 10 за 3 часа |
| Продления через ARI | вне всех лимитов |
| Продления без ARI с тем же набором имён | считаются продлением: освобождены от лимитов «новые заказы на аккаунт» и «новые сертификаты на домен», но подпадают под «5 на идентичный набор» и «ошибки авторизации» |

HTTP-01: только порт 80; следует редиректам до 10 уровней, только на `http:` и `https:` и порты 80/443; сертификаты при редиректе на HTTPS не проверяет; **не выдаёт wildcard**. DNS-01 даёт wildcard, но нужен API DNS.

Подводные камни:
- Let’s Encrypt проверяет **с нескольких точек сети** (multi-perspective validation). Нельзя закрывать порт 80 или резать зарубежные IP на уровне WAF и Traefik.
- Если у домена есть AAAA, проверка идёт **по IPv6 в первую очередь**; неверный AAAA ломает выпуск. Просить клиента удалять чужие AAAA или отдавать наши.
- CAA-записи должны разрешать `letsencrypt.org`.
- DNSSEC с ошибкой у регистратора ломает проверку (Tilda рекомендует отключать).
- Wildcard-записи A и CNAME на стороне клиента Tilda просит не использовать.
- Глобальный редирект HTTP→HTTPS на entrypoint Traefik и HTTP-01: сам Let’s Encrypt редиректы на HTTPS проходит, но временный Ingress cert-manager должен обслуживаться и на `websecure`; проверять на стенде **[не подтверждено]**.
- Распространение DNS: Tilda называет 3–24 часа, Taplink 2–4 часа. UI должен уметь ждать и перепроверять сам (кнопка «Проверить DNS» + фоновый опрос).

### 7.3. Как формулируют инструкцию Tilda и Taplink (для текстов в UI)

| | Tilda | Taplink |
|---|---|---|
| Корневой домен | два способа: делегировать на NS-серверы Tilda (`ns1.tildadns.com`, `ns2.tildadns.com`) или прописать A-запись на IP, который сервис показывает в «Настройки сайта → Домен» | делегирование на NS-серверы Taplink (панель управления DNS-зоной на их стороне) |
| Поддомен | A-запись на тот же IP | запись `CNAME` на `cname.taplink.cc`, ждать 2–4 часа, нажать «Проверить DNS» |
| Что сказано про ожидание | изменения занимают от 3 до 24 часов; пока не вступили, «домен подключен» не появится | 2–4 часа |
| Предостережения | на корневой домен только одна A-запись (остальные удалить); не использовать wildcard A/CNAME; при делегировании на их NS в панели DNS у них доступны только записи TXT и MX | на их NS можно добавлять MX, TXT, CNAME и A; для Яндекс.Вебмастера и Google подтверждение владения через мета-тег |
| Помощь | пошаговые инструкции для Reg.ru, RU-CENTER, GoDaddy, 2domains, Timeweb, Beget, ps.kz и др. | вкладка «Публикация → Подключение домена» |

Рекомендация для текста в Wizard: «Добавьте у регистратора две записи: A на `<IP>` для `example.ru` и CNAME `www` на `sites.<домен>`; затем TXT `_wizard-verify` со значением `<токен>`. Обновление записей занимает от нескольких минут до суток. Если запись для домена уже есть, удалите старую». Показывать чек-лист с автопроверкой каждой записи и расшифровкой, какой записи не хватает.

## 10. Что основателю зарегистрировать или запросить

1. **Статический исходящий IP** для egress-прокси. Нужен для whitelist тестовой среды Т-Банка (чат ЛК, ИНН + IP + URL) и защищает от блокировок антифродом SMS.ru.
2. **Production-одобрение Unsplash** (заявка с демонстрацией атрибуции, hotlink и `download_location`) и снятие лимитов Pexels письмом `api@pexels.com`.
3. **Приложение МойСклад («решение»)** для лимита 45 запросов за 3 секунды вместо 11 (после 01.12.2026) и нормальной установки.
4. **Публичная интеграция amoCRM** (если нужен OAuth без вставки токена) либо принять сценарий «приватная интеграция + долгоживущий токен». Предупредить клиентов об отказе от техподдержки amoCRM.
5. **Приложение Bitrix24** для OAuth (если вебхук-URL клиента нас не устраивает).
6. **Договор с SMS-агрегатором** и решение, чьим аккаунтом отправляем (платформа или клиент), плюс процесс согласования имён и шаблонов (1–2 дня и до недель).
7. **Аккаунты и платёж Z.ai**, **сервисный аккаунт Cloud.ru FM**, ключ **Yandex AI Studio**; дымовые тесты vision на Cloud.ru.
8. **Домен и IP входа для кастомных доменов**: `sites.<домен>`, статический IPv4 на Traefik, DNS-провайдер с API (для wildcard `*.sites.<домен>` по DNS-01).
9. **Партнёрская программа ЮKassa** (OAuth), если хотим создавать вебхуки по API и не просить клиента вставлять URL.
10. Юридически: оферта на автоплатежи (требует ЮKassa), шаблоны согласий; обработка телефонов и email покупателей через SMS и платёжные API относится к ПДн **[не подтверждено юристом]**.
